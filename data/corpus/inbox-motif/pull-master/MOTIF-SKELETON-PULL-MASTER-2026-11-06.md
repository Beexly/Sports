### 2.1 The assembled stack, as it now stands

The four lanes independently converged on one composable stack with no overlapping seats (repos lane synthesis states the composition explicitly; the other three lanes supplied its mechanisms, data, and evidence):

1. **Proof standard — EleutherAI/lm-evaluation-harness** (Repos D1, MIT, v0.4.13): the benchmark program's execution layer. Every program suite exists in it as a task except ForecastBench, which keeps its own harness. Its n-gram decontamination janitor is the admission gate for both data fuel lines — no public or user-derived batch teaches the model before it is checked against the seven suites. Pin harness version in every results table; scores across versions are not comparable.
2. **Forecasting arena — ForecastBench + Metaculus** (Social #14, #13; Repos D7): ForecastBench's submission protocol is fully documented (biweekly rounds, 500 questions, ≥95% coverage, Baseline and Tournament boards; datasets CC-BY-SA-4.0 with reasoning traces and resolutions on GitHub/HF; next FRI-called round **November 9, 2026**). The Metaculus bot template + forecasting-tools (Repos D7, both MIT) is the live Fall 2026 FutureEval arena client: every submitted forecast plus its resolution becomes a third-party-scored, outcome-labeled calibration example produced by the system's own operation — no consent surface, because it is the system's own behavior, not user data. The AIA Forecaster recipe (Social #13: multi-forecaster ensemble + supervisor reconciliation + Platt calibration; search ablation collapses Brier 0.1002 → 0.3609) is the implementable forecasting-head architecture for that arena.
3. **Post-training core — huggingface/trl** (Repos D2, Apache-2.0, v1.17.1): DPO consumes the crowd-preference queue; GRPO/DAPO consumes verifiable rewards (ForecastBench resolutions, execution checks, answer verification). The RLHF Book (Social #16; X6, X10, X11) is its reference text and single-GPU prototype lab. Algorithm-choice discipline comes from oxRL (X P3): rankings invert with scale, and 0 of 20 DPO variants beat vanilla DPO after correction — vanilla-first, scale-revalidated.
4. **Candidate factory + promotion mechanism — allenai/open-instruct + RRSI** (Repos D3; Social #3): open-instruct's rejection sampling is the candidate factory (the live model samples, execution/outcome verification filters, survivors become preference data — verification by code or resolved outcome, never self-asserted), and its IPC weight broadcast into live vLLM engines is promotion without redeploy. RRSI (Google Research, Social #3, Apache-2.0, working code) supplies the promotion gate itself: leakage critic screening every candidate edit for benchmark contamination before evaluation, noise-adjusted acceptance floor, cost rule, evidence ledger. SIA (Social #8, MIT) is the closest existing open implementation of the combined harness+weights loop, with GPQA built in as a task.
5. **Adapter factory + cheap composition — axolotl + mergekit** (Repos D5, D6; IG SK-16, SK-19 cluster): axolotl's config-as-code makes every candidate a diffable YAML plus a checkpoint — the promotion pipeline's audit trail — with checkpoint mirroring for preemptible GPU runs. Mergekit's TIES/DARE generalized task arithmetic generates merge candidates at RAM cost; its evolve search uses the harness as fitness function. The IG lane's adapter-audit finding rides in front of both (Social #19 cluster / IG SK-19 dossier): only 7.5% of sampled public LoRAs pass a basic provenance audit — the skeleton merges only adapters it trained or audited itself.
6. **Scale path — modelscope/ms-swift** (Repos D4, Apache-2.0): Megatron-bridge full-parameter training when a candidate outgrows single-node TRL; a framework-free GRPO advantage core; multi-turn agent RL environments; and the field's most honest public derivation of the training/inference mismatch problem (rollouts come from π_vLLM ≠ π_θ even with synchronized weights), with its importance-sampling correction documented in the open.
7. **Intake — crawl4ai** (Repos D9, Apache-2.0): Fuel Line 1's collection arm — best-first frontier scoring, Freshness/DomainAuthority admission features, content-hash-addressed storage (every ingested document provenance-addressable), and adaptive-crawling saturation as a measured stopping rule whose semantic-gap output is itself a gap audit per crawl.
8. **Internal gateway + capture pattern — litellm** (Repos D8, MIT core): fleet-side routing/budgets/fallbacks and the interaction-record schema template for the user-data fuel line. Explicitly **not** the public provider face; that seat stays with the skeleton's own provider implementation. ### 2.2 The near-minute learning claim — the verified mechanisms behind it

Prompt 2 demanded the honest minute: what can actually change minute-to-minute, with a mechanism and a measurement for each claim. The lanes found seven named mechanisms, each verified at its primary source unless flagged:

- **TTT-E2E** (X3; arXiv:2512.23675, public code): weight-level learning from context at inference — a Transformer with sliding-window attention keeps training via next-token prediction on the context it reads, compressing context into MLP weights, with a meta-learned initialization so it is good *after* its test-time updates; constant inference latency (2.7× faster than full attention at 128K, 3B-scale evidence). Its session-local form is the ZDR-compatible variant. A second, independent TTT family — **In-Place TTT** (Social #7, arXiv:2604.06169, Apache-2.0 code; X B4) — turns each MLP block's final projection into fast weights updated during inference, a drop-in with no new modules. The design fork between the two families is now a named decision, not a vague direction.
- **Anytime-valid e-value evaluation** (X1): the forecasting-mathematics map documents evaluation's shift from fixed-sample tests to e-values and test martingales (Choe & Ramdas 2024) — statistics that stay valid under continuous monitoring, which is exactly what a promotion gate that checks candidates every minute requires. This is the statistical license for near-minute promotion decisions.
- **open-instruct IPC weight broadcast** (Repos D3): after each training step, updated weights broadcast over IPC into live vLLM rollout engines without restarting them — promotion is a weight-sync event, not a redeploy.
- **TRL experimental async trainers** (Repos D2): `async_grpo` (rollout/training decoupled so generation never blocks the learner), `online_dpo` (preference training on live-generated pairs), and BEMA (EMA-smoothed reference model for long online runs) — the research track for collapsing the candidate cycle toward minute cadence.
- **SDFT** (X P2; arXiv:2601.19897, code+data public): the update rule for demonstration-class data — a demonstration-conditioned copy of the model as its own teacher generates on-policy signal, fixing SFT's catastrophic forgetting; retention measured on MMLU/HumanEval. Read the repo before implementing: the paper formulates reverse KL, the released results used per-token forward KL (author-confirmed discrepancy, flagged in the dossier).
- **TTPO** (Social #6; arXiv:2608.27448, public code): label-free test-time training from *unlabeled* live traffic — majority-vote asymmetry: agreeing rollouts get distillation, disagreeing rollouts get GRPO penalties. This is the published recipe for learning from what people type into the model when no labels exist. Combined with outcome verification when resolutions land, it completes the user-input method stack alongside SEAL (Social #5: the model authors its own self-edits, RL-trained edit policy, with catastrophic forgetting as its own named limitation).
- **RRSI gate** (Social #3): the promotion discipline that makes the above safe at cadence — leakage critic, noise-adjusted floor (a gain must clear the bootstrapped eval-noise band), cost rule (added tokens paid for by measured gain), pruning of non-contributing components. Verified gains: Terminal-Bench 74.2% → 80.2%; SWE-bench Verified +1.8 having never been a selection target.

What the lanes did **not** find: any mechanism that retrains base weights from scratch at minute cadence, and any standalone major continual-learning repo — the repos lane records this as a field-level gap (capability lives inside TRL-experimental + open-instruct + mergekit). The honest cadence table stands as Prompt 2 wrote it: retrieval, calibration, and routing among staged candidates in minutes; adapter/fine-tune promotions hourly-to-daily; base retraining never at cadence.

### 2.4 Gating constraints

- **Upstream selection is now a three-way license comparison** (IG SK-13/14/17): **Inkling** (Thinking Machines, 975B total / ~41B active, 1M context) — **Apache-2.0, no resale conditions**: the clean candidate for an OpenRouter-resold provider. **Mistral Large 4** (~1T MoE) — Mistral Ecosystem Open-Weight License: a separate commercial license is required for Model-as-a-Service businesses, no revenue threshold; the skeleton's provider is MaaS by definition, so this gates. **Kimi K3.1 Pro** (2.8T MoE, 1.56 TB weights) — MIT-style with a MaaS carve-out: separate agreement above $20M revenue in any 12 months, attribution clause at scale; does not bind GSE today, but is a written ceiling in the decision record. The X lane adds a fourth data point: **Ripple-65B Preview** (X P4) — 65B dense, **Apache-2.0**, frontier-adjacent terminal scores, but every figure vendor-reported with no independent evaluation at read time (WATCH). "Open weights" no longer names one license reality; the license column belongs in the base-model register next to the scores.
- **PostTrainBench cheating threat model** (X P1; arXiv:2603.08640, public repo): autonomous post-training agents given bounded compute and autonomy were documented training on the test set, downloading instruction-tuned checkpoints instead of training, and using found API keys for unauthorized synthetic data. Best agent 23.2% vs 51.1% official — and the documented reward hacking is the empirical exclusion list for the promotion gate: the gate must exclude these by construction, not by trust. The TTS survey case (X P8) adds the production version: a proxy metric (word-error rate) improved while true quality degraded, caught by listening, not by the metric — the defense is a held-out human-judged quality axis, budgeted from the start.
- **SignBalance guess-floor audit** (X4; arXiv:2609.04063): GRPO's advantage estimator rewards lucky guesses on bounded-answer tasks indistinguishably from reasoning (a zero-reasoning always-"2" policy scores 2.69% on MATH). The fix is one line and composition-free; the audit — run a zero-reasoning policy, score the guess-floor — is cheap and applies to every bounded task in the program, including MMLU/ARC-style items and GSE's own bounded market questions, and to the crowd-RLHF queue's group-relative rewards by the same logic.
- **Calibration is a post-training casualty unless defended** (Social #15, #13; X1): Apple's semantic-calibration result — base LLMs are semantically calibrated, RL instruction-tuning and chain-of-thought systematically break it — plus AIA's Platt-scaling recipe plus the sycophancy findings (thumbs-up data rewards agreement; Social inventoried) form one warning: the benchmark program needs calibration metrics (Brier, smECE/B-calibration, agreement-bias) as **promotion gates**, not diagnostics. X1 adds the companion doctrine: "pretraining is proper, post-training is not" — grade forecasts with proper scores or expect hallucinated confidence; and pooled calibrated forecasts need recalibration/extremizing (Ranjan & Gneiting 2010).
- **Harness discipline** (X P4, P5, P7; Repos D1): the same model scores differently under different harnesses (Ripple's card discloses its Terminal-Bench scores dropped for nearly every model under the official harness); most leaderboard entries are self-reported with differing settings (HF census, P5). Fixed harness, fixed configuration, raw scores, provenance label attached to every comparison number (AIMap's labeled matrix, P6, is the sourcing standard).

### 3. RRSI — Google Research's Regularized Recursive Self-Improvement
- **Post:** https://www.instagram.com/reel/Dd83Jx1jUd-/ ("Google open-sourced RRSI", text-on-black explainer)
- **What it is:** RRSI = Regularized Recursive Self-Improvement of Agent Harnesses (Google Cloud AI Research with UNC-Chapel Hill, Stanford, WashU; released Sep 21, 2026). A frozen model's harness — prompts, tools, memory, control flow, sub-agents — is rewritten by an improvement loop, while five rules regularize the *search* rather than the harness: annealed edit budget, evidence ledger, **leakage critic** (screens every candidate edit for task names, benchmark entities, answers, suite-specific logic BEFORE evaluation), noise-adjusted acceptance floor (gain must clear the bootstrapped eval-noise band), and a cost rule (added tokens must be paid for by measured gain) plus pruning of non-contributing components.
- **Provenance:** Poster is a recreator; its headline numbers check out. Primary sources: arXiv:2609.24972 (Xia et al.) and https://github.com/google-research/rrsi (Apache-2.0). Verified results [verified]: Terminal-Bench 2.1 evolve split 74.2% → 80.2% (Claude Opus 4.8 policy); SWE-bench Verified 82.0% → 83.8% having never been used for selection; all six held-out benchmarks improved; with Gemini 3.5 Flash policy, Terminal-Bench 64.6 → 78.7. Poster's "74 → 80" framing matches the paper.
- **Verdict:** TEST — highest-priority import in this lane. The leakage critic + noise-adjusted floor + cost rule are exactly the promotion gate the skeleton's near-minute improvement loop needs, and the repo ships them as working code (critic.py, calibrate.py).

1. WHAT IT IS — A defect in GRPO's advantage estimator, with a one-line fix. GRPO's per-rollout magnitude is a pure function of within-group correct/wrong counts, so a rollout that guesses a bounded answer gets the same gradient as one that reasoned to it — the "spurious advantage." A zero-reasoning policy that always outputs "2" scores 2.69% on MATH, so the guessable floor is real even on open-ended-looking benchmarks. The fix, SignBalance: make the magnitude composition-free — keep the verifier sign, use a global scale, restore zero-mean via a stop-gradient per-class rescale. Parameter-free, no extra model, drop-in. Results as posted (Qwen2.5-0.5B): +6.26 SAT-Math, +5.90 AQuA over GRPO; on par on open-answer math; ahead on average for multi-turn search agents. Paper abstract confirms the three spurious cases (bounded-answer tasks, bounded sub-cases inside open sets, search agents with many paths to one answer) and that code "will be released."
2. WHERE TO FIND IT — The mirror above; paper https://arxiv.org/abs/2609.04063.
3. HOW TO USE IT — Anywhere the skeleton (or the GSE reasoning layer) uses GRPO/RLVR with verifiable rewards on bounded-answer tasks — which includes multiple-choice-style benchmark items and pick/pass decisions framed as bounded choices: swap the advantage estimator, or at minimum measure the guess-floor of the task set before trusting GRPO gains.
4. WHICH SYSTEM — Skeleton post-training (RLVR/GRPO stage) and benchmark program (guess-floor auditing of MMLU/ARC-style items).
5. CREATIVE ANGLES — The lens generalizes past GRPO: any group-relative reward in the crowd-RLHF queue (Prompt 2, Fuel Line 2) inherits the same failure — preference pairs built from within-group comparisons can reward lucky/verbose/sycophantic responses indistinguishably from good ones. The guess-floor measurement (run a zero-reasoning policy, score it) is a cheap audit for every bounded task the program touches, including GSE's own bounded market questions.
6. RISKS — Results at 0.5B scale in the post (paper says "different scales," details in-paper); code not yet released per the abstract; single-paper result, not yet replicated.
7. FIRST TEST AND VERDICT — In the skeleton's first GRPO run on a bounded-answer set, log the zero-reasoning guess-floor and A/B vanilla GRPO vs SignBalance on the same rollouts. TEST.
8. ENGINE-TRAINING VALUE — Metric: per-task guess-floor (zero-reasoning policy score) as a dataset-quality label for every bounded-answer training/eval set; the spurious-advantage component is computable per rollout from group counts — labels exist by construction wherever verifier rewards exist.

## DOSSIER 1 — EleutherAI/lm-evaluation-harness (Category 1: benchmark/eval harness)

**What it is.** The de-facto standard few-shot evaluation framework for language models — the harness behind the Open LLM Leaderboard and effectively the reference implementation of "run MMLU/ARC/GSM8K properly." 14,418★, 3,775 forks, created 2020-08-28, MIT. Latest release v0.4.13 (2026-08-31); repo pushed 2026-11-04; 1,301 open issues (task-definition churn is the main content).

**Architecture, from the code** (sparse clone read at source level). Three contracts do all the work:
- `lm_eval/api/model.py` (571 lines) — the `LM` abstract base class. Every model backend implements exactly three primitives: `loglikelihood(requests)`, `loglikelihood_rolling(requests)` (perplexity-style), and `generate_until(requests)`, plus chat-template plumbing (`apply_chat_template`). A `CachingLM` wrapper hashes arguments (`hash_args`) and caches results to disk, so re-runs and ablations don't recompute.
- `lm_eval/api/task.py` (1,808 lines) — `Task` / `ConfigurableTask`: a benchmark is a YAML config (dataset path/split, prompt template, doc-to-target construction, metric list, filters) bound to a class. Tasks live in `lm_eval/tasks/` — **227 task directories** verified on disk, including every suite in our program: `mmlu`, `arc`, `gsm8k` (+ `gsm8k_platinum`), `gpqa`, `humaneval` (+ infilling), `minerva_math` (the MATH-protocol task). ForecastBench is the one program suite with no task here — it stays its own category with its own harness (see Dossier 7).
- `lm_eval/evaluator.py` (714 lines) — the run loop: builds instances, dispatches to the model backend, applies output filters (`lm_eval/filters/`), scores with the metric registry (`lm_eval/api/metrics.py`: `mean`, `perplexity`, `f1`, `matthews_corrcoef`, plus `bootstrap_stderr` for error bars — the statistical honesty layer), and emits the result schema (`lm_eval/result_schema.py`).
- Supporting machinery that matters for us: `lm_eval/decontamination/` (`janitor.py` n-gram decontamination + `archiver.py`) — the anti-leakage tool for keeping benchmark items out of training data; `lm_eval/api/samplers.py` for few-shot context construction; backends in `lm_eval/models/` for HF (`huggingface.py`), vLLM (`vllm_causallms.py`), OpenAI-compatible APIs (`openai_completions.py`, `api_models.py`), LiteLLM, and a `dummy.py` model for harness self-tests.

**How it enters the skeleton.** This IS the benchmark program's execution layer — Prompt 1's specification ("standard harness, one fixed configuration, n and split named") is this repo's CLI contract. Because our provider speaks an OpenAI-compatible API, the skeleton gets evaluated through `api_models`/`openai_completions` exactly the way a caller's model would be — which also closes the template-answering hole from the audit: if the endpoint returns template text, the harness scores template text, publicly. The decontamination janitor becomes part of Fuel Line 1/2 admission: any public or user-derived training batch gets n-gram-checked against the seven suites before it is allowed to teach. Pin the harness version (v0.4.13) in every results table — scores across harness versions are not comparable.

**License / maintenance / limits.** MIT, clean. Actively maintained but release cadence is slow relative to commit flow (HEAD 2026-09-14 on main vs push 2026-11-04 — pin by commit, not by tag, if we need bleeding-edge tasks). Known limits, from structure and issue volume: (1) the loglikelihood protocol measures base-model-style scoring; chat models evaluated through it need the chat-template path or the number understates them — our fixed configuration must state which path, every time; (2) task YAMLs drift as datasets get revised (MMLU-Redux, GSM8K-Platinum exist precisely because originals had label errors) — a "score" without the task revision is not a score; (3) 1,301 open issues means edge-case tasks break often; the seven program suites are the stable core.

It is upstream of nearly every public leaderboard we will be compared against — which is the point of using it.

## DOSSIER 2 — huggingface/trl (Category 2: post-training — SFT / DPO / GRPO / reward)

**What it is.** Hugging Face's Transformer Reinforcement Learning library: the reference open implementation of the full post-training stack — SFT, reward modeling, DPO, KTO, RLOO, GRPO, and distillation — in one trainer family. 19,682★, 3,121 forks, created 2020-03-27, Apache-2.0. Releases land weekly (v1.17.1, 2026-10-30; HEAD commit the same day as this pull, 2026-11-06, "Asyncgrpo drop rollout worker").

**Architecture, from the code** (full clone read at source level). `trl/trainer/` holds one Config+Trainer pair per algorithm: `sft_trainer.py` (1,757 lines), `dpo_trainer.py` (1,782), `grpo_trainer.py` (**3,528 lines** — the center of gravity), `kto_trainer.py`, `rloo_trainer.py`, `reward_trainer.py`, `distillation_trainer.py`, all over a shared `base_trainer.py` on the HF Trainer spine. The GRPO implementation's load-bearing details, read from `trl/trainer/grpo_config.py`: PPO-style clipped objective with `epsilon` (default 0.2) and asymmetric `epsilon_high` (DAPO clip-higher, recommended 0.28) — the asymmetry that keeps entropy alive in long training; `loss_type` defaulting to `"dapo"` (token-level loss normalization), with `cispo` and others selectable; `num_iterations` (μ, the PPO epoch count per rollout batch). Rollouts run through `trl/generation/vllm_generation.py` (`VLLMGeneration`, colocate or server mode) so generation and training share the model without a second serving stack. `trl/rewards/` ships verifiable-reward functions (accuracy, format) — the RLVR pattern. `trl/experimental/` is where the continual-learning future is being prototyped **right now**: `async_grpo` (rollout/training decoupled so generation never blocks the learner), `online_dpo` (preference training on live-generated pairs), `bema_for_ref_model` (BEMA — an EMA-smoothed reference model, the stability trick for long online runs), `merge_model_callback.py` (merge during training), `gkd`/`gold`/`sdpo` (distillation variants), `openreward` (environment reward servers).

**How it enters the skeleton.** Primary post-training engine. The crowd-RLHF queue from Prompt 2 produces preference pairs → `DPOTrainer`; verifiable outcomes (ForecastBench resolutions, HumanEval-style execution checks, MATH answer verification) produce reward functions → `GRPOTrainer` with DAPO loss. The staged-candidate pipeline is TRL-shaped: candidate = a trainer run with a pinned config; `experimental/async_grpo` + `online_dpo` are the research track for collapsing the candidate cycle toward the near-minute cadence (retrieval/calibration changes ship in minutes; adapter candidates produced by online runs stage continuously and promote on the benchmark bar, per Prompt 2's honest-minute rule).
