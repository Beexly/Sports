## DOSSIER 1 — EleutherAI/lm-evaluation-harness (Category 1: benchmark/eval harness)

**What it is.** The de-facto standard few-shot evaluation framework for language models — the harness behind the Open LLM Leaderboard and effectively the reference implementation of "run MMLU/ARC/GSM8K properly." 14,418★, 3,775 forks, created 2020-08-28, MIT. Latest release v0.4.13 (2026-08-31); repo pushed 2026-11-04; 1,301 open issues (task-definition churn is the main content).

**Architecture, from the code** (sparse clone read at source level). Three contracts do all the work:
- `lm_eval/api/model.py` (571 lines) — the `LM` abstract base class. Every model backend implements exactly three primitives: `loglikelihood(requests)`, `loglikelihood_rolling(requests)` (perplexity-style), and `generate_until(requests)`, plus chat-template plumbing (`apply_chat_template`). A `CachingLM` wrapper hashes arguments (`hash_args`) and caches results to disk, so re-runs and ablations don't recompute.
- `lm_eval/api/task.py` (1,808 lines) — `Task` / `ConfigurableTask`: a benchmark is a YAML config (dataset path/split, prompt template, doc-to-target construction, metric list, filters) bound to a class. Tasks live in `lm_eval/tasks/` — **227 task directories** verified on disk, including every suite in our program: `mmlu`, `arc`, `gsm8k` (+ `gsm8k_platinum`), `gpqa`, `humaneval` (+ infilling), `minerva_math` (the MATH-protocol task). ForecastBench is the one program suite with no task here — it stays its own category with its own harness (see Dossier 7).
- `lm_eval/evaluator.py` (714 lines) — the run loop: builds instances, dispatches to the model backend, applies output filters (`lm_eval/filters/`), scores with the metric registry (`lm_eval/api/metrics.py`: `mean`, `perplexity`, `f1`, `matthews_corrcoef`, plus `bootstrap_stderr` for error bars — the statistical honesty layer), and emits the result schema (`lm_eval/result_schema.py`).
- Supporting machinery that matters for us: `lm_eval/decontamination/` (`janitor.py` n-gram decontamination + `archiver.py`) — the anti-leakage tool for keeping benchmark items out of training data; `lm_eval/api/samplers.py` for few-shot context construction; backends in `lm_eval/models/` for HF (`huggingface.py`), vLLM (`vllm_causallms.py`), OpenAI-compatible APIs (`openai_completions.py`, `api_models.py`), LiteLLM, and a `dummy.py` model for harness self-tests.

**How it enters the skeleton.** This IS the benchmark program's execution layer — Prompt 1's specification ("standard harness, one fixed configuration, n and split named") is this repo's CLI contract. Because our provider speaks an OpenAI-compatible API, the skeleton gets evaluated through `api_models`/`openai_completions` exactly the way a caller's model would be — which also closes the template-answering hole from the audit: if the endpoint returns template text, the harness scores template text, publicly. The decontamination janitor becomes part of Fuel Line 1/2 admission: any public or user-derived training batch gets n-gram-checked against the seven suites before it is allowed to teach. Pin the harness version (v0.4.13) in every results table — scores across harness versions are not comparable.

**License / maintenance / limits.** MIT, clean. Actively maintained but release cadence is slow relative to commit flow (HEAD 2026-09-14 on main vs push 2026-11-04 — pin by commit, not by tag, if we need bleeding-edge tasks). Known limits, from structure and issue volume: (1) the loglikelihood protocol measures base-model-style scoring; chat models evaluated through it need the chat-template path or the number understates them — our fixed configuration must state which path, every time; (2) task YAMLs drift as datasets get revised (MMLU-Redux, GSM8K-Platinum exist precisely because originals had label errors) — a "score" without the task revision is not a score; (3) 1,301 open issues means edge-case tasks break often; the seven program suites are the stable core.

**Provenance.** Original project, EleutherAI, born from reproducing GPT-3's evaluation protocol openly in 2020. Builds on Hugging Face `datasets`/`transformers` and the `evaluate` metrics lineage. It is upstream of nearly every public leaderboard we will be compared against — which is the point of using it.

**GSE engine-training value.** None directly — it trains nothing. Its per-instance outputs (which items fail, loglikelihood margins per item) are the diagnostic feature set that tells the training lanes *what* to teach: item-level failure clusters become curriculum targets for Dossiers 2–4.

## DOSSIER 2 — huggingface/trl (Category 2: post-training — SFT / DPO / GRPO / reward)

**What it is.** Hugging Face's Transformer Reinforcement Learning library: the reference open implementation of the full post-training stack — SFT, reward modeling, DPO, KTO, RLOO, GRPO, and distillation — in one trainer family. 19,682★, 3,121 forks, created 2020-03-27, Apache-2.0. Releases land weekly (v1.17.1, 2026-10-30; HEAD commit the same day as this pull, 2026-11-06, "Asyncgrpo drop rollout worker").

**Architecture, from the code** (full clone read at source level). `trl/trainer/` holds one Config+Trainer pair per algorithm: `sft_trainer.py` (1,757 lines), `dpo_trainer.py` (1,782), `grpo_trainer.py` (**3,528 lines** — the center of gravity), `kto_trainer.py`, `rloo_trainer.py`, `reward_trainer.py`, `distillation_trainer.py`, all over a shared `base_trainer.py` on the HF Trainer spine. The GRPO implementation's load-bearing details, read from `trl/trainer/grpo_config.py`: PPO-style clipped objective with `epsilon` (default 0.2) and asymmetric `epsilon_high` (DAPO clip-higher, recommended 0.28) — the asymmetry that keeps entropy alive in long training; `loss_type` defaulting to `"dapo"` (token-level loss normalization), with `cispo` and others selectable; `num_iterations` (μ, the PPO epoch count per rollout batch). Rollouts run through `trl/generation/vllm_generation.py` (`VLLMGeneration`, colocate or server mode) so generation and training share the model without a second serving stack. `trl/rewards/` ships verifiable-reward functions (accuracy, format) — the RLVR pattern. `trl/experimental/` is where the continual-learning future is being prototyped **right now**: `async_grpo` (rollout/training decoupled so generation never blocks the learner), `online_dpo` (preference training on live-generated pairs), `bema_for_ref_model` (BEMA — an EMA-smoothed reference model, the stability trick for long online runs), `merge_model_callback.py` (merge during training), `gkd`/`gold`/`sdpo` (distillation variants), `openreward` (environment reward servers).

**How it enters the skeleton.** Primary post-training engine. The crowd-RLHF queue from Prompt 2 produces preference pairs → `DPOTrainer`; verifiable outcomes (ForecastBench resolutions, HumanEval-style execution checks, MATH answer verification) produce reward functions → `GRPOTrainer` with DAPO loss. The staged-candidate pipeline is TRL-shaped: candidate = a trainer run with a pinned config; `experimental/async_grpo` + `online_dpo` are the research track for collapsing the candidate cycle toward the near-minute cadence (retrieval/calibration changes ship in minutes; adapter candidates produced by online runs stage continuously and promote on the benchmark bar, per Prompt 2's honest-minute rule). BEMA is the specific mechanism to test for reference-model drift in long online runs.

**License / maintenance / limits.** Apache-2.0. Maintenance is the best in this lane (HF core team, weekly releases). Limits: (1) the API moves fast — v1.x has already reshaped config surfaces; pin versions per candidate and treat upgrades as their own evaluated change; (2) GRPO at scale is memory-hungry (policy + reference + rollout engine); colocate mode trades memory for simplicity, server mode is the production shape; (3) distributed GRPO (multi-node) remains the sharp edge — most public success reports are single-node or modest clusters, which matches our realistic compute for the first candidates.

**Provenance.** Original HF project (2020, PPO-for-LM era), rebuilt repeatedly as the field moved PPO → DPO → GRPO. Builds on `transformers`, `accelerate`, `peft`, and vLLM for rollouts. It is the upstream that Axolotl (Dossier 5) delegates its RL algorithms to.

**GSE engine-training value.** Direct: preference pairs built from resolved GSE forecasts (published pick vs passed pick, with outcome labels) are DPO data whose reward is reality, not opinion; GRPO reward functions over nflverse-labeled states (EPA/WP outcomes) train the forecasting head on verifiable signal. The queue→pair→DPO path is the exact mechanism the skeleton's user-data fuel line needs, with consent gating in front of it (Prompt 2, Fuel Line 2).

## DOSSIER 3 — allenai/open-instruct (Category 2/3: post-training recipes + the continual candidate factory)

**What it is.** The Allen Institute for AI's post-training codebase — the code lineage behind the Tulu family of open instruction models: SFT data mixing, DPO, rejection sampling, and GRPO, run as production recipes rather than library abstractions. 3,924★, 175 open issues, created 2023-06-09, Apache-2.0. Release v0.3.0 (2026-06-11); pushed the day of this pull.

**Architecture, from the code** (1,147 files enumerated via recursive tree; core RL files read). Flat, script-first layout in `open_instruct/`: `finetune.py` (SFT), `dpo.py` (a compact 358-line entry — the algorithm lives in shared utils), `grpo_fast.py` (**2,409 lines**, the flagship async GRPO implementation), `grpo.py`, `actor_manager.py`. The RL numerics live in `open_instruct/rl_utils.py` (465 lines, read in full): `calculate_advantages` (GAE with γ/λ), `calculate_advantages_packed`, `pack_sequences`/`reset_position_ids` (sequence packing with position-id resets so packed samples don't attend across boundaries), `masked_mean`. Inference/training coupling lives in `open_instruct/vllm_utils.py` (1,480 lines, read): `LLMRayActor` (Ray actors wrapping vLLM engines), `create_vllm_engines`, and — the load-bearing mechanism — `broadcast_weights_to_vllm` with `_prepare_params_for_sync` / `_collect_weight_metadata` / `_broadcast_weights_ipc`: after each training step, updated weights (FSDP2 submodules) are broadcast over IPC into the live vLLM rollout engines **without restarting them**. Around the trainers: `rejection_sampling/` (`generation.py`, `rejection_sampling.py`, `synthetic_preference_dataset.py` — sample k completions, verify/score them, build preference data from the model's own outputs), `decontamination/` (same duty as Dossier 1's janitor), `human_eval/` and `IFEvalG/` (in-repo eval utilities), `environments/` (sandboxed execution backends), `merge_models.py` / `merge_lora.py`, and `mason.py` (Ai2's Beaker cluster launcher — the infra assumption showing through).

**How it enters the skeleton.** This is the closest existing blueprint for Prompt 2's Fuel Line 3 machinery: (1) **rejection sampling is the candidate factory** — the live model samples, execution/outcome verification filters, surviving pairs become DPO/GRPO data; self-generated, self-verified, no self-asserted verification (the verifier is code or a resolved outcome, per the prompt's absolute bar); (2) **IPC weight broadcast is the honest version of "improvement by the minute"** — a promoted candidate reaches the serving engines without downtime, so promotion is a weight-sync event, not a redeploy; (3) `grpo_fast` + Ray actor pools are the scale-out shape when candidate generation outgrows one node. We adopt the *patterns* (and can lift `rl_utils` numerics under Apache-2.0) rather than the repo wholesale — see limits.

**License / maintenance / limits.** Apache-2.0. Ai2-maintained, active, but opinionated toward Ai2's own infrastructure: `mason.py` assumes Beaker; many recipes assume a Ray cluster and OLMo-family checkpoints (`olmo_core_*` modules). Single-GPU adaptation is real work. Release cadence is sparse (two tags in 2026) relative to commit flow — pin commits. GRPO here is a recipe, not a product: expect to own the glue.

**Provenance.** Original Ai2 project; the Tulu 2/3 post-training recipes (SFT mix → DPO → RLVR/GRPO) are its public track record, and `ground_truth_utils.py`/`math_utils.py` carry the verifiable-reward approach those recipes published. Builds on PyTorch FSDP2, Ray, vLLM, and OLMo-core.

**GSE engine-training value.** The rejection-sampling loop is directly portable to the reasoning engine: sample multiple reasoning traces per matchup state, keep the ones whose intermediate claims verify against labeled data (nflverse EPA/WP joins, resolved lines), and train on the survivors — execution-verified reasoning data with GSE's own labels as the verifier.

## DOSSIER 4 — modelscope/ms-swift (Category 2: training + post-training at frontier-model scale)

**What it is.** Alibaba ModelScope's SWIFT: a unified CPT/SFT/RLHF framework covering 600+ LLMs and 300+ multimodal models, with a Megatron bridge for full-parameter training of frontier-class models (its own example scripts run DeepSeek-V4.1, Qwen3-235B MoE, GLM-5.x). The AAAI 2025 paper's codebase. 16,056★, 594 open issues, created 2023-08-01, Apache-2.0 (LICENSE file body verified). Release v4.6.0 (2026-10-13); pushed the day before this pull.

**Architecture, from the code** (1,604 files, 29 top-level modules under `swift/` enumerated; RL core read). The spine: `swift/pipelines` + `swift/trainers` (HF-Trainer-based PT/SFT), `swift/tuners` (PEFT family), `swift/megatron/` (conversion + training bridge to Megatron-LM for tensor/pipeline-parallel full training), `swift/sequence_parallel`, `swift/ray` (distributed rollout placement). The post-training core, read at source level:
- `swift/rlhf_trainers/` — `grpo_trainer.py`, `ppo_trainer.py`, `dpo_trainer.py`, `cpo_trainer.py`, `orpo_trainer.py`, `kto_trainer.py`, `gkd_trainer.py` (generalized knowledge distillation), `reward_trainer.py`, with `rollout_mixin.py`/`vllm_client.py` coupling generation.
- `swift/rl_core/` — the algorithm heart, deliberately framework-free: `grpo_algorithm.py` (144 lines: `compute_rewards_per_func`, `score_completions` — completions scored by a *set of independent reward functions*, combined downstream) and `advantage.py` (483 lines, read: `compute_advantages(rewards_per_func, reward_weights, num_generations, advantage_estimator ∈ {grpo, rloo, reinforce++}, scale_rewards, kl_in_reward, beta)` returns **per-sequence** advantages as a pure tensor function "suitable for all backends (HF, Megatron, Ray)" — with the reference-model KL subtracted from rewards *before* group normalization, dynamic-sampling std computation, and per-token teacher-KL/log-ratio hooks (`compute_teacher_kl_per_token`, `compute_teacher_logratio`) for on-policy distillation signals applied after the base advantage is broadcast).
- `swift/rollout/` — `agent_loop.py`, `multi_turn.py`, `gym_env.py`, `openenv_wrapper.py`: multi-turn agent RL environments, not just single-turn completion RL.
- `swift/infer_engine/` — one protocol over `vllm_engine.py`, `sglang_engine.py`, `lmdeploy_engine.py`, `transformers_engine.py`, plus `grpo_vllm_engine.py`: the same serving-abstraction trick Dossier 1 uses for eval, applied to training rollouts.
- `swift/loss/` and `swift/metrics/` — pluggable loss registry (`causal_lm`, `decision`, `embedding`, `reranker`) and eval metrics (`acc.py`, `nlg.py` with ROUGE/BLEU, embedding/reranker metrics).
- Its `docs/source_en/Instruction/GRPO/AdvancedResearch/` tree is a research program in itself: per-algorithm documents for DAPO, CISPO, GSPO, SAPO, CHORD, FIPO, REAL, REINFORCE++, RLOO, TreePO — and a `training_inference_mismatch.md` that derives, in the open, the core honesty problem of this whole lane: GRPO assumes samples come from π_θ, but vLLM rollouts come from π_vLLM ≠ π_θ even with synchronized weights (different operator implementations), silently breaking the on-policy assumption; SWIFT documents its importance-sampling correction. Any lab that publishes its own mismatch math is a lab whose numbers deserve more trust.

**How it enters the skeleton.** Three seats: (1) **The scale path** — when a candidate outgrows single-node TRL, SWIFT's Megatron bridge is how the same GRPO recipe runs full-parameter on MoE-class bases; TRL for iteration speed, SWIFT for scale, same advantage math lineage. (2) **The research watch** — its AdvancedResearch docs are the fastest reliable survey of post-GRPO algorithm variants; each variant enters our register through the loop before any adoption. (3) **The multi-turn seat** — `rollout/`'s agent-loop environments are how the *reasoning engine's* multi-step work (usage → health → matchup → situation chains) becomes trainable trajectories rather than single completions.

**License / maintenance / limits.** Apache-2.0, verified from the LICENSE file itself. Limits: (1) documentation is Chinese-first — a complete English mirror exists under `docs/source_en/` (verified), but newest material lands in Chinese first; (2) ecosystem gravity toward ModelScope Hub (its dataset registry resolves ModelScope IDs first, HF second) — a mirror/egress consideration for us; (3) the surface is enormous (600+ model templates) and moves fast — pin versions; the Megatron path assumes serious GPU clusters, which is a frontier-tier cost reality, not a defect.

**Provenance.** Original ModelScope (Alibaba) project, AAAI 2025. Builds on HF transformers/peft, Megatron-LM, vLLM/SGLang/LMDeploy, Ray. Its GRPO core descends from the DeepSeekMath GRPO formulation, extended with the DAPO/GSPO/CISPO research line it documents.

**GSE engine-training value.** Its dataset registry (`swift/dataset/data/dataset_info.json`, read: **111 registered datasets** with pretrain/SFT/preference tags and dual ModelScope/HF IDs) is a ready-made Fuel Line 1 index — and its reasoning shelf is specific: `AI-MO/NuminaMath-CoT`, `NuminaMath-TIR`, `NuminaMath-1.5`, `TIGER-Lab/MATH-plus`, `AI-ModelScope/MathInstruct`, `school_math_0.25M` (MATH-suite fuel), `AI-ModelScope/starcoderdata`, `swift/github-code`, `codefuse-ai/Evol-instruction-66k` (HumanEval-direction fuel), `allenai/c4`/`swift/dolma` (pretrain), `swift/WebInstructSub` (instruction synthesis), `FreedomIntelligence/medical-o1-reasoning-SFT` (GSI-side reasoning). For GSE proper: the multi-function reward composition (`compute_rewards_per_func` + weights) is the cleanest pattern for blending our reward components — market-free reasoning quality, calibration error, outcome accuracy — into one advantage signal without collapsing them into a single scalar too early.

## DOSSIER 5 — axolotl-ai-cloud/axolotl (Category 2: fine-tuning orchestration / adapter factory)

**What it is.** The config-driven fine-tuning orchestrator: one YAML file describes base model, data, adapters, optimization, and evaluation; Axolotl compiles it into a correct HF Trainer run. 12,668★, 1,471 forks, created 2023-04-14, Apache-2.0. Release v0.21.1 (2026-10-27); pushed the day of this pull; 250 open issues.

**Architecture, from the code** (sparse clone read). The contract is a giant Pydantic schema (`src/axolotl/utils/schemas/config.py` — one validated field per knob: `sample_packing` with group/bin sizing and a separate `eval_sample_packing`, FSDP config imported from `schemas/fsdp.py`, fp8 toggles, cloud/checkpoint schemas beside it). Execution: `src/axolotl/core/` — `trainers/`, `datasets/`, `builders/`, `attention/`, plus production-hardening pieces most trainers lack: `checkpoint_mirror.py` (a `CheckpointMirrorCallback`), `checkpoint_publisher.py`, `checkpoint_retry.py` — checkpoints mirrored/publisher-retried to object storage as a first-class behavior. `src/axolotl/kernels/` holds fused Triton/CUDA kernels (`lora.py`, `dora.py`, `geglu.py`, `swiglu.py`, `rms_norm_gated.py`, `gemma4_fused_rope.py`) — LoRA math fused rather than composed from primitives. `src/axolotl/monkeypatch/` is the honest price of the ecosystem: patch layers for transformers, peft, xformers, ring attention, tiled MLP, per-model quirks (`monkeypatch/models/`). Data: `datasets.py` + `prompt_strategies/` per training type (`dpo/`, `kto/`, `orpo/`, `ebft/`, `bradley_terry/`, `messages/` — chat-format strategies), `prompt_tokenizers.py`, samplers in `utils/samplers/`, and `evaluate.py` for in-run evals. Preference algorithms are prompt-strategy + TRL-backed; Axolotl's own depth is SFT/adapter/data, not RL numerics.

**How it enters the skeleton.** The **adapter factory for staged candidates**. Prompt 2's promotion system requires every candidate to be explainable — what data, what config, what scores produced it. Axolotl's config-as-code is exactly that audit trail: a candidate IS a YAML file plus a checkpoint; two candidates differ by a diffable config. The near-minute cadence layers use it like this: data refresh (Fuel Line 1/2) → new config revision → short LoRA/DoRA run with sample packing → checkpoint mirrored out → Dossier 1 evaluates → promote or discard. Checkpoint mirroring is the piece that makes candidate generation survivable on preemptible GPU rentals — a killed run resumes from the mirror instead of from zero.

**License / maintenance / limits.** Apache-2.0. Very actively maintained. Limits: (1) the monkeypatch architecture means Axolotl breaks when transformers/peft jump versions — pin the whole stack per candidate generation; (2) config surface is enormous, so config review is a real step in the loop (a wrong field silently changes the run's meaning); (3) RLHF depth is delegated to TRL — Axolotl is not where GRPO behavior gets customized.

**Provenance.** Community-original project (Axolotl AI), the most-used open fine-tuning front-end of the 2023–2026 open-model era. Builds on transformers, peft, TRL, DeepSpeed/FSDP, FlashAttention. Its example-config corpus doubles as the community's recipe book.

**GSE engine-training value.** Indirect but real: GSE-specific adapters (forecasting voice, injury-report reading, matchup-reasoning format) are Axolotl-shaped jobs — small data, pinned config, fast turnaround — and the config history becomes the engine's own training provenance record.

## DOSSIER 6 — arcee-ai/mergekit (Category 3: model merging / zero-training candidate generation)

**What it is.** The standard toolkit for merging pretrained LLMs in weight space: task arithmetic, TIES, DARE, SLERP, model stock, and evolutionary merge search, configured by YAML. 7,436★, 277 open issues, created 2023-08-21, **LGPL-3.0**. Release v0.1.5 (2026-10-20); pushed 2026-10-31.

**Architecture, from the code** (201 files enumerated; core method source read). `mergekit/merge_methods/` is a registry of merge policies over a shared contract (`base.py`: `GroupMergeMethod`, `ParameterSpec`/`ParameterScope`, `TensorGroup`, `InputContract`). The flagship, read at source level: `generalized_task_arithmetic.py` — a frozen dataclass policy composing the whole modern merge family in one method: task vectors (fine-tune minus base) are **sparsified** via `mergekit/sparsify.py` (`SparsificationMethod`, `RescaleNorm` — DARE-style random dropping with norm rescaling, or TIES-style magnitude trimming), combined under a **consensus rule** (`ConsensusMethod`: `count` vs `sum` — sign-consensus is the TIES interference fix), then normalized/rescaled and scaled by `lambda` before being added back to the base. Siblings: `linear.py` (weighted average), `slerp.py`/`multislerp.py`/`nuslerp.py` (spherical interpolation), `model_stock.py` (geometric layer-wise stock), `karcher.py` (Karcher-mean on the manifold), `nearswap.py`, `sce.py`, `arcee_fusion.py`, `task_adapter.py`, `passthrough.py` (layer grafting — Frankenmerge). `mergekit/scripts/` includes `evolve.py` (mergekit-yaml-evolve: evolutionary search over merge hyperparameters, scored by lm-eval — Dossier 1 as the fitness function), `extract_lora.py`, `layershuffle.py`.

**How it enters the skeleton.** The **cheapest candidate generator in the promotion pipeline**. When two staged adapters each win on different suites (one on GSM8K-style reasoning, one on forecasting calibration), a TIES/DARE merge is a new candidate that costs RAM-minutes, not GPU-hours — it enters shadow eval like any other candidate and lives or dies by the same promotion bar. `evolve.py` closes the loop automatically: merge-config search with harness scores as fitness, bounded by the regression budget. This is also the cold-start compensation from Prompt 2: at zero user traffic, merges of public-data adapters still generate improving candidates.

**License / maintenance / limits.** LGPL-3.0 — fine as a build-time tool; get a license review before embedding mergekit code inside any shipped product (tool use vs library linking is the distinction that matters). Maintenance is steady but not fast (two releases in a year). Hard limits: (1) merges require the same base model and tokenizer family — merging across bases is undefined behavior, not a technique; (2) merged models can silently lose calibration while gaining benchmark points — for a forecasting system, every merge candidate must pass the calibration gate, not just the accuracy suites; (3) evolutionary search will happily overfit the eval it scores on — hold out a confirmation split.

**Provenance.** Arcee AI's open implementation of the 2022–2024 merge literature (Task Arithmetic, TIES-Merging, DARE, Model Stock, SLERP), generalized into one policy class — the `generalized_task_arithmetic.py` design is itself the provenance map: each paper is a parameter setting.

**GSE engine-training value.** None as training; high as composition. Merging a forecasting adapter with a general-reasoning adapter is how the skeleton avoids choosing between its two jobs — with Dossier 1 and the calibration gate deciding whether the composition actually worked.

## DOSSIER 7 — Metaculus/metac-bot-template + Metaculus/forecasting-tools (Category 6: forecasting arena client)

**What it is.** Metaculus's official bot template for the **Fall 2026 FutureEval** tournament — the current season of the arena behind the ForecastBench line of work — plus the `forecasting-tools` Python framework it is built on. Template: MIT, 21 files, pushed 2026-11-04. Framework: MIT, 89★, pushed 2026-11-06.

**Architecture, from the code** (full tree + main sources read). `main.py` (783 lines) defines `FallTemplateBot2026(ForecastBot)`: the parent class's `forecast_on_tournament(tournament_id)` drives the loop — load open questions → per question, run research `research_reports_per_question` times (`run_research`, with `AskNewsSearcher`/`SmartSearcher` retrieval) → run the type-specific forecast function `predictions_per_research_report × research_reports` times → aggregate → submit. Every question type has a dedicated path (methods enumerated from source): binary (`_run_forecast_on_binary`/`_binary_prompt_to_forecast`), multiple choice, numeric (`_run_forecast_on_numeric`, distribution construction via `_create_single_distribution_parsing_message` and explicit upper/lower-bound messages), date, and **conditional** questions (`_run_forecast_on_conditional`, with a conditional-disclaimer injection). ## DOSSIER 8 — BerriAI/litellm (Category 5: LLM gateway — routing, budgets, interaction capture)

**What it is.** The largest open LLM gateway: one OpenAI-shaped API in front of 100+ providers, with routing, fallbacks, load balancing, virtual keys, budgets, spend tracking, and logging callbacks — now with a Rust core. 62,846★, 5,692 open issues, created 2023-07-27. Releases are near-daily (v1.108.2 the day of this pull). License is split (verified from the LICENSE file itself): MIT outside `enterprise/`, proprietary inside it — which is why the API reports NOASSERTION.

**Architecture, from the code** (18,712 tree entries enumerated; router/proxy layout read — the repo is 2.87 GB, so dissection was structural for the proxy core, not line-level throughout). `litellm/router.py` + `router_core.py` + `router_attempt.py` implement the Router: deployment pools per model name, strategy-based selection, cooldowns on failure, ordered fallbacks across providers. `litellm/proxy/proxy_server.py` is the hosted face: virtual-key issuance, per-key/per-team budgets, spend accounting, rate limits — the multi-tenant machinery a public provider needs. `litellm/litellm-rust/` + `litellm/router_rust/` (an `invoke/` pipeline: `endpoints.py`, `shaping.py`, `slots.py`, `streaming.py`, `callbacks.py`) show the current migration of the hot path to Rust. The callbacks/logging layer is architecturally central: every call can emit a structured record (request, response, latency, cost, key) to sinks — this is the interaction-capture hook point for a preference-data pipeline.

**How it enters the skeleton.** Two distinct seats, and naming them apart matters: (1) **NOT the public face.** Our OpenRouter listing needs a provider endpoint implementing OpenRouter's provider spec; LiteLLM is a consumer-side aggregator — it faces the other direction. The existing stealth-skeleton provider code (audited earlier today: gateway plumbing, template brain, hardcoded queue) keeps that seat. (2) **The internal gateway and the capture pattern.** Fleet-side, LiteLLM is the proven way to route our own model calls with budgets and fallbacks; and its callback-record design is the template for Prompt 2's Fuel Line 2 capture schema — what an interaction record must contain (prompt, response, model version, cost, key identity, timestamps) before consent filtering decides what may enter the training pool. Its router's fallback/cooldown semantics are also the reference for the provider gateway's upstream-failure behavior when the skeleton routes staged candidates.

**License / maintenance / limits.** MIT core + proprietary `enterprise/` — adopt the core only, and treat the split as a standing caution (features migrate across that line). Maintenance velocity is extreme (daily releases, 5,692 open issues): pin hard, upgrade deliberately. The repo's sheer size (GBs) makes full vendoring impractical; consume as a package or a deployed proxy, not as source. Provider-coverage breadth means per-provider quirks accumulate in its translation layer — the cost of the one-API promise.

**Provenance.** BerriAI's original project (2023), grown from a translation library into a gateway platform; the Rust rewrite is its current chapter. It is the upstream the metac-bot framework (Dossier 7) uses for model access, and Dossier 1 has a LiteLLM backend — the ecosystem's connective tissue.

**GSE engine-training value.** Its spend/usage records are the operational dataset for routing economics (which model earns its cost per task class) — features for the router policy, not for the model. The training value flows through the capture-schema pattern above, not through LiteLLM itself.

## DOSSIER 9 — unclecode/crawl4ai (Fuel Line 1: public-data ingestion — the "train on public data" intake arm)

**What it is.** Crawl4AI: an open-source, LLM-oriented web crawler that turns the live web into clean markdown and structured extraction at scale — the collection arm for Prompt 2's first fuel line. 87,015★, 311 open issues, created 2024-05-09, **Apache-2.0** (LICENSE file body verified). Release v0.9.5 (2026-10-14); pushed 2026-11-04. (Repo description also advertises a hosted cloud API; the repo itself is the self-hostable Apache-2.0 crawler — we use the repo.)

**Architecture, from the code** (969 files enumerated; core modules read).
- **Execution core:** `crawl4ai/async_webcrawler.py` (Playwright-driven async crawling) behind `crawl4ai/async_dispatcher.py` (788 lines, read): a `RateLimiter` (honors 429/503 with backoff — the politeness/robustness layer for scheduled source sweeps) and a `MemoryAdaptiveDispatcher` that throttles concurrency against live RAM pressure, so a crawl fleet degrades gracefully instead of OOM-dying mid-harvest.
- **Storage & provenance:** `crawl4ai/async_database.py` (678 lines, read): an `aiosqlite` store (`crawled_data` table) with content-addressed payload storage — `generate_content_hash` keys each artifact (raw HTML, cleaned HTML, markdown, extracted content, screenshot), which gives dedupe, change detection, and a provenance hash per document for free.
- **Extraction:** `extraction_strategy.py` (LLM-extraction, CSS/XPath schema extraction, regex), `markdown_generation_strategy.py` (fit-markdown pruning), `chunking_strategy.py`, `table_extraction.py`.
- **Deep crawling:** `crawl4ai/deep_crawling/` — `bfs_strategy.py`, `dfs_strategy.py`, and `BestFirstCrawlingStrategy` (437 lines, read: priority-queue frontier expansion with a `score_threshold` cutoff) driven by `scorers.py` (519 lines, read): a `CompositeScorer` over `KeywordRelevanceScorer`, `PathDepthScorer`, `ContentTypeScorer`, **`FreshnessScorer`**, and **`DomainAuthorityScorer`** — a ready-made source-vetting feature set.
- **The standout:** `crawl4ai/adaptive_crawler.py` (**1,923 lines**, read) — "adaptive information foraging." Its `CrawlState` tracks term/document frequencies, saturation history (new-terms-per-crawl curve), and, in embedding mode, a coverage model: KB and query embeddings, an alpha-shape coverage hull, and explicit `semantic_gaps`. The crawler stops when the query's information space is *covered* — a measured sufficiency criterion, not a page budget.

**How it enters the skeleton.** Fuel Line 1's machinery, concretely: scheduled deep crawls of the public source universe (arXiv listings, HF/Kaggle dataset pages and files, OpenAlex, benchmark repos, documentation, the book repositories from Prompt 3's register) with (1) best-first frontier scoring deciding what's worth fetching, (2) freshness/authority scores feeding the dataset-admission record, (3) content-hash storage making every ingested document provenance-addressable — when a training example is challenged, its source document is one hash lookup away — and (4) adaptive saturation as the stopping rule for open-ended harvests ("collect everything on X" becomes "collect until coverage," with the gap list as a by-product: the semantic gaps ARE the gap audit for a crawl). Extraction strategies produce the markdown corpus the training lanes consume, in the same operation.

**License / maintenance / limits.** Apache-2.0, verified. Actively maintained, healthy issue count for its size. Limits: (1) JS-heavy targets need the browser pool — memory is the scaling constraint, hence the adaptive dispatcher; budget RAM per crawl node; (2) extraction quality is strategy-bound — LLM extraction costs tokens per page and schema extraction needs per-source config, so the admission pipeline still needs a quality gate downstream; (3) robots/ToS compliance is the operator's duty — the RateLimiter helps, it does not decide; the source universe stays public-and-permitted per Prompt 2's licensing enforcement; (4) the hosted-cloud upsell in the description is not the repo's license reality — self-host, per the fleet's posture.

**Provenance.** Original project by "unclecode" (2024), grown from an LLM-markdown crawler into the deep/adaptive system above; the adaptive module's design descends from information-foraging theory (saturation/coverage) rather than from other crawler code.

**GSE engine-training value.** Produces the corpus itself: timestamped, hash-addressed public documents with freshness and authority features per source — the raw material for public-data SFT/retrieval refresh, and the per-source quality features (freshness, authority, saturation-at-capture) become admission-scoring features for every future dataset decision, GSE and GSI alike.
