# [0120] ReliabilityBench: Evaluating LLM Agent Reliability Under Production-Like Stress Conditions (arXiv:2601.06112v1)

**Citation:** Aayush Gupta (aayush.gupta@gohighlevel.com). *ReliabilityBench: Evaluating LLM Agent Reliability Under Production-Like Stress Conditions*. arXiv:2601.06112v1, 2 January 2025. URL: https://arxiv.org/abs/2601.06112v1
**Ledger completed:** 2026-09-21. **Read:** full text (PDF via arxiv.org, 1402 lines; all sections, equations, tables, appendices read).
**Verdict:** ADAPT — the reliability-surface methodology (R(k, ε, λ)), deterministic state-based oracles, and chaos fault injection give GSE a rigorous pre-deployment protocol for its agents. Deploy ReliabilityBench's grid (consistency × perturbation × fault injection) against GSE's research/content agents; the "simpler beats complex under stress" and "rate limits hurt most" findings directly inform GSE architecture choices.

## 1. Research question
Production agents are evaluated by single-run pass@1 on clean data, which overestimates real reliability. Building on τ-bench's pass^k insight and chaos engineering (Netflix Simian Army, SRE practices), the paper proposes a 3D "reliability surface" framework — consistency under repetition (k), robustness to paraphrased/perturbed tasks (ε), fault tolerance under infrastructure failure (λ) — plus Action Metamorphic Relations (perturbations judged by end-state equivalence, not text similarity) and a chaos-style fault-injection system. Evaluated on ReAct vs. Reflexion agents with Gemini 2.0 Flash and GPT-4o across four tool-using domains.

## 2. Dataset / schema
Synthetic task suite: 20 tasks across four domains (Scheduling: book/reschedule/cancel meetings; Travel: search/hold/confirm flights; Support: tickets, KB search, escalation; Ecommerce: search/order/coupon/returns), each with state-dict initial state, 25+ domain-specific tools, and deterministic state-based verifier predicates (Appendix A lists all tool signatures; Appendix C gives sample tasks). Complexity levels per domain (Table 4): L1 simple (direct booking), L2 harder (cheapest + coupon, conflict handling). Episodes: main 960 (20 tasks × 3 ε levels × 2 λ levels × 2 agents × 2 runs, per model aggregated to 480/model) + ablation 320 (20 tasks × 4 fault types × 2 agents × 2 runs); grand total 1,280 episodes. Models: Gemini 2.0 Flash (primary), GPT-4o (comparison). Architectures: ReAct, Reflexion.

## 3. Method / model
(1) **Reliability surface:** R(k,ε,λ) = E_τ∼D[pass^k(perturb_ε(τ), A) | fault profile λ]; derived metrics: Surface Volume V = ∫∫∫R dk dε dλ, Degradation Gradient ∇R = (∂R/∂k, ∂R/∂ε, ∂R/∂λ), Critical Threshold (k*,ε*,λ*) where R drops below θ. (2) **Action Metamorphic Relations:** taxonomy (Table 2) — linguistic (synonym, paraphrase, voice), structural (reordering, split/merge), contextual (distractor, mid-task correction), temporal (date format, relative time); correctness = end-state equivalence v(Sf,S0) = v(S′f,S0), not trajectory similarity. (3) **Chaos fault injection:** taxonomy (Table 3) — network (TransientTimeout, ConnectionReset), rate limit (SoftRateLimit 429-retryable, HardRateLimit non-recoverable), data (PartialResponse, SchemaDrift, StaleData, EmptyResponse); profiles λ=0.0/0.1/0.2/0.3 with failure_rate 0.0/0.075/0.175/0.275 and fault_weights per level (Appendix B); injector wraps tool execution: draw u∼Uniform(0,1), select fault, return error message (recoverable) or modified response (non-recoverable). (4) **State-based oracles:** deterministic verifier v(S0,Sf) per task (e.g., reservations[flight_id].status=="confirmed"), no LLM judges. (5) Empirical comparison across the 2×2 model×architecture grid, per-domain breakdown, fault-type ablation at λ=0.2.

## 5. Features / target
No ML features. Independent variables: model (2), architecture (2), ε ∈ {0.0,0.1,0.2}, λ ∈ {0.0,0.2}, domain (4), fault type (ablation). Target: pass^k (k=2) per cell; derived: surface volume, degradation gradient, recovery statistics (faults encountered, successful recoveries, extra tool calls), cost per 100 episodes.

## 6. Validation design
Full factorial grid: 20 tasks × 3 ε levels × 2 λ levels × 2 architectures × 2 runs per model = 480 episodes/model main + 320 ablation episodes; grand total 1,280. State-based deterministic oracles eliminate judge noise. Baselines: ReAct vs. Reflexion, Gemini 2.0 Flash vs. GPT-4o, timeout-only/ratelimit-only/partialresponse-only vs. mixed faults. Strengths: multidimensional grid, deterministic verification, real fault taxonomy from production experience, full cost accounting. Weaknesses: k=2 only; n=20 tasks/domain-subset small; no ε=0.3; models from December 2024 (dated — costs at $0.075/1M in, $0.30/1M out for Gemini; GPT-4o $2.50/$10.00); synthetic tools; no human-user phrasing corpus.

## 7. Numerical results / baselines
- **Perturbation degradation (Table 5, Gemini, k=2):** ε=0.0: 96.88% → ε=0.1: 88.12% → ε=0.2: 88.12%. **8.8% drop** from baseline to medium perturbation. GPT-4o: 95.00% → 87.50% → 88.75%.
- **Model comparison:** Gemini pass2 91.04% overall vs. GPT-4o 90.42% (−0.62% gap) at **82× lower cost** ($0.12 vs. $9.77 per 480 episodes; $0.025 vs. $2.04 per 100 episodes). Total 1,280-episode experiment cost under $10.
- **Architecture (Table 6, Gemini):** ReAct surface volume 0.900 vs. Reflexion 0.875; ReAct ε=0 pass 97.5% vs. 96.3%, ε=0.2 pass 90.0% vs. 86.3%. Simpler ReAct more robust under stress.
- **Fault tolerance:** ReAct degrades 7.5% from λ=0→0.2; Reflexion 10.0%. ∂R/∂λ steeper for Reflexion (−0.50 per 0.1 λ vs. −0.38). Combined (ε=0.2, λ=0.2): 84.0% pass2 (Fig. 3).
- **Recovery (Table 8, λ=0.2):** ReAct 47 faults encountered, 38 recovered (80.9%), +1.2 extra tool calls; Reflexion 52/35 (67.3%), +1.8 calls.
- **Fault ablation (Table 9):** mixed baseline 96.25%; timeout-only 98.75% (+2.50%, minimal impact); **rate-limit-only 93.75% (−2.50%, highest impact)**; partial-response-only 97.50% (+1.25%).
- **Domains (Table 7, λ=0, ReAct):** Scheduling pass@1 100%/pass2 100% (2.1 avg calls); Travel 87.5%/75.0% (5.4); Support 91.7%/83.3% (4.8); Ecommerce 87.5%/75.0% (4.6).
- **Failure patterns:** travel — missing payment context; support — escalation inconsistency; rate limits cause task abandonment rather than retry; schema drift propagates through subsequent calls.

## 9. Leakage & limitations
Adversarial reading: (1) k=2 is the weakest consistency signal — the τ-bench finding the paper builds on (60% pass@1 → 25% pass^8) suggests k=2 hides most variance; a GSE deployment at k=8 could look far worse. (2) The headline "8.8% degradation" mixes architectures/models in aggregation — per-cell numbers (Table 5) are cleaner. (3) Synthetic tools with known fault profiles may underestimate real-world failure modes (auth expiry, API deprecation, rate-limit windows) — the paper's own §6.2 admits this. (4) Single independent author; computations on Apple Silicon; no third-party replication. (5) Model/pricing data from December 2024 — the 82× cost ratio is a snapshot, though the direction (cheap model ≈ parity reliability) is the durable insight. (6) For GSE: rate-limit-only being the worst fault is the most actionable finding — it matches Garrett's live constraint (Odds API 20K credits/mo; 429s are GSE's production fault #1).

## 10. GSE overlap

Complementary, not duplicative — together they cover GSE's handoff layer and execution layer. Also adjacent: 0112 FailureAtlas (fault taxonomy — ReliabilityBench's fault profiles operationalize it as injectable configs), 0115 HiveMind (rate limiting is both HiveMind's scheduling problem and ReliabilityBench's worst fault), 0116 governed MCP (schema drift as a fault class → the MCP validator is the defense). No existing repo work on agent reliability benchmarking. Overlap type: complementary evaluation methodology, no duplication.

## 11. GSE implementation spec
(1) Reimplement the benchmark harness for GSE's actual agents: define a reliability grid over GSE's tool-using agents (research agent, content agent, data-fetch agent) with k ∈ {2,4,8}, ε ∈ {0.0,0.1,0.2} (paraphrased pick/research requests — real Garrett phrasing variants), λ ∈ {0.0,0.2} using GSE's real fault modes (429 rate limits, Odds API quota exhaustion, truncated responses, schema changes); (2) deterministic state-based verifiers per task (e.g., pick record written with correct fields, odds snapshot stored) — no LLM judges; (3) measure R(k,ε,λ), surface volume, and ∇R per agent; (4) establish the critical threshold (k*,ε*,λ*) below which an agent is not cleared for unattended production runs; (5) the paper's headline heuristic applies directly: multiply any single-run benchmark by 0.7–0.8 to estimate production reliability. Estimated effort: 3–5 days to build the harness on GSE's existing agent code, then ~$10-scale evaluation runs per agent (the paper's full 1,280 episodes cost under $10 on Gemini-class pricing).

## 12. Reproducible test
Reimplement Appendix A–C (tool specs, LAMBDA profiles, sample tasks are fully specified in the paper) and rerun the λ=0.2 fault ablation (320 episodes) with a current model; check that rate-limit-only still causes the largest degradation and that ReAct-style simple agents beat reflection-heavy architectures under stress. For GSE: run the GSE reliability grid on the research agent with k=4; exact metric: pass^4 at (ε=0, λ=0) vs. (ε=0.2, λ=0.2); exact baseline: the paper's 96.88% → 84.0% trajectory at k=2.

## 13. Acceptance / rejection gate
ADAPT if: (a) the GSE harness reproduces the paper's directional findings (rate limits worst fault; simpler architecture more robust under stress; ≥5% perturbation degradation); (b) total evaluation cost stays under $25 per agent per full grid run; (c) deterministic verifiers can be written for ≥80% of GSE agent tasks. Reject running the full 3D grid as a gate for every agent change — instead gate only on the critical-threshold cell (k*,ε*,λ*) once established, with the full grid quarterly or after architecture changes.

## 14. Improvement experiment
Extend where the paper stopped: run the grid at k ∈ {4,8} (the paper's admitted gap) on GSE's agents — testing whether the τ-bench 60%→25% consistency collapse replicates in GSE's domain, and whether the degradation is uniform or concentrated in specific task types (multistep odds-fetch vs. single-shot research). Second experiment: replace synthetic faults with GSE's real incident log (actual 429s, quota exhaustions, API schema changes from the Odds API / MySportsFeeds integrations) as the fault profile — measuring whether synthetic fault injection under- or over-estimates production reliability, which determines whether the harness can be trusted as a deployment gate.
