## 1. Research question
How do you build a production system that replicates content from 10,000+ creator-authorized YouTube channels to a blockchain-based decentralized platform, when YouTube's anti-automation defenses (API quota restrictions, IP rate limiting, behavioral bot detection, OAuth token lifecycle policies) do not distinguish authorized bulk access from abuse? The paper's central observation is a **coupled-defense phenomenon**: the protection layers are not independent — circumventing one (e.g., API quotas) silently activates another (e.g., OAuth token expiration), producing cascading, delayed failures. Grounded in three production incidents over 15 releases and 3.5 years, it argues detection-driven anti-bot measures impose a download-bound throughput ceiling (~10³ videos/day per instance) at or below steady-state demand, making priority triage and horizontal scaling structural necessities and driving a survivability-over-throughput design (a 25× reduction in download concurrency).

## 2. Dataset / schema
Not a data paper — the "dataset" is the production system's own operational history: 10,000+ enrolled YouTube channels, 15 release versions, 144 merged pull requests, 203 tracked issues across 3.5 years of operation (since August 2022). System state: AWS DynamoDB, 5 tables (channels: hash userId, range id, GSIs on joystreamChannelId/referrerChannelId/phantomKey; videos: hash channelId, range id, GSI on state+publishedAt; users, stats, whitelist), all PAY_PER_REQUEST billing; Redis 7.2.1 as the BullMQ job-queue backing store (maxmemory-policy noeviction; queue fully reconstructed from DynamoDB on restart); Elasticsearch; HubSpot CRM. Source code: https://github.com/Joystream/youtube-synch. No downloadable dataset link stated.

## 3. Method / model
Not an ML model — a production system architecture, "YouTube-Synch":
- **Split-service topology** (v3.4+, Figure 1): Sync Service (Docker, content processing) + HTTP API Service (Docker, NestJS REST: creator onboarding, channel state, dashboards, Swagger, BullMQ Board) sharing DynamoDB (state) and Redis (job coordination); Operational API container (ytopapi, self-hosted YouTube metadata); SOCKS5 proxy pool; Joystream chain (Substrate; ~6 s block time; Content Directory on-chain registry; Colossus distributed storage nodes; Orion GraphQL query node; DAO governance).
- **Four-stage BullMQ DAG pipeline** (Table II): (1) Download — concurrency 2, timeout 10,800 s, ytdlp via youtubedlexec with SOCKS5 routing, random 0–30 s pre-download sleep for behavioral variance, max 15 GB / 3 h per video; (2) Metadata — concurrency 2, timeout 1,800 s, blake3 content hashes + ffprobe (resolution/codec/duration); (3) Creation — concurrency 10, batches up to 10 video-creation extrinsics per Substrate batch call, auto-renewing locks (60 s duration, 30 s renewal); (4) Upload — concurrency 20, to random active Colossus nodes, 5 retries with 6 s inter-attempt sleep, maxRedirects: 0. BullMQ FlowProducer with failParentOnFailure: true.
- **Video state machine:** 7 processing states + 9 terminal unavailability states (16 total: Deleted, Private, AgeRestricted, MembersOnly, LiveOffline, DownloadTimedOut, EmptyDownload, PostprocessingError, Skipped, etc.); failed states retry next cycle.
- **Priority scheduling (Algorithm 1):** score = c.backlogPct × 1000 + sudo × 2000 + recency (recency = publishedAt − 946,684,800, seconds since Y2K; sudo = 10 base + 20 if fresh content >300 s + 20 if tier ∈ {Silver, Gold, Diamond}); p = 2,097,152 − ⌊(score/maxScore) × 2,097,152⌋, maxScore = 201,100; p ∈ [0, 2,097,152] (BullMQ max priority, lower = higher priority). YPP tiers: Bronze (5 videos, 1 GB, referral 2, default priority) / Silver (100, 10 GB, 25, +20) / Gold (250, 100 GB, 50, +20) / Diamond (1,000, 1 TB, 100, +20) — the tier system functions as admission control.
- **Auth evolution:** Phase 1 (v1.0–v3.7) Google OAuth2 (youtube.readonly, userinfo.profile, userinfo.email), storing 7 OAuth fields (accessToken, refreshToken, authorizationCode, email, googleId, userAccessToken, userRefreshToken) — the attack surface for the mass-expiration incident; Phase 2 (v4.0+) **video-based verification**: creator uploads an unlisted video titled "I want to be in YPP", backend verifies via the self-hosted Operational API (exists, unlisted, title matches, channel meets requirements), youtubeVideoUrl becomes the sole verification artifact — zero Google dependencies, zero quota consumption. Creator requirements: ≥50 subscribers, ≥2 videos, channel age ≥720 hours.
- **Fault tolerance:** Write-Ahead-Log model with cross-system state reconciliation between the immutable blockchain target and the defended source; AsyncLock (maxPending = Number.MAX_SAFE_INTEGER) serializing all DB operations after race-condition corruption.
- **Proxy evolution:** three generations (direct → Chisel tunnel → proxychains4 pool); download concurrency reduced 50 → 2 (25×) for survivability.

## 4. Equations & assumptions
- **Throughput ceiling (§IV-E, reconstructed — uncertain):** "The download stage is the binding constraint (concurrency C_d = 2). Per-video service time is T_v = 3·E[U(0, 30 s)] + t_f = 45 s + t_f, where the 45 s term is the triple pre-download sleep (known by construction) and t_f is the proxied fetch time. Single-instance throughput is λ = C_d/T_v = 2/(45 + t_f) videos/s. Even in the physically impossible best case t_f → 0, λ_max = 2/45 ≈ 3,840 videos/day; for any realistic t_f ≥ 45 s, λ ≤ 1,920 videos/day." *(Reconstructed — uncertain.)*
- **Demand vs. ceiling:** "Steady-state demand at target scale is ≈ 10,000 ×" (extraction truncated — stated as at/above the ceiling, exact factor not captured). The argument: detection limits, not blockchain throughput, are the binding constraint; therefore priority triage and horizontal scaling are structural necessities, not optimizations.
- **YouTube Data API v3 quota costs (Table I):** channels.list 1–5 units (2,000–10,000 max calls/day); search.list 100 units (100/day); videos.list 1–7 (1,428–10,000/day); playlistItems.list 1–3 (3,333–10,000/day); OAuth token exchange 0 (unlimited). Hard cap: 10,000 units/day/project — "at 10,000 channels, a single channels.list call per day per channel consumes the entire daily quota."
- **OAuth lifecycle:** refresh tokens expire after 6 months of inactivity; access tokens after 1 hour; "testing"-status projects' tokens after 7 days — "time bombs" for intermittently-used OAuth access.
- Assumptions: creator authorization model (opt-in YPP) partially addresses the legally gray area of proxy-based extraction; behavioral fingerprinting (request-timing variance, connection counts, User-Agent consistency) is adaptive; "perfectly regular request intervals are a stronger bot signal than high volume with natural variance."

## 6. Validation design
Longitudinal experience report, not a controlled experiment: three production incidents with concrete impact are the evidence base — (1) 28 duplicate on-chain objects from a database throughput failure (DynamoDB throttling → duplicate Creation-stage batches; fixed by PAY_PER_REQUEST billing via Pulumi IaC + AsyncLock serialization); (2) 10,000+ channels lost to a single OAuth mass-expiration event in one polling cycle (6-month unused-token policy + API migration rendering tokens unused → forced complete elimination of Google OAuth); (3) 719 daily errors from queue pollution (poison jobs). The throughput-ceiling argument is analytical (§IV-E, from the system's own concurrency and rate parameters). No baselines, no statistical testing, no external replication — single-system case study. Strengths: unusually honest about cascading failures and the coupling between defenses; exact production configs disclosed (Tables I–V, algorithms, state machine).

## 7. Numerical results / baselines
- Scale: 10,000+ enrolled channels; 15 releases; 144 merged PRs; 203 tracked issues; 3.5 years (Aug 2022 → report).
- Incident impacts: 28 duplicate on-chain objects (DB throughput failure); 10,000+ channels mass-expired in a single polling cycle (OAuth); 719 daily errors (queue pollution).
- Throughput: per-instance ceiling λ_max ≈ 3,840 videos/day (best case), ≤ 1,920 videos/day realistic (t_f ≥ 45 s); download concurrency cut 50 → 2 (25× survivability-over-throughput tradeoff); Creation stage batches 10 extrinsics per ~6 s block; Upload 5 retries × 6 s sleeps.
- Pipeline config (Table II): Download C=2/10,800 s; Metadata C=2/1,800 s; Creation C=10/6 s-per-block batch; Upload C=20/5×6 s.
- Video caps: 15,000 MB (15 GB), 10,800 s (3 h) per video.
- Priority: p ∈ [0, 2,097,152], maxScore = 201,100.
- YPP tiers: Bronze 5 videos/1 GB → Diamond 1,000 videos/1 TB; creator bar: ≥50 subs, ≥2 videos, ≥720 h channel age.
- No baselines (experience report); the comparison is before/after within the system's own history.

## 9. Leakage & limitations
Adversarial reading: (1) Single-system case study — no evidence the coupled-defense phenomenon or the throughput-ceiling math generalizes beyond YouTube-Synch's parameter choices; the "principles" are post-hoc rationalizations of incidents. (2) The analytical ceiling assumes the 45 s pre-download sleep is necessary (it's a design choice, not a physical constant). (3) No counterfactuals: we don't know whether OAuth elimination (video-based verification) actually reduced failures vs. better token-refresh hygiene — the mass expiration was caused by their own API migration making tokens go unused. (4) The legal framing ("creator authorization partially addresses" the gray area of proxy evasion) is the author's; circumventing IP blocks via proxies remains TOS-violating regardless of authorization, and the paper's lessons are partly lessons in evading platform defenses — usable defensively (hardening one's own pipelines) but not a playbook GSE should run against YouTube. (5) For GSE: the entire blockchain replication lane is irrelevant; the YouTube Data API quota mechanics matter only if GSE ever does bulk YouTube operations, which it doesn't (its YouTube presence is a single channel with manual uploads). (6) 3.5-year-old system; YouTube's defenses have likely evolved past the paper's specifics.
