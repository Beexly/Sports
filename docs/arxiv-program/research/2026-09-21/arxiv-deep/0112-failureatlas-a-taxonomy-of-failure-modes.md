# [0112] FailureAtlas: A Taxonomy of Failure Modes in Multi-Provider LLM Serving Infrastructure (arXiv:2607.17525v1)

**Citation:** Vishal Pandey, Gopal Singh (Metriqual, London / Athens), 2026. *FailureAtlas: A Taxonomy of Failure Modes in Multi-Provider LLM Serving Infrastructure*. arXiv:2607.17525v1. URL: https://arxiv.org/abs/2607.17525v1
**Ledger completed:** 2026-09-21. **Read:** full text (PDF via arxiv.org, 961 lines; abstract, taxonomy design, methodology, catalog §5, case studies §6, discussion, limitations, appendix A with full YAML definitions).
**Verdict:** ADAPT — no equations or prediction models to lift, but the 5×2 Layer×Detectability grid is a concrete reliability audit instrument for Garrett's own multi-provider gateway stack (his OmniRoute fork, the LLM/API layer behind Motif/Minis agents, and any provider-failover code GSE runs).

## 1. Research question
What goes wrong in the reverse-proxy layer between application code and foundation-model APIs (multi-provider LLM gateways like LiteLLM, Portkey, OpenRouter — which route, load-balance, fail over, rate-limit, and govern cost across model APIs), and how should those failures be classified so practitioners stop independently re-deriving the same root causes? The paper introduces "FA": a two-axis taxonomy (Layer of origin × Detectability: Loud vs. Silent) plus an evidence-grounded catalog of five verified failure modes with mechanistic root-cause analyses and reproduction scripts. Its principal finding: the most operationally severe failures are *silent* — they return HTTP 200, pass every standard health check, and corrupt application state in ways that require semantic-level observability to detect.

## 2. Dataset / schema
No conventional dataset. Evidence streams: (a) firsthand stress testing — two entries discovered during ContinuityBench (CB) Phase 2 evaluation campaigns (hundreds of parallel agent instances against a mock LLM-provider gateway simulating real-world latency, rate limits, transient 502s; documented via system logs + semantic-continuity metric drops); (b) structured survey of public GitHub issue trackers for LiteLLM, Portkey, OpenRouter using layer-scoped queries (e.g., SSE stream "cut off" OR "truncated", function calling "malformed JSON" streaming; "connection timeout" gateway failover; asyncio block) — dozens of candidates, filtered to three survivors meeting the inclusion criteria. Each catalog entry carries a structured YAML record (id, name, layer, detectability, summary, mechanism, evidence with URL, reproduction path, mitigation). Access: public catalog repo (see §8).

## 3. Method / model
Taxonomy design (rejected alternatives documented): single-axis by symptom rejected (conflates failures with different root causes — a retry storm and a Redis semaphore leak both produce 429s but need different fixes); three-axis adding severity rejected (severity is almost entirely determined by detectability). Chosen: two orthogonal axes, Layer (5 levels) × Detectability (2 classes), 5×2 matrix. Layer boundaries drawn where failure mechanism, responsible code owner, and mitigation strategy change simultaneously. Inclusion criteria for catalog entries: (1) concrete and specific — not a general complaint; (2) independently verifiable provenance — persistent URL to a GitHub issue, postmortem, or merged PR (anecdotes rejected); (3) mechanistically explainable — the full sequence of events leading to the failure must be unambiguous, not just a stack trace. Manual validation: whole issue threads read, logs examined, execution traced through the open-source codebase, merged fixes checked. Standalone reproductions for three of five entries (minimal isolated scripts); the other two get detailed README setup instructions (require Kubernetes/Redis). Companion relationship with ContinuityBench documented (§2.3): CB measures continuity loss quantitatively; FA catalogs the failure categories.

## 4. Equations & assumptions
No equations stated. The paper is a taxonomy and catalog study; no mathematical models, no hyperparameters. (The one formula-like object is the taxonomy grid itself: 5 layers × 2 detectability classes = 10 cells, five populated.) Assumptions stated in text: (1) taxonomy boundaries are a pragmatic design choice, "not a mathematically provable or mutually exclusive decomposition of all failure space" (§8); (2) Layer×Detectability is the minimal structure capturing the two triage questions "where did this break?" and "why didn't we catch it sooner?"; (3) the surveyed patterns (sync calls blocking async loops, stateless chunk processing losing inter-chunk state, unreleased resource counters) are architectural rather than implementation-specific and "likely to recur in any gateway built on similar design choices"; (4) severity is almost entirely determined by detectability, which is why a severity axis was rejected.

## 5. Features / target
The "features" are the two taxonomy axes. Axis 1 — Layer (origin): L1 Network/Transport (TCP timeouts, TLS, DNS; sync calls blocking asyncio event loops); L2 Streaming/Protocol (SSE token-stream statefulness: running index for parallel tool calls, partial-JSON accumulators; stateless chunk processing); L3 State/Session (conversation-history corruption/truncation/reordering/silent turn deletion; uniquely concurrency-sensitive); L4 Model Behavior (intrinsic generation drift, unannounced provider-side changes — deliberately included but intentionally EMPTY; no evidence-grade entries found); L5 Governance/Cost (retry policies, rate-limit counters, cost accounting; control-plane failures that trigger exactly when upstream providers degrade). Axis 2 — Detectability: Loud (HTTP 5xx, exceptions, crashes, hard 429s, health-check timeouts — high signal-to-noise, enters the incident pipeline) vs. Silent (HTTP 200 OK, passes health checks, corrupts the semantic payload — drops turns, merges tool-call arguments into malformed JSON, substitutes cheaper model variants). "Target": classification of each entry into exactly one of the 10 cells.

## 6. Validation design
Validation = evidence grading, not a train/test split. Every entry had to survive: specificity screen, verifiable-provenance screen (persistent primary-source URL), mechanistic-explainability screen, plus manual thread/code/fix tracing. Two firsthand entries include controlled experimental reproductions: race condition (minimal asyncio script, shared vs. isolated state mutation) and retry storm (mock rate-limited provider, 100 concurrent simulated agents, fixed-interval vs. exponential-backoff-with-jitter side-by-side). One surveyed entry (index collision) adapted the reporter's own repro script from LiteLLM#33678 to run against statically captured chunks. No cross-validation, no statistical metrics, no baselines compared — the paper explicitly positions itself as taxonomy, not measurement. Taxonomy robustness check: the three-axis (symptom, symptom+severity) alternatives are argued against rather than evaluated numerically.

## 7. Numerical results / baselines
Key numbers, quoted from the paper (no baselines in the ML sense; the catalog is the result):
- Race condition (§6.1, firsthand): at C=5 concurrent agent sessions, Continuity Preservation Rate (CPR) near-perfect; at C=100, CPR collapsed to ~28% (a ~72-percentage-point drop; appendix A.1 records "72% drop in Continuity Preservation Rate under high concurrency"). Mechanism: two coroutines per session each read history, appended a turn, called the model, wrote history back — the second writer silently overwrote the first's contribution; shared global history cache mutated by concurrent requests, read-modify-write cycle containing an async yield (the LLM network call) with no lock. HTTP 200 on every request; detected only via CB semantic-continuity metric drops.
- Retry storm (§6.2, firsthand): 100 parallel agents, fixed 1-second retry interval after transient upstream 502; synchronized retries saturated the provider rate limit on every window; "25% of requests to fail permanently despite the underlying issue being a momentary hiccup"; provider bills for partial completions (tokens before mid-stream failure) → runaway billable API spend for zero successful completions. Mitigation: exponential backoff with jitter + global circuit breaker.
- Index collision (§5.1.1, LiteLLM#33678, Silent): proxy's SSE iterator reset its internal index counter per chunk, stamping every tool-call chunk index=0; client concatenated independent tool arguments (e.g., `{"path": "a.rs"}{"path": "b.rs"}`) into corrupted string saved into conversation history; surfaced only on the next turn as JSONDecodeError misdirecting debugging to the network layer.
- Redis semaphore leak (§5.1.2, LiteLLM#20256, Loud): error-handling path bypassed the semaphore decrement (missing finally), "active" count stranded in Redis; accumulated upstream errors drove the count to max_parallel_requests → permanent HTTP 429 for that API key with zero requests actually in flight; resolved only by manual Redis flush. Mitigation: TTL on in-flight counters or strict try/finally.
- Event-loop block (§5.1.3, cited in body as LiteLLM#21033 — a database-query-blocking-/health endpoint issue; appendix A.5 YAML cites LiteLLM#24788, describing a synchronous base64 image-URL conversion hanging on a 2-minute socket timeout for unroutable IPs — paper-internal discrepancy noted): synchronous I/O in an asyncio gateway blocks the whole event loop; health checks every ~10 seconds → persistent micro-outages. Mitigation: async drivers everywhere in the critical path or run_in_executor thread pools.
- Structural observations: detectability is independent of layer (no layer exclusively Loud/Silent); Silent column sparser (2 of 5 entries) but more dangerous; Model Behavior row entirely empty — stated as a finding, not a gap ("The gaps in a taxonomy often point exactly to where the field's observability tooling is weakest").

## 9. Leakage & limitations
Adversarial reading: (1) Tiny catalog (n=5) — the "silent failures dominate" thesis rests on 2 Silent entries; the paper is candid that this is a foundational vocabulary, not an exhaustive survey. (2) Self-sourcing bias, disclosed: the two most thoroughly characterized entries are the authors' own firsthand discoveries, from a harness designed specifically to stress-test state management and retry policies — exactly the failures it surfaced; community sourcing is needed for balance. (3) Evidence quality varies: surveyed entries rely on public issue trackers, some from a single detailed bug report. (4) Internal discrepancy: §5.1.3 cites LiteLLM#21033 (synchronous DB query blocking /health); appendix A.5 YAML cites #24788 (synchronous base64 conversion, 2-minute socket timeout) — a careful reader should verify which issue the mechanism text actually matches. (5) Survivorship bias in the engineering record, acknowledged by the authors: Loud failures are overrepresented in issue trackers precisely because monitoring catches them; Silent failures are underrepresented because "the infrastructure for noticing them does not yet exist in most deployments." (6) The taxonomy axes are a pragmatic design choice, not a provable decomposition (§8). (7) Domain gap: zero sports/prediction content; relevance to GSE is purely operational (gateway reliability), and the paper documents LiteLLM-specific bugs — whether Garrett's OmniRoute fork shares the architectural patterns (sync-blocking loops, SSE index handling, Redis semaphores) must be verified against his code, not assumed.

- Mitigations to verify: exponential backoff with jitter on all provider calls; global circuit breaker per provider; TTL on any Redis/counter-based rate limits; try/finally on all semaphore decrements; async-only I/O in hot paths; deep-copy isolation of per-session state before any async yield.

## 12. Reproducible test
Clone the FailureAtlas repo and run all three standalone reproductions (race-condition, retry-storm, index-collision). Exact check: race-condition repro must show shared-state mutation losing turns under concurrency while isolated state preserves them; retry-storm repro must show fixed-interval retries synchronizing and saturating the mock provider's 15 req/min limit while backoff-with-jitter succeeds (Appendix A.3 notes the mock: 100 concurrent failovers against a 15 req/min rate-limited provider); index-collision repro must emit index=0 on parallel tool-call chunks from captured Ollama data without a live server. If the reproductions don't reproduce, the paper's catalog claim fails and the ADAPT is voided. Then: apply the Layer×Detectability grid to one real GSE component (e.g., the OddsPapi polling loop) and produce a one-page failure-mode worksheet — each hop classified into exactly one cell with a Loud/Silent call justified in one sentence.

## 14. Improvement experiment
Extend the taxonomy one axis for Garrett's sports-data context: add a **Temporal/Staleness** dimension. LLM gateways fail in space (which layer); sports-data pipelines fail in time (stale odds snapshots, delayed injury feeds, cached projections served past their validity). A 5×2×2 cube (Layer × Detectability × Fresh/Stale) would classify failures like "OddsPapi 429 retry storm during line-movement window returns cached pre-move lines with HTTP 200" — Silent, Governance, Stale — which is exactly the failure that would silently poison the GSE engine's CLV labels. Build it by logging every odds-API response with (fetch timestamp, provider timestamp if present, HTTP status) for one week, then classify every anomaly into the cube; any anomaly that lands in Silent×Stale is a candidate for a semantic-observability alarm (e.g., line age > N minutes during open hours).
