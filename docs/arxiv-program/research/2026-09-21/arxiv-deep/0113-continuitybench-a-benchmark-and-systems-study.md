# [0113] ContinuityBench: A Benchmark and Systems Study of Stateful Failover in Multi-Provider LLM Routing (arXiv:2607.15899v1)

**Citation:** Vishal Pandey, Gopal Singh (Metriqual, London / Athens), 2026. *ContinuityBench: A Benchmark and Systems Study of Stateful Failover in Multi-Provider LLM Routing*. arXiv:2607.15899v1. URL: https://arxiv.org/abs/2607.15899v1
**Ledger completed:** 2026-09-21. **Read:** full text (PDF via arxiv.org, 1066 lines incl. appendices A–D).
**Verdict:** ADAPT — companion to FailureAtlas (0112); the History-Forwarding failover pattern, the factual-anchor judge protocol, and the CPR/CLO metrics port directly to Garrett's multi-agent stack (agent-bus handoffs between Motif and Minis, OmniRoute provider failover, concurrent research-agent orchestration).

## 1. Research question
In production LLM deployments, high API availability does not equal conversational continuity: when a primary provider fails, naive stateless failover keeps uptime but silently discards conversation history. The paper (a) formalizes continuity as a measurable property distinct from availability, (b) introduces two metrics — Continuity Preservation Rate (CPR) and Continuity Latency Overhead (CLO), (c) builds a stateful multi-provider proxy using History-Forwarding (forward the full messages[] array to the fallback provider) and evaluates it at N = 750 failover events, and (d) releases `continuitybench`, an open harness that generates multi-turn conversations with embedded factual anchors, injects failovers at configurable turns, and scores context preservation via automated LLM judging. It also documents two severe failure modes found during stress testing (concurrency race condition, failover retry storm).

## 2. Dataset / schema
- Synthetic test suite: N = 150 multi-turn conversations, each 7–11 turns (mean 9.1) of alternating user/assistant messages. Turn 0 establishes a distinctive factual anchor (claim, preference, invented name, date, or term); subsequent turns are topically unrelated filler; the final user message is a probe answerable only with the turn-0 anchor.
- Fact types (30 conversations each, 5 types): Preference ("I only read Gothic horror"), Invented term ("The protocol is codenamed Plexarine"), Proper name ("The keynote speaker is Yuna Kowalski"), Numeric value ("The passcode is 42-8901"), Date ("The warranty expires January 21, 1966").
- Probe turns at index 6 / 8 / 10 (44 / 58 / 48 conversations).
- Experiment manifest (experiment_manifest.json): fixed triples (conversation_id, failure_turn, fallback_provider), generated deterministically from seed s = 42; failure timing "late" (injected at the probe turn). Three injected failure classes: TIMEOUT, API_ERROR (simulated 502), RATE_LIMIT (simulated 429).
- Evaluation scale: 5 independent runs × 150 conversations = N = 750 failover events per system (baseline and treatment), concurrency C = 100 via asyncio.Semaphore, 5-second cooling period between runs; logged responses judged by GPT-4o.
- Provider chain: primary OpenAI (gpt-4o-mini, temperature 0.0) → fallback Anthropic (claude-3-5-sonnet-20240620, temperature 0.0). (Gemini gemini-1.5-flash was tested as tertiary fallback but its 15 req/min free-tier limit triggered the retry-storm failure; excluded from reported results.)
- Access: synthetic, released with the harness (see §8).

## 3. Method / model
Architecture (Fig. 1, §3.2): request interceptor (OpenAI-compatible POST /v1/chat/completions; extracts conversation_id and messages[]), conversation state store (Python dict keyed by conversation_id in the harness; Rust-native in-memory store with sub-5ms read/write in the Metriqual production deployment — explicitly distinguished from harness numbers), deterministic fault-injection layer (seed + manifest → one of the three failure modes at the designated turn), failover controller (iterates a configurable fallback chain from providers.yaml). Provider abstraction normalizes OpenAI and Anthropic into a common chat(messages, model, temperature, max_tokens) signature. The two systems under comparison differ in exactly one decision: the messages[] payload forwarded at failover — baseline forwards only the latest user message (single-element payload); treatment (History-Forwarding) forwards the complete messages[] array. Judge protocol (§4.3): GPT-4o with structured output (response_format=JudgeScore) → binary preserved ∈ {true, false} + free-text reasoning; judge sees only expected fact, probe question, and the response (not full history — no leakage). Fast-path: case-insensitive verbatim substring match → preserved=true without an API call; responses containing [ERROR]/[HTTP ERROR] → false. Judge calibration: 20 hand-labeled edge cases, 19/20 = 95% agreement (single disagreement: partial date recall "June 2029" vs "June 14, 2029" correctly rejected); ≥90% required to proceed. Manual audits: 15 treatment responses in Phase 1, per-change audits in Phase 2, 10 randomly sampled Run-5 responses in the final audit (all passed; scripts/audit_phase2.py + results/phase2_audit_output.txt). Retry policy adopted after the retry-storm discovery: exponential backoff with jitter on HTTP 429/502/503/504: t_wait = min(30s, 2^a + U(0,1)), a = 0-indexed attempt; max 5 retries per failover request; proxy read timeout 300.0s. Six treatment failures (6/750) root-caused to fallback-model instruction-following errors (e.g., month+year without day), not forwarding failures — verified via proxy logs.

## 4. Equations & assumptions
- **Definition 1 (Continuity Preservation Rate):** "Let F = {f_1, …, f_N} denote the set of failover events in an evaluation run. For each event f_i, let preserved(f_i) ∈ {0,1} indicate whether the fallback provider's response demonstrates access to a factual anchor established in the pre-failover conversation history, as determined by an automated LLM judge (Section 4). The Continuity Preservation Rate is: CPR = (1/N) Σ_{i=1}^{N} preserved(f_i)." CPR reported with 95% Wilson score CI. *(Verbatim wording; formula reconstructed from garbled PDF extraction — uncertain in exact notation.)*
- **Definition 2 (Continuity Latency Overhead):** "For each failover event f_i, let ℓ_i^{treat} and ℓ_i^{base} denote the end-to-end latency of the treatment (history-forwarding) and baseline (stateless) systems, respectively. The Continuity Latency Overhead is: CLO = (1/N) Σ_{i=1}^{N} (ℓ_i^{treat} − ℓ_i^{base})." Reported as mean and P95. *(Reconstructed — uncertain.)*
- **Backoff:** t_wait = min(30s, 2^a + U(0,1)), a = attempt index (0-indexed), U(0,1) uniform jitter. (Verbatim §4.6/§6.2.)
- Assumptions (stated): (1) CPR's judge-verification task is factual (expected fact vs. response), not preference-based — "we expect and empirically observe higher interrater reliability"; (2) the deterministic fault-injection schedule is a valid controlled proxy for real provider failures — "eliminating confounding from stochastic failure timing"; (3) cross-provider heterogeneity (different model families for primary and fallback) ensures measured recall is genuine context transfer, not model-specific memorization; (4) final CPR/CLO are pooled across the 5 runs (Wilson CI over pooled counts) rather than averaged per run; (5) absolute latency values are properties of the third-party APIs, not the proxy — only the paired CLO differential is attributable to the forwarding strategy; (6) harness performance (Python/asyncio) is explicitly NOT the production claim (Rust data plane, sub-5ms, zero-copy).

## 5. Features / target
Input: full messages[] conversation array (the "feature" is the complete dialogue history). Target: preserved(f_i) ∈ {0,1} — binary judge verdict on whether the fallback response correctly incorporates the expected factual anchor. No ML model is trained; the "model" is the architecture choice (History-Forwarding vs. stateless) and the LLM judge is GPT-4o as a fixed evaluator. Secondary target: per-event latency differential (CLO). No feature engineering; the instrumentation is the factual-anchor/probe construction and the judge prompt (Appendix A, verbatim system prompt in paper).

## 6. Validation design
- Controlled A/B: baseline and treatment share identical infrastructure (interceptor, fault injector, provider abstraction, logging, evaluation harness) and the same deterministic manifest; the only difference is the failover payload construction — "differ in exactly one line of code."
- Test suite: 150 synthetic conversations with ground-truth anchors; deterministic fault injection (seed 42, "late" timing at the probe turn); both systems experience identical failure events.
- Scoring: GPT-4o judge + fast-path heuristic; judge calibrated at 95% agreement (≥90% gate); judge blinded to full history; manual audits at three stages.
- Replication: 5 independent runs × 150 events = 750 per system at C=100 concurrency; pooled Wilson CI over all 750; per-run stability table (Appendix B/Table 2).
- Baselines: stateless failover (industry-standard request-level gateway behavior, as in LiteLLM/Portkey/OpenRouter — §2.1) as the control; no other architectures compared.
- Negative-result documentation: the race condition and retry storm discovered during stress testing are reported with mechanism and fix, not absorbed.
- No train/validation split (no learning); no time-ordering concerns (synthetic synchronous runs).

## 7. Numerical results / baselines
- CPR (Table 1, N = 750 pooled): treatment 744/750 = 99.20% [95% Wilson CI: 98.27%, 99.63%]; baseline 0/750 = 0.00% [0.00%, 0.51%]. ("The difference is significant by any reasonable standard.")
- Per-run stability (Table 2 / Appendix B Table 5): runs 1–3 and 5: 149/150 = 99.3% [96.3, 99.9]; run 4: 148/150 = 98.7% [95.3, 99.6]; max spread 0.6 percentage points. (Appendix B pooled CI prints as [98.3, 99.6] — minor rounding discrepancy vs. the body's [98.27%, 99.63%], noted.)
- By conversation length (Table 4, Run 5): treatment CPR 97.7% (7 turns, n=44), 100.0% (9 turns, n=58), 100.0% (11 turns, n=48); baseline 0.0% throughout. Single 7-turn failure = fallback-model instruction-following error, not a forwarding failure.
- CLO (Table 3, Run 5, n=150, paired per-conversation differences, ms): mean +59, median −450, P25 −1,687, P75 +1,295, P95 +13,614. Baseline median latency 4,311 / treatment 4,457; IQR spans ~4,000 ms for both (dominated by third-party API variance). Queue-wait medians: 942 ms baseline, 902 ms treatment; P95 ≈ 1,200 ms both. Interpretation (paper's): "the History-Forwarding strategy imposes negligible additional latency at the central tendency"; the P95 tail (+13,614 ms) is attributed to 9–11-turn conversations with the largest payloads at the Anthropic fallback.
- Stress-test failures (negative results, §6): (a) race condition — C=5 → near-perfect CPR; C=100 → CPR collapsed to ~28% (shared global history cache, asyncio interleaving across the network-call yield); fixed by per-conversation deep-copies before async yield. (b) Retry storm — 100 concurrent failovers against Gemini's 15 RPM free tier with fixed 2.0s retry → self-sustaining synchronized cycle, thousands of req/min, sockets exhausted, proxy crashes, CPR → 0; fixed by t_wait = min(30s, 2^a + U(0,1)) + max 5 retries → "completely stabilized queue wait times and eliminated proxy crashes … without a single dropped connection" in the N=750 run.
- Judge calibration: 95% agreement (19/20) vs. hand labels; threshold ≥90% passed on first attempt; final manual audit 10/10 passed, zero false positives found.

## 9. Leakage & limitations
Adversarial reading: (1) Synthetic conversations — explicit probes ("Which cuisine did I say I prefer?") are far easier than organic elliptical/implicit references; real-world validation on human-annotated logs is stated as "a necessary next step." (2) LLM-as-judge epistemology: GPT-4o judging Anthropic Claude outputs risks cross-family bias; manual audits found zero false positives in 10 sampled cases but cannot rule out systematic bias (paper's own framing). (3) Judge blindness to history is good for leakage but means the judge cannot catch cases where the model answers correctly by hallucinated luck matching the anchor. (4) Single provider chain: OpenAI→Anthropic only; the Gemini arm was abandoned (retry storm) — no empirical claim about the broader model ecosystem's instruction-following on forwarded history. (5) Exactly one failure per conversation, injected at the final turn — no rolling/compounding failures; multi-hop failover robustness unmeasured. (6) Text-only, turn-level, batch HTTP — no SSE streaming, no multimodal, no mid-stream voice failover (the motivating domain). (7) The 6/750 treatment failures are attributed to fallback-model instruction-following, not forwarding — correct per logs, but it means measured CPR conflates forwarding fidelity with fallback-model quality; the "residual 0.8%" is a model property, not an architecture property. (8) Domain gap: zero sports/prediction content; and the Python harness numbers (latencies, CLO) are not production-proxy numbers — the paper explicitly warns against conflating them. For GSE, the portable assets are the method (anchor-injection testing, judge protocol, CPR metric) and the two failure-mode mitigations, not the 99.20% number.

## 11. GSE implementation spec
Build a "HandoffBench" for the GSE agent-bus, porting the CB protocol:
- Anchor injection: every parent→subagent task gets 2–3 planted factual anchors (e.g., a specific baseline number, a named constraint like "never touch gse-grok-build-sandbox", an invented term). The subagent's returned report is the "probe response."
- Judge: a deterministic fast-path (anchor string present verbatim?) plus an LLM judge on the report (same blinded setup — judge sees anchor + task + report, not the parent's full context). Calibrate the judge on 20 hand-labeled handoff cases to ≥90% agreement, mirroring §4.3.
- Metrics: Handoff Preservation Rate (HPR) = fraction of handoffs where all planted anchors survive, with Wilson CI; Handoff Latency Overhead analogous to CLO if desired. Run at the program's real concurrency (parallel subagent batches).
- Failover analog: provider/model failover in Garrett's stack — if OmniRoute fails over mid-conversation between model providers, require History-Forwarding (full messages[] forward), not request-level retry; verify retry policy is exponential-backoff-with-jitter (t_wait = min(30s, 2^a + U(0,1)), ≤5 attempts), never fixed-interval; verify per-session state isolation (deep-copy before any async yield) in any stateful proxy code.
- Effort: ~1 day to write the anchor-injection + judge harness; ~1 day to run the first HPR measurement across one batch of subagent handoffs.

## 12. Reproducible test
Clone https://github.com/Vishalsyscode/continuitybench at tag v1.0-phase2-final; run the harness against a mock provider pair (no live API spend needed for the mechanism check — the repo's fault injector is deterministic, seed 42). Exact checks: (a) reproduce the CPR gap on the 150-conversation suite — treatment CPR ≥ 95% (allow for fallback-model variance vs. the paper's 99.20%) vs. baseline ≈ 0%; (b) reproduce the two negative results — shared-state harness at C=100 must show the CPR collapse (the paper's ~28%), and fixed-interval retries against a 15 RPM mock must self-sustain (the thundering-herd cycle) while backoff-with-jitter stabilizes; (c) verify judge calibration ≥ 90% agreement on 20 hand-labeled edge cases before trusting any HPR number. If the harness doesn't run or the gap doesn't reproduce, ADAPT is voided.

## 13. Acceptance / rejection gate
ADAPT if: (a) the continuitybench harness runs to completion from the tagged commit and reproduces the treatment-vs-baseline CPR gap (treatment ≥ 95%, baseline ≤ 5%) on the synthetic suite; (b) the retry-storm repro shows fixed-interval retries destabilizing and jittered backoff stabilizing (mechanism check); (c) judge calibration on 20 hand-labeled handoff cases reaches ≥ 90% agreement (the paper's own gate). REJECT the paper (flag for replacement) only if the harness is unrunnable or the core CPR claim fails to reproduce — per the template, weak papers get full ledgers with REJECT; this one is methodologically strong, so non-reproduction is the only REJECT trigger.

## 14. Improvement experiment
Close the paper's own stated gap: compounding failures. Run the HandoffBench port with *rolling* anchor checks — inject a mid-conversation provider failover (or a mid-task subagent restart, which is the GSE analog) at turn k, then a second failover at turn k+2, and measure cumulative anchor loss and latency overhead per failover depth. The paper leaves this open (§7: "measuring the cumulative latency overhead and context degradation of multiple consecutive failovers … remains an open empirical question"). For GSE specifically: measure HPR across a full Motif→Minis→Motif round trip (handoff, phone-side build, return), not just one direction — the two-hop case is where silent context loss compounds, and it's the configuration Garrett actually operates in.
