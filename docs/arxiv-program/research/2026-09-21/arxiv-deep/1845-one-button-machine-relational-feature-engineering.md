Rationale: the only anchor method built natively for relational data *with* temporal cutoff handling (no post-cutoff leakage by construction) and train/validation drift-feature detection; GSE should adapt its entity-graph + cutoff-timestamp + drift-detection design to nflverse tables, replacing the Spark implementation with a modern batch pipeline.

## 1. Research question
Can the most labor-intensive step of data science — joining relational tables and hand-crafting features from the joined data — be automated end-to-end ("one button")? OneBM takes a database with a main table (target column + key columns), enumerates joining paths over the entity graph (tables = nodes, foreign-key links = edges) via depth-first search, collects each entity's data as a relational tree, auto-identifies the collected data type (numerical, categorical, text, timestamp, multiset, sequence, time series), and applies type-appropriate transformation modules. It extends DSM (Deep Feature Synthesis, Kanter & Veeramachaneni 2015) with unstructured/temporal types, explicit anti-leakage cutoff timestamps, drift detection, and a Spark implementation scaling to 100 GB. Validated on three Kaggle competitions: top 16–24% finishes with no hand-crafted features, beating DSM head-to-head on KDD Cup 2014 (rank 81 vs 145).

## 2. Dataset / schema
Three Kaggle competitions (Table I): KDD Cup 2014 (donation-project success prediction; 4 tables, 51 columns, 0.9 GB); Grupo Bimbo inventory demand (weekly bakery sales; 5 tables — sale history [main], town state, product, client — 19 columns, 7.2 GB; RMSLE metric); Outbrain click prediction (ad click likelihood; 8 tables, 25 columns, 100.22 GB uncompressed, 119M training examples, 32M test). Time ranges: competition-specific (2014–2017 era). Public via Kaggle. Running example in paper: Irish rail database (main/delay/info/event tables, train arrival delays).

## 3. Method / model
**Entity graph + joining paths:** Definition — a joining path p = T₀ —c₁→ T₁ —c₂→ T₂ … —cₖ→ Tₖ ⇥ c, where T₀ is the main table. Enumerated by depth-first traversal up to user-set MaxDepth, simple paths only. Two modes: *forward-only* (no backward traversal from depth d₁ to d₂ with d₁ ≥ d₂; covers most interesting relations) and *full* (backward allowed; more relations, more cost). Edge types: one-to-one, one-to-many, many-to-one, many-to-many. Path types: *one-to-one* (no one-to-many/many-to-many edge → collected data is a single value) vs *multiple* (collected data is a collection). Redundant paths removed via canonical forms (shortest equivalent path).
**Data collection:** per entity e, the collected column values along path p form a relational tree Tᵉ_p (root = entity, leaves = values, intermediate nodes = joined rows). GroupBy(Tᵉ_p, d) groups leaves by depth-d nodes, exposing per-group multisets (e.g. events per reported train message vs all events).
**Data transformation (type-identified, pluggable):** numerical → as-is; categorical → (un)normalized label distribution; text → sequence features; timestamp → calendar features; number multiset → avg, variance, max, min, sum, count; item multiset → count, distinct count, high-correlated items; **time series** (numerical + timestamp on path) → avg, max, min, sum, count, variance, **recent(k)**, FFT, discrete wavelet transform, autocorrelation coefficients; categorical sequence → count, distinct count, high-correlated subsequences. Defaults are "the most common features data scientists examine first"; custom extractors plug in via interface.
**Temporal safety (§III-B.4):** "OneBM only collects data that was generated before the prediction cutoff time to avoid mining leakage." The cutoff column is declared by naming convention in the main-table header; each entity's cutoff is compared against data-generation timestamps; only earlier data is kept. For timestamped tables, subsampling takes the *most recent* rows rather than uniform.
**Feature selection (§III-C):** deduplicate; **drift detection** — if train/test have implicit order (timestamp), compare feature distributions between training and validation sets and drop drifted features ("may cause overfitting"); Chi-square hypothesis test of feature–target dependence, drop marginally independent features. (Full feature-selection automation declared out of scope/future work.)
**Efficient implementation (Spark):** depth-first traversal with a LIFO cache stack of intermediate joined tables (stack size ≤ MaxDepth; freed when leaving a branch); dynamic subsampling via MAX-JOINED-SIZE — estimate joined size, compute sampling ratio, stratified uniform sampling per training example; most-recent sampling for timestamped tables. Cluster: 12 machines × 92 GB RAM × 12 cores.

## 5. Features / target
Input: raw multi-table relational databases. Generated features per path–column–type combination: aggregations (avg/var/max/min/sum/count/distinct), label distributions, calendar features, time-series features (recent-k lags, spectral, autocorrelation), high-correlation itemsets/subsequences. Counts: KDD Cup 90 features, Bimbo 84, Outbrain 133. Targets: project success (AUC), weekly demand units (RMSLE on log demand), ad click (MAP@12). Horizons: competition-defined (e.g. Bimbo: predict weeks 10–11 from weeks 3–9; separate models per horizon — 1-week and 2-week ahead).

## 6. Validation design
Kaggle public/private leaderboards as the validation protocol (the paper's explicit choice): model selection between RF (100 trees) and XGBoost (trained to convergence, early-stopped on validation) via *public* leaderboard, final numbers reported on *private* leaderboard — "standard in Kaggle competitions". No hyperparameter tuning ("not the main focus"). Head-to-head vs DSM on KDD Cup 2014 (DSM numbers from the DSM paper: untuned rank 314/AUC 0.55481 top 66%; tuned rank 145/AUC 0.5863 top 30%). No CV, no significance tests.

- Grupo Bimbo: RMSLE **0.48681**, rank 326th = top 16%, beating 1,642 of 1,969 teams; at the plateau of the error curve ("very close to the best human results"). ## 9. Leakage & limitations
Adversarial read: (a) The cutoff-timestamp mechanism is the paper's strongest leakage control, but it depends on a *naming convention* in the data header — silent misconfiguration = silent leakage; GSE must enforce this programmatically, not by convention. (b) Kaggle public-leaderboard model selection is itself a mild overfitting protocol (public LB probing), standard but worth noting. (c) The Bimbo "series table" was a manual human intervention (copying the main table with timestamp) — the vaunted time-series features required a human to frame the problem temporally; not fully "one button". (d) Outbrain's first solution mis-typed ad id as numerical — the type-inference is brittle and needed manual correction; same risk for sports IDs (team_id as number vs category). (e) Drift-feature removal by train/validation distribution comparison can delete *legitimately predictive* regime features (e.g. a genuinely new offensive scheme) — drift ≠ leakage, and the paper conflates them. (f) Feature selection is admittedly thin (dedup + drift + Chi-square); no interaction-aware selection. (g) No equations, no statistical guarantees; Spark-era engineering (2017) is overkill for NFL-scale data (millions, not billions, of rows).

## 11. GSE implementation spec
Build "GSE-OneBM" as the relational discovery layer (no Spark — NFL scale fits in DuckDB/pandas): (1) Entity graph: games → plays (one-to-many), games → drives, plays → players (many-to-many via participation), games → odds snapshots (timestamped), teams → games. (2) Main table: game rows with target (cover/total) and **cutoff timestamp = kickoff** (enforced in code, not naming convention). (3) Path enumeration: forward-only, MaxDepth 2 (game→plays→players is enough; depth 3 explodes). (4) Type modules: play multiset → EPA avg/var/max/min/success rate/explosive rate; drive sequences → per-drive means; timestamped odds → line-movement recent(k)/volatility (the paper's time-series module, directly reusable); categorical → label distributions (e.g. cover rate by referee crew). (5) Selection: dedup + Chi-square vs target + **drift quarantine** (compare feature distribution 2020–2022 vs 2023; quarantine drifted features into a "regime-risk" list rather than deleting — correcting the paper's conflation). (6) Output: versioned feature definitions with (path, type, transform, cutoff) provenance. Effort: ~1 week (DuckDB + Python; the transform modules are the bulk).

## 12. Reproducible test
Dataset: nflverse 2020–2024 relational tables (games, plays, drives) + odds snapshots. Target: spread cover; metric: log-loss; baseline: hand-built flat features (LightGBM). Compare LightGBM on baseline vs baseline + OneBM-discovered relational features. Drift-quarantine list published as a diagnostic artifact.

## 13. Acceptance / rejection gate
ADOPT the relational discovery layer iff (a) 2024 held-out log-loss improves by ≥ 0.003 over baseline, AND (b) the leakage audit passes 100% — every generated feature recomputed from a kickoff-cutoff replay matches its stored value exactly on a 500-game sample, AND (c) the drift-quarantine list is non-empty and reviewed (a run that finds zero drift across 2020–2024 is suspicious and fails the gate — the COVID season must show up). REJECT if any leakage-audit mismatch, if gain < 0.003, or if path enumeration exceeds 4 hours on the full history (efficiency bound).

## 14. Improvement experiment
Beyond the paper: make the traversal *target-aware* instead of exhaustive. Score each joining path after depth-1 expansion by the mutual information of its cheapest aggregate with the residual of the baseline model, and only deepen paths in the top quartile (beam search over the entity graph, beam width 8). This attacks the paper's exponential-path weakness while keeping its relational semantics. Second: replace the paper's delete-on-drift with a regime-interaction feature — for each quarantined drifted feature f, emit f × 1[season ≥ drift_point] as a companion feature, letting the model learn the regime break explicitly. Hypothesis: preserves predictive signal the paper discards while containing the overfitting risk it correctly identified.
