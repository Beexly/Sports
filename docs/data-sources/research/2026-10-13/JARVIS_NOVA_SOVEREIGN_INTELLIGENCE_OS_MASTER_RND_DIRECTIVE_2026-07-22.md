# 3. Forensic review of JARVIS as it exists today

The repository already contains more JARVIS infrastructure than the high-level documents admit. It also contains material contradictions.

## 3.1 What is genuinely strong

The existing JARVIS design correctly treats JARVIS as a governed intelligence layer rather than a personality. It already separates:

- deterministic platform assessment;
- OwnerSummary;
- a decision queue;
- capability registry;
- council charters;
- memory concepts;
- owner approval;
- proof and caveats;
- “wired” from “designed”;
- claims from targets.

That is the right philosophical base.

The council is also useful when interpreted correctly: the seats are **roles and governance charters**, not 23 model processes that should all run and debate every task.

The repository already contains:

- deterministic question answering;
- a capability registry;
- agent and workflow registries;
- task types and routing;
- an episodic-memory schema and actions;
- decision-memory linking;
- memory-state transitions;
- a write gate;
- recall code;
- handoff and subagent ledgers;
- a capability/operational twin;
- source rights and public-claim gates;
- multiple audit-oriented data structures.

The correct strategy is to converge and elevate these assets, not replace them with another framework.

## 3.2 The documents are stale

The canonical JARVIS architecture says:

- 16 capabilities;
- 15 council seats;
- no memory store;
- REMEMBER not wired.

The current codebase has evolved beyond those counts and already contains PostgreSQL memory tables, transitions, write actions, recall code, and a database-aware memory status. The operator brief and fixed Ask JARVIS responses still repeat the older state.

Required action:

- create a deterministic JARVIS truth generator from code registries and migrations;
- generate or validate the architecture/operator documents from that truth;
- fail CI when counts, wiring state, or file maps drift;
- replace manually maintained numerical claims with generated receipts.

## 3.3 Ask JARVIS is still a menu, not an intelligence interface

Current Ask JARVIS is:

- 18 fixed intents;
- deterministic handlers;
- no free-form planning;
- no model synthesis;
- no broad world-model query;
- no causal or counterfactual reasoning.

That is valuable as a safe fallback and should remain.

It should become **JARVIS Safe Mode**, not the ceiling of JARVIS:


# 8. ARCHIVE Memory 2.0

Do not outsource canonical memory to a vector database or managed memory vendor.

Canonical memory remains in PostgreSQL as append-only evidence. Vector, graph, and file systems are indexes and retrieval layers.

## 8.1 Memory hierarchy

### Constitutional memory

Always visible, small, immutable/versioned:

- owner values;
- constitutional rules;
- current authority model;
- critical business definitions;
- hard safety and rights policies.

### Working memory

Run-scoped:

- current objective;
- plan;
- unresolved questions;
- active constraints;
- current tool outputs;
- task state.

### Episodic memory

What happened:

- run;
- action;
- observation;
- outcome;
- correction;
- incident;
- decision.

### Semantic memory

Source-backed facts and definitions:

- system behavior;
- business rules;
- domain concepts;
- data semantics;
- provider/program rules.

### Procedural memory

How to do things:

- tested workflows;
- runbooks;
- skills;
- recovery procedures;
- tool recipes;
- known prerequisites.

### Negative memory

What failed and why:

- recurring bugs;
- misleading approaches;
- rejected architecture;
- source gotchas;
- failed experiments;
- prompt-injection patterns;
- past overclaims.

### Preference memory

Owner/user preferences, explicitly scoped and revocable.

### Counterfactual memory

Alternatives considered and forecasts, later joined to outcomes.

## 8.2 Memory facts

Each memory assertion needs:

```ts
interface MemoryAssertion {
  id: string;
  memoryType: MemoryType;
  scope: string;
  subject: string;
  predicate: string;
  object: unknown;

  observedAt: string;
  recordedAt: string;
  effectiveFrom?: string;

  sensitivity: string;
  rightsStatus: string;

    | "CANDIDATE"
    | "CONFIRMED"
    | "CONFLICTED"
    | "STALE"
    | "SUPERSEDED"
    | "REJECTED"
    | "EXPIRED";

  supersedes?: string;
}
```

Do not mutate a fact to make history disappear. Append a superseding assertion.

## 8.3 Recall pipeline

```text
1. classify query and authority
2. determine required memory scopes
3. permission filter before retrieval
4. retrieve exact/structured facts
5. temporal graph retrieval
6. semantic and full-text retrieval
7. rerank by relevance, evidence, freshness, authority, and contradiction
8. diversify evidence
9. return compact evidence bundle
10. cite every memory in the answer
11. record recall event and whether it helped
```

Never inject every memory into context.

## 8.4 Temporal knowledge graph

Benchmark Graphiti/Zep patterns, but preserve Postgres truth.

The graph should represent changing relationships and historical intervals. It is particularly valuable for:

- provider/model availability;
- credits and expiration;
- organizational dependencies;
- project ownership;
- decisions and supersession;
- sources and terms;
- customer/revenue relationships;
- recurring incidents.

## 8.5 Consolidation

A nightly “sleep” cycle may:

- cluster duplicate memories;
- identify contradictions;
- mark staleness;
- propose semantic summaries;
- extract procedural candidates;
- identify repeated failure patterns;
- propose eval cases;
- recommend expiry or supersession.

It may not confirm, delete, or rewrite canonical memory silently.

## 8.6 Memory evaluation

Create GSE-specific tests modeled on long-term memory research:

- extraction;
- multi-session reasoning;
- temporal reasoning;
- updates and supersession;
- abstention;
- workflow knowledge;
- environment gotchas;
- premise awareness;
- permission boundaries;
- contradiction handling.

Measure:

- recall precision/recall;
- answer accuracy;
- citation accuracy;
- stale-memory use;
- unauthorized-memory leakage;
- token cost;
- latency;
- helpfulness compared with no memory.

# 10. Authority, identity, and the agent immune system

## 10.1 Agents as first-class principals

Evolve `TrustedActor` into:

```text
HumanPrincipal
ServicePrincipal
SystemPrincipal
AgentPrincipal
DelegatedAgentPrincipal
```

An agent is not the user. It receives a revocable delegation for a task.

Use an authorization model compatible with OpenFGA concepts:

```text
agent may act_on_behalf_of user
agent may execute capability
capability may operate_on resource
grant is scoped_to task/session
grant expires_at time
```

Pin an authorization-model version on every action.

## 10.2 Capability grants

```ts
interface CapabilityGrant {
  id: string;
  principalId: string;
  capability: string;
  taskId: string;
  resourceScope: readonly string[];
  toolScope: readonly string[];
  dataClasses: readonly DataClassification[];
  maximumCashUsd: number;
  maximumCreditUsd: number;
  maximumExternalActions: number;
  allowedActionClasses: readonly ActionClass[];
  expiresAt: string;
  revocable: true;
  issuedBy: TrustedActorRef;
  policyVersion: string;
}
```

No general “agent can use GitHub” grant. Grant:

```text
read repository X at commit Y
write only worktree Z
open draft PR against branch B
no merge
expires in 2 hours
```

## 10.3 Policy engine

Start with typed pure policy and conformance tests. Keep interfaces compatible with external policy engines.

Evaluate:

- OpenFGA for relationship/task delegation;
- OPA/Rego for contextual policy;
- SPIFFE/SPIRE only when workload topology justifies cryptographic service identity.

Do not add infrastructure merely to look enterprise-grade.

## 10.4 Prompt-injection defense

External content is tainted.

Required controls:

- source content and instructions stored separately;
- models are told that retrieved content cannot authorize tools;
- no secrets in research-agent contexts;
- tool capability determined before content retrieval;
- egress allowlists;
- destination binding;
- argument validation;
- human approval for sensitive calls;
- logged-out browsing where possible;
- sandboxed code;
- canary/honeytoken detection;
- attack corpus and automated red-team;
- no direct execution of discovered code;
- no automatic plugin installation;
- no source-provided command execution.

## 10.5 Tool design

Tools should be:

- narrow;
- namespaced;
- typed;
- token-efficient;
- explicit about read/write/destructive/idempotent behavior;
- permission-aware;
- evaluated with realistic agent tasks;
- limited to the smallest task-specific set.

NOVA’s three-candidate capability governor is a good starting policy.

# 11. The self-learning system

“Self-learning” must be decomposed. Otherwise it becomes marketing.

## 11.1 Learning levels

### L1 — factual learning

Store source-backed corrections and changed facts.

### L2 — episodic learning

Remember what happened and the outcome.

### L3 — procedural learning

Create a candidate runbook or skill from repeated successful traces.

### L4 — prompt/tool optimization

Use traces and evals to propose prompt, schema, or tool changes.

### L5 — code optimization

Generate candidate code changes in an isolated worktree and evaluate them.

### L6 — model adaptation

Fine-tuning, LoRA, RL, or local model specialization—only when:

- data rights are proven;
- a benchmark exists;
- economics justify it;
- safety and privacy are reviewed;
- the base model/license allows it.

No level silently promotes itself.

## 11.2 Correction-to-eval loop

Use the strongest practical pattern from current agent systems:

```text
owner/domain correction
→ structured CorrectionEvent
→ compare expected vs produced
→ cluster repeated failures
→ create LearningFinding
→ compile deterministic or rubric eval
→ add held-out cases
→ generate bounded improvement candidates
→ run in sandbox
→ independent grading
→ Pareto archive
→ shadow deployment
→ canary
→ promotion receipt
→ monitor outcome
```

## 11.3 Trace-to-skill compiler

A skill candidate must include:

```ts
interface SkillArtifact {
  id: string;
  version: string;
  objectiveClasses: readonly string[];
  prerequisites: readonly string[];
  inputSchema: string;
  steps: readonly SkillStep[];
  tools: readonly string[];
  authorityRequirements: readonly string[];
  failureModes: readonly string[];
  stopConditions: readonly string[];
  evidenceRequirements: readonly string[];
  rollback: string;
  sourceRunIds: readonly string[];
  evalSuiteId: string;
  status: "CANDIDATE" | "EVALUATED" | "APPROVED" | "DEPRECATED" | "REJECTED";
}
```

A successful trace does not automatically become a skill. It becomes evidence for a candidate.

## 11.4 Evolutionary Skill Foundry

Use ideas from AlphaEvolve, GEPA, Reflexion, and self-improving coding-agent research, but only inside a lab.

The Foundry maintains a **Pareto archive** of candidate:

- prompts;
- tool descriptions;
- context assemblies;
- workflow structures;
- retrieval policies;
- model routes;
- code changes;
- evaluation rubrics.

Candidates are selected across:

- correctness;
- safety;
- cost;
- latency;
- consistency;
- owner attention;
- maintainability;
- generalization.

Never optimize one reward alone.

## 11.5 Red Queen evaluator evolution

Evaluators can become stale or gameable.

Allow evaluator-change proposals only at epoch boundaries:

```text
fixed eval epoch
→ candidate improvements
→ adversarial analysis
→ evaluator gap proposal
→ owner/AUDIT review
→ new versioned eval epoch
```

The system may co-evolve evaluators and agents in the lab. Governance rules remain outside the evolutionary search.

## 11.6 Reflexion and negative memory

After a failure, capture:

- what was attempted;
- what assumption failed;
- observable evidence;
- the narrow correction;
- what should be checked next time;
- whether the failure is reusable across tasks.

This is a candidate negative memory and eval, not an unverified self-critique.

## 11.7 Agent training data

Every trace should carry:

- rights and privacy;
- consent;
- source provenance;
- retention;
- whether it may be used for retrieval;
- whether it may be used for eval;
- whether it may be used for training;
- whether it may leave the local environment.

No “we have data, therefore train on it.”

# 24. Research conclusions incorporated

The architecture above intentionally combines the strongest current patterns:

- OpenAI’s in-house data agent: layered context, human annotations, institutional knowledge, scoped memory, runtime validation, and pass-through permissions.
- OpenAI’s self-improving tax agent: practitioner correction → product trace → recurring finding → eval target → bounded coding improvement.
- OpenAI harness engineering and Symphony: repository legibility, isolated worktrees, objective-driven agents, agent-to-agent review, issue/task control plane, and human attention as the constrained resource.
- OpenAI and Anthropic agent-security work: prompt injection as social engineering, constrained authority, sandboxing, confirmations, transparency, and behavioral red-teaming.
- Anthropic’s tool and eval guidance: fewer clearer tools, realistic environment evaluations, held-out tests, pass@k/pass^k, and eval-driven development.
- LongMemEval and LongMemEval-V2: temporal updates, abstention, workflow knowledge, environment gotchas, and premise awareness.
- Zep/Graphiti, Letta, and Mem0: temporal graphs, context hierarchies, editable/shared memory, entity scoping, consolidation, and retrieval—used as patterns and benchmarks, not canonical authority.
- Restate, Temporal, and LangGraph: durable execution, state, interrupts, and recovery—behind a GSE-owned contract.
- OpenFGA, OPA, SPIFFE, MCP: first-class principals, delegated task-scoped authority, versioned policy, workload identity, and protected tool access.
- AlphaEvolve, Reflexion, DSPy/GEPA, Darwin/Huxley/Red Queen Gödel Machines, and Agent Lightning: evaluator-driven search, reflective feedback, diverse archives, evolving objectives, and training/execution separation—restricted to a sandboxed candidate-improvement lab.
- Inspect AI and Hugging Face/OpenEnv: provider-independent agent evaluation, external coding agents, sandboxing, local/open model training and evaluation.
