The Enforcement Ladder

Your operating prompt asks a model to remember 310 lines of rules. Six of those rules can be made unbreakable instead. This is the map of which mechanism does what — and where the current stack is quietly wrong.

Read 26 Aug 2026 Sources: academy.claude.com · code.claude.com · platform.claude.com Hooks tested, 12/12 pass

The one idea

Everything below follows from a single distinction the current prompt stack doesn't yet draw.

A rule written in CLAUDE.md or an operating prompt is guidance. It competes with every other line in the file for the model's attention, and the longer the file grows, the less reliably any single line lands. That is not a defect in the model; it is what a prompt is.

A rule written as a hook is code that runs before the action and can refuse it. And the property that makes this decisive for your setup: a PreToolUse hook fires before any permission-mode check, in every mode — including bypassPermissions. A hook that exits 2 blocks the call even under --dangerously-skip-permissions. Settings-level deny rules do not have that property against a bypass session; hooks do.

So the question for every rule in §5 of your operating prompt is not "is it stated clearly enough?" It is "which rung of the ladder is this rule on, and is it on the right one?"

0

Hooks can block

The only mechanism that enforces. Fires on lifecycle events, runs as code, returns a decision. Zero context cost — it isn't in the prompt at all. Everything you cannot afford to have ignored belongs here and nowhere else.

1

Permission rules can block

Evaluated deny → ask → allow, first match wins, specificity irrelevant. A broad deny cannot carry allowlist exceptions. Blocks in every mode except that allow rules go inert under bypass. Good for scoping; weaker than hooks as a guarantee.

2

CLAUDE.md guidance only

Loads every request, re-injected after every compaction. Target under 200 lines. Conventions and always-true facts live here. Hard rules do not.

3

Skills guidance only

Descriptions load at session start within a ~1% context budget; the body loads only on invocation — and then persists for the rest of the session. Reusable procedures belong here, which is where most of your §7.2 and §10 currently sit misfiled.

4

Subagents scoped tools

Separate context window, summary returns. Cannot block, but tools / disallowedTools / permissionMode hard-scope what one can touch. This is where "builder never verifies own work" becomes mechanical rather than aspirational.

5

Autonomy controls structural

/goal, worktrees, plan mode. These don't constrain behavior — they shape how long the seat runs unattended and whether two seats can collide. Worktrees make your multi-seat collision risk structurally impossible instead of procedurally discouraged.

Why this ordering matters for you specifically

NORTHSTAR names the real constraint precisely: not intelligence, not effort, but attention economics — the fleet's error detection works while its error prevention doesn't. Rungs 0 and 1 are prevention. Everything currently sitting on rung 2 that belongs on rung 0 is a rule you're paying attention to enforce, every session, forever.

Corrections to the current stack

Five findings where the existing prompt stack is wrong, half-right, or missing something that changes a decision. Stated plainly, including where your seat got it right.

--dangerously-skip-permissions rejection

Correct — and there's a better answer now

Your Sonnet seat rejected it, and rejected the source document's reasoning ("safe because we've already verified workspace contents") as a non-sequitur. That was right: content verification has nothing to do with permission safety.

The upgrade is that you no longer face a choice between autonomy and safety. Auto mode plus PreToolUse hooks gives you both — the classifier reviews each action, and your hooks block the sealed paths regardless of mode. That's strictly more autonomy than the current default with strictly more enforcement than the prose rules provide. The guidance for unattended runs is explicit: keep them in auto mode, not bypass, because the classifier stays active — while noting it "never judges whether the code is actually correct."

--bare rejection

Half right — the reasoning conflates two things

The document says --bare would skip "the pre-commit secret scan, the stop-hook git check, and the sealed-path guards." Two of those three are Claude Code hooks and would indeed be skipped. But a git pre-commit hook in .githooks/ is run by git, not by Claude Code — --bare doesn't touch it. Git runs it whenever a commit happens, from any client.

The conclusion still holds for interactive dev sessions, so the rule can stay. But the reason should be corrected, because the docs now say --bare is recommended for scripted and SDK calls and will become the default for -p in a future release. A rule justified by a mistaken mechanism will break confusingly when that default lands.

There's also a sharper security fact underneath: without --bare, a -p session runs hooks from a project's settings and connects .mcp.json servers even in a folder never trusted, with no dialog. For a repo carrying many agent-authored config files, that is worth knowing in both directions.

Seat switching costs more than anyone has priced

Not currently in the stack

The fleet switches models by design — Fable for judgment moments, Sonnet for the workhorse, Hermes on free tiers. Here is the part nobody has costed: the model and the effort level are part of the prompt-cache key. Switching either mid-session recomputes the entire request from scratch, at full input price rather than the 0.1× cache-read rate.

Fable's own doctrine is "on → decide → off," which is the right instinct. This gives it a number: every on/off cycle inside a live session pays for a full context rebuild twice. Batch the judgment moments; don't interleave them.

Two related economics worth having: /rewind truncates to an already-cached prefix and is therefore cheaper than /compact for abandoning a bad path — compaction reads the whole conversation to summarize it. And resuming a long session after a Claude Code upgrade busts the cache, making "the first turn back into a long session the most expensive request you send."

Project skills grant tools even in untrusted runs

Security-relevant, not in the stack

Workspace trust gates a project's permissions.allow rules — but it does not gate a skill's allowed-tools frontmatter. A project skill's tool grant applies even in a -p run in an untrusted folder.

For most repos this is a footnote. For one where multiple agent seats author config files into .claude/ across 400+ branches, it means a skill file is a capability grant that bypasses the trust prompt. Worth adding .claude/skills/ to whatever review gate already covers .claude/ in your never-modify list — which the sealed-path hook in the kit now enforces.

The Academy corpus dependency

Partially resolvable now

§9 routes to docs/CLAUDE-ACADEMY-PLAYBOOK.md, a 755-page index whose full texts live only at C:\Users\Garrett\academy-corpus\. The instruction to degrade to titles-only and never invent contents is exactly right and should stay.

Cache mechanics worth knowing exactly

Order is immutable: tools → system → messages, matched on exact prefix. A change anywhere invalidates everything after it. Cache writes happen only at breakpoints — the 20-block lookback finds entries prior requests already wrote, it does not retroactively cache stable content sitting behind your breakpoint.

Read is 0.1× base input. A 5-minute write is 1.25× and pays for itself after one read; a 1-hour write is 2.0× and pays for itself after two. Below the model's minimum cacheable size nothing caches and no error is returned — verify with cache_creation_input_tokens and cache_read_input_tokens rather than assuming.

The CI-minutes situation has a cheaper answer than waiting for the pool

Actions minutes are exhausted and §6 correctly makes the local verify block the gate. The kit's Stop hook goes further: it runs typecheck, check:ledger, and agent:eval on every turn end and refuses to let the turn close while they're red — with the failure fed straight back so the seat fixes it unprompted. Build and guardrails stay out of it deliberately, because a Stop hook you notice is a Stop hook you'll disable.

Autonomy without loosening anything

Three mechanisms that raise how much a seat can do unattended, none of which require relaxing a guardrail.

Worktrees — the collision fix

Right now, two seats working simultaneously are kept apart by ledger discipline alone: claim before work, never edit rows you don't own. That's procedure. Worktrees make it structural — each session gets an independent file tree, and the isolation is enforced by four checks that block edits, shell commands, and git redirects back into the main checkout, for the session and every subagent it spawns.

claude --worktree c75-wave        # named worktree, own branch
claude --worktree "#672"          # branch from an existing PR

A .worktreeinclude at the repo root copies gitignored files (env, local config) into each new tree — only files that match a pattern and are gitignored, so tracked files are never duplicated. Or set it permanently per-agent:

---
name: refactorer
description: Applies mechanical refactors across many files
isolation: worktree
---

One caveat that matters: a -p run has no exit prompt, so its worktree is never auto-cleaned. And ${CLAUDE_PROJECT_DIR} keeps pointing at the original root after entering a worktree — the worktree path arrives as the cwd field in the hook's input JSON instead.

/goal — a completion condition, not a prompt

Sets an end state and keeps working across turns until a fast evaluator confirms it. This fits the C-75 wave and the acceptance-harness work directly, because both have checkable end states:

/goal the falsifier acceptance harness passes planted-edge, pure-noise,
      and inverted cases at n in {100, 1000, 5000}, and npm run
      check:ledger exits 0 — or stop after 20 turns

The binding constraint: the evaluator only reads the transcript. It does not run commands or read files independently, so the condition has to be something the seat's own output can demonstrate. Bound it inside the condition itself — the "or stop after 20 turns" clause above is the documented pattern. A goal does not change permission mode; run it in auto mode for unattended turns.

Plan mode with context discharge

Standard advice is to plan before executing and actually read the plan. The under-used part: with showClearContextOnPlanAccept enabled, the approval menu gains an option that approves the plan and clears the planning context — so implementation starts without carrying the exploration transcript. On a codebase this size, that exploration is often the larger half of the context.

Prompt doctrine, with the numbers

The techniques that measurably move output quality, and the two that have quietly changed underneath most existing runbooks.

Specificity is the largest single lever. Anthropic's own eval on one running example: a vague request scored 2.32/10. Rewritten to be clear and direct — naming the action, deliverable, timeframe, audience, and constraints — it scored 3.92. Adding output-quality guidelines on top ("list all portion sizes in grams," not "be detailed") took it to 7.86. The tell for a good guideline is that it names an artifact which either appears in the output or doesn't.

Put long data above the question. Queries placed at the end, after the documents, improved response quality by up to 30% on complex multi-document inputs. Every prompt in the business library follows this shape.

Force reasoning before any score. A grader asked for a bare 1–10 regresses to the middle — "models tend to default to middling scores around 6." Demand strengths, weaknesses, and reasoning first, then the number, then discard the reasoning if you don't need it. This is why your falsifier's verdict vocabulary works and a confidence score wouldn't.

Two things that changed under existing runbooks

Prefilling the assistant turn is gone. On Claude 4.6+ a prefilled final assistant message returns a 400 error. Anything forcing JSON with a prefilled { needs to move to structured outputs or an explicit format instruction.

"Think hard" language now backfires. Aggressive thinking prompts were written for models that under-triggered. Current models with adaptive thinking over-trigger on them. Same for tool prompts — "CRITICAL: MUST use tool" should become "Use this tool when…". Note also that ultrathink adds an in-context instruction for that turn without changing the effort sent to the API; "think", "think hard", and "think more" are not recognized keywords at all.

Skill authoring traps worth knowing before writing any

Descriptions are budgeted and truncated. The skill listing gets ~1% of the context window; when it overflows, descriptions are dropped starting with least-invoked skills. Per-entry, description plus when_to_use is capped at 1,536 characters. Put the key use case first — the tail is what gets cut.

Invoked content persists for the whole session and is not re-read on later turns. Write standing instructions, not one-time steps. After auto-compaction, only the most recent invocation of each skill is re-attached, first 5,000 tokens each, 25,000 total.

$0 is the first argument, not $1. Indexed skill arguments are zero-based.

A failed !-injected command aborts the entire invocation — Claude never sees the content. Append || true to anything expected to exit non-zero.

Portability: outside Claude Code, only six frontmatter fields are legal. An extra field is a hard error, not an ignored one.

Uncertainty ledger

What isn't confirmed. Written here rather than omitted, because a document about honesty laws that quietly smooths over its own gaps would be self-refuting.

  • Two hook output shapes conflict across sources. For PostToolUse and Stop, the guide prose puts decision/reason at the top level while reference code blocks nest them under hookSpecificOutput. The kit's Stop hook uses exit 2 with stderr, which is unambiguous in both readings — so this conflict doesn't affect anything shipped. Verify empirically before relying on the JSON form.
  • escalate as a permissionDecision value is unverified. allow/deny/ask/defer are solid across three sources; one reference lists escalate as a synonym for ask. Nothing shipped depends on it.
  • promptCacheTtl in settings is version-gated (v2.1.242+) and unverified against your installed build. If it errors, remove the key — the subscription default is already 1h for the main conversation.
  • The /cost command could not be confirmed to still exist. Current docs show /usage, /usage-credits, and /insights. If a runbook references /cost, check it.
  • /output-style was removed in v2.1.91. Use /config or the outputStyle setting. Any runbook calling the old command is broken.
  • Subdirectory namespacing for .claude/commands/ is no longer documented. The old frontend/component.md → /frontend:component behavior may or may not survive; directory-qualified names are documented only for nested skills dirs.
  • All docs moved hosts. docs.claude.com/en/docs/claude-code/* now redirects to code.claude.com/docs/en/*, and prompt-engineering pages to platform.claude.com. Any stored URL in the repo's playbook index is stale.

Separately, and worth saying directly: the hooks in the kit were tested against synthetic input in an isolated clone, not against your actual repo with your actual npm scripts. The Stop hook in particular assumes npm run typecheck, check:ledger, and agent:eval exist and behave as §7.3 describes. Run it once interactively before trusting it to gate an unattended session.
