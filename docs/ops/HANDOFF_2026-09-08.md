## 1. The launch call

**Postpone.** Not on polish. On the premise. Three findings, each independently

### 1a. The board did not rank on edge. This is now FIXED in code.

The strategy doctrine (`_HANDOFF-to-coding-agent.md`, intel repo) names one rule above all
others: fire and rank on `e = p - q`, never on confidence, because confidence-gating is
"scores24's fatal error." Measured at the start of this session: the live plan set
`selectiveRecommended.edge = null`, so public selection was `|p - 0.5| >= 0.12`, and **387
of 428 published moneyline picks carried no market probability at all**, so `rawEdge` on
those rows was literally `trueProb - 0.5`.

It was never a data problem. **232 of those 387 had a real bookmaker quoting both sides in
our own `odds` table at or before the pick's own `generatedAt`.** The signal slate never
looked. C-253 wired the same resolver the calibration loader uses into the publish path;
measured ceiling on the moneyline board goes from 41/428 to 273/428.

**Still open and founder-gated:** the tuner and the runtime resolve `marketP` from
different places. The sweep uses `independentEdge.marketFairProb ?? factorBreakdown.marketFairProb ?? receipt.marketFairProb`;
`/api/picks/route.ts` reads only the top-level `factorBreakdown.marketFairProb`, present on
48 of 435. A threshold tuned on one population would be enforced on another. It is a no-op
while `edge` is null, which is why it was left.

### 1b. The settled record is contradicted by the feed it came from. Founder-owned.

C-247: 25/169 MLB, 14/48 MLS, 2/37 NCAAF stored FINAL scores disagree with ESPN's own API;
68 settled published picks sit on them; 8 moneyline results are the opposite of what
happened. Every calibration number in the repo is a measurement over those inputs.

**There is now a command for it** (C-254/C-256): `npm run ops:repair-scores`. Dry run by
default. `--execute` applies it one transaction per game. Writes exactly four fields, and a
test enforces that by scanning every Prisma `data:` block. Re-grades through the engine's
own `calculatePickResult` and `selectGradingLine`. Refuses a game whose settled picks
cannot all be re-graded, and refuses to run at all while a write-once
`PickSignalSnapshot.settlementResult` or `PickSettlementEvent.result` would be left
contradicting a corrected result, unless the operator passes
`--accept-stale-derivatives`. **Not run against production in this session.**

### 1c. Our own bake-off names the market as the best score we produce.

`/api/ops/public-surface-truth` carries `"bestScore": "marketFairProb"`. The market's
de-vigged probability beats every score we generate on Brier (0.2337 vs our best 0.2474),
ECE (0.0280 vs 0.0838) and **Murphy resolution** (0.0185 vs 0.0112). Resolution is ranking
power. On moneylines the confidence score's separation is **-0.0018** at n 745.

Two confounds recorded rather than buried: the scores are not on an identical row set
(market coverage 0.774 vs confidence 1.000), so the *size* of the gap is not established;
and the outcomes are the C-247 record. Neither rescues the finding.

**The measurement nobody has run, and the next session should:** put all four scores on an
identical row set and re-read the gap.

### 1d. Two paid API surfaces returned invented numbers. FIXED in code (C-259).

Found by the ten-dimension audit and re-verified by hand against the source, because that
audit's own verify stage died on a usage limit. This outranked every other finding on the
branch, the coin-flip edge included: that was a real computation with honest copy beside it.
This was a made-up number wearing a provenance badge.

`GET /api/gse/v1/values/:metricId` routed every ACTIVE public metric with no wired loader to
a `demo` provider that derived a value from a character-code hash of the string
`"<metricId>:<entityId>"` mod 10000, and returned it 200 inside
`provenance: { sourceIds, rights, pitCorrect: true }` — a machine-readable claim that the
number came from the sources the metric names, `odds.the_odds_api` among them, served behind
a session-tier check to paying subscribers. A `_note` in the route said "demo/memory
provider", which contradicts the provenance block one field away rather than qualifying it,
and no machine reads prose.

`POST /api/gse/v1/own/values` seeded its store with `own.model.p` 0.58, `own.model.p_lo`
0.54, `own.model.width` 0.08 and `own.quote.q` 0.51 for `nfl:kc` and `nfl:phi`, stamped
`first_party` / `gse.own` / `pitCorrect: true`, with `asOf` computed as now minus two hours
on every process start so the data always looked fresh — invented model outputs presented as
ours, on a route whose only check is an 8/min IP rate limit.

In both cases the honest refusal was already written and merely unreachable, so the fix
deletes the fabrication rather than adding a path. Full evidence, including what is NOT
established: `docs/ops/FABRICATED_API_VALUES_2026-09-08.md`.

**Two things were deliberately left open there, and they are the follow-on work:**

- `own/values` has **no entitlement check** — a rate limit, a JSON parse, then the handler.
  With an empty store it leaks nothing today, so this is not urgent, but gating a public B2B
  surface needs a decision about who that endpoint is for before a gate can be picked.
- `pitCorrect: true` is **hardcoded** in the provenance block. It is now only ever stamped on
  a value a wired loader actually returned, but it is still the handler asserting something
  no provider told it. Making loaders report their own PIT correctness is a contract change
  across all of them.

## 3. What the research changed

### 3a. The optimizer gap is an input and two layers, not a rewrite

SaberSim's CEO, on their own site: *"for every lineup we build you, we randomly choose a
bucket of sims and optimize based on the average score for each player in that bucket."*
That is a **deterministic point-projection solve, the same shape as ours**, run many times
against vectors drawn from a 100,000-run simulation. Our exact DP kernel is right. What we
lack: a sims-by-players score matrix, a contest-field simulator, a portfolio selector.

### 3b. Their pricing is the category's product boundary

Starter $97 (**500 lineups per build**), Pro $197 (5,000), Ultimate $297 (contest-specific
sims and the ROI suite). Their own help centre: *"you'll need Ultimate to access detailed,
contest-specific simulations."* **Our Pro tier is $14.99. The category floor is $97.**

### 3c. The seam is wide and structural

For a product whose pitch is "we compute your ROI 100,000 times," SaberSim publishes zero
projection accuracy, zero calibration, zero aggregate ROI. What they publish is 2,084
winner screenshots totalling $38.56M, concentrated in 746 unique names with one holding 31
cards, and **no "results not typical" disclaimer anywhere in the HTML**. Their own FAQ:
*"Why do my lineups look different every time I build? Each build samples a new set of
simulations."* **Their product cannot reproduce its own output.** Ours is documented as
"no randomness, no local search, no restarts." Seed the sim draw, store the seed, publish
it with the lineup, and a GSE lineup is re-derivable by a third party. Nobody in the
category ships that.

## 5. THE RECURRING DEFECT CLASS — read this before writing any code here

**A count, label, badge or flag whose stated meaning is not what it measures.**

C-241, C-246, C-250, C-251, C-252, and twice inside C-255. C-250 was committed *inside the
instrument built to detect the class*. C-255 fixed a counter that over-counted, in the
counter added to measure the fix for the class.

**Assume more exist.** Red-check every guard you write: mutate the fix, confirm the test
fails, restore. Every fix in this session was red-checked and the counts are in the commit
messages. When a guard fires too broadly, **narrow its context, never its power** (law 9);
C-254 and C-255 each have a worked example of doing exactly that.
