## 6. Traps

- **Path trap**: the work lives in `C:\Users\Garrett\Sports`, **not** `C:\Users\Garrett`. A bare
  `cd ~` + `ls docs/...` will show an unrelated `arxiv-program` tree and look like nothing landed.
- **Shell trap**: `terminal` runs bash (git-bash/MSYS) on this Windows host — POSIX syntax only. MSYS
  path translation is disabled for native programs, so pass `C:/Users/...` forward-slash paths to
  git/python/node. Use `$TMPDIR`, never a bare `/tmp`.
- **Repo hygiene**: there is a large amount of **untracked cruft** in this repo (`AppData/`,
  `_tmp_wiring*.json`, `bot.py`, `_tmp_barrel.json`, `docs/arxiv-program/research/2026-10-13/` with
  ~40 PDFs and .docx files). Never `git add -A` — stage explicit paths only. The secret-scan runs on
  commit and on push; both passed clean as of `8683bfa30`.
- **Stale docs**: the delegate's ops doc contained a confidently-wrong conclusion (§3b). Verify claims
  against the raw payloads before repeating them in new docs.
- **"PASSING" trap — a green count over a refused board.** Section 5's `games_requested == cards_emitted
  == ranked == 14` and `gaps == []` are satisfied by a board on which **all 14 cards were INVALID and
  withheld**. A card-count test cannot distinguish a reasoned slate from a wholly-refused one. This is
  how the wrong "Section 5 PASSING" heading got written and survived several commits. **Assert on the
  product (`pick is not None`, `trace_label`), not on the count.**
- **`trust=None` trap — an UNCHECKED track masquerading as a data gap.** The 14/14 INVALID board is
  triggered by *one* argument: `run_game.py:308` passes `trust=None`, which `api.py:335` converts to
  `trust_signals = "UNCHECKED"`, which the L5 gate rejects on. It looks like "the trust data is
  missing" but it is really "the provider was never passed" — a wiring bug, not a data gap. **And the
  naive fix is itself a trap:** wiring the provider against an *empty* intake store reports
  `trust_signals = "CLEAR"` ("intake swept, nothing material") and flips cards to **FINAL** on no data.
  Measured this session: `trust=None -> UNCHECKED -> ChecklistInvalid` vs
  `trust=FileStore(empty) -> CLEAR -> L5/FINAL`. Do not "fix" the UNCHECKED by silencing it.
- **Depth mis-stamp trap — INVALID cards report `L1` when they were refused at `L5`.** `api.py:557`
  builds the INVALID trace with `req.requested_depth`, so `trace_depth: L1, levels: []` on an INVALID
  card means "requested L1 and the deep run was refused", **not** "the analysis was shallow". Reading
  the depth field as analysis depth will mislead you in exactly the way "PASSING" misled this session.
- **Meaning-not-transport trap** (generalises): Action Network returned HTTP 200 with the right byte and
  game counts while labelling DraftKings as Caesars. The transport verified; the *meaning* did not. Any
  live check that asserts shape but not semantics can pass forever while being wrong.
- **`| tail` masks the exit code — a traceback reads as a success.** Nearly every check command in this
  repo is written `python ... 2>&1 | tail -N`. The pipeline's exit status is **`tail`'s, not python's**,
  so a `ModuleNotFoundError` scrolls past and the run is reported "exit code 0". Verified this session:
  `python -c "raise SystemExit(3)" 2>&1 | tail -2` → `$?` = **0**, `${PIPESTATUS[0]}` = **3**. This is the

  `set -o pipefail`, or read `${PIPESTATUS[0]}`, or drop the pipe.** A batch summary that says "exit code
  0" for a command ending in `| tail` has told you nothing about the command.
- **A redaction token in a listing is a transcript artifact, not a filename bug.** The per-game cards are named
