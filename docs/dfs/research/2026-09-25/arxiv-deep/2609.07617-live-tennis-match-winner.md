# Ledger: 2609.07617 — "Forecasting the Winner of a Live Tennis Match" (cs.LG)

**VERDICT: ADAPT** — The tennis domain does not transfer, but the live-updating recipe does: Bayesian pseudo-count shrinkage of in-game rates toward pre-game priors, plus a gradient-boosting meta-learner stacked over structural-model probabilities in both probability and logit space, selected and evaluated on strictly chronological splits with log loss and calibration curves. That recipe ports directly to GSE's live NFL win-probability and calibration stack.

## 1. Research question

How should pre-match information (player strength) and live in-match information (score state, observed serve performance) be integrated to produce accurate, well-calibrated live win-probability estimates as a tennis match unfolds? The paper compares five approaches — score-structure-only, pre-match-strength-adjusted, live-shrinkage-updated, pure machine learning, and a hybrid ("Trace") — under one chronological evaluation, and asks which information source adds value at which stage of a match.

## 2. Dataset/schema

- Source: Jeff Sackmann's Grand Slam point-by-point data combined with ATP/WTA match results (used to build pre-match Elo ratings).
- After cleaning: **8,222 matches, 1,505,355 point-level prediction states** (each row = match state *before* a point is played; the eventual winner is stored in a separate target column so each prediction uses only information available at that point).
- Split (chronological): training 2011–2021 (6,774 matches / 1,238,084 states); validation 2022 (473 / 87,439); testing 2023–2024 (975 / 179,832).
- Filtering (21.8% of raw matches excluded, 2,286): kept only matches with a valid non-tied final set score, winner completing 2 or 3 sets, >20 points recorded, and server/point-winner identified as player 1 or 2. Walkovers etc. removed.
- Elo matched to 96.0% of prepared matches (7,896 of 8,222).
- Point scores numerically encoded: 0→0, 15→1, 30→2, 40→3, AD (advantage)→4, because the Markov recursion cannot consume labels.

## 3. Method/model

Five models, evaluated at fixed match-progress checkpoints (25%, 50%, 75% of points played) and across all points:

1. **Symmetric Markov baseline**: both players treated as equally strong (pa = pb = p); win probability comes only from score structure via the Markov recursion. Isolates the predictive value of tennis scoring.
2. **Elo-asymmetric Markov**: pre-match Elo difference converted to a serve-probability edge added to a tour-average baseline serve probability (β), clipped to realistic bounds. Fixes the 50/50 default when players differ in strength.
3. **Serve-shrink Markov**: starts from the Elo-based prior serve probabilities and updates them mid-match with observed in-match serve-point win rates via Bayesian shrinkage (pseudo-count κ): early in the match the prior dominates; as serve points accumulate, weight shifts to the live rate. The shrunk rates feed the same Markov recursion.
4. **HGBM baseline** (scikit-learn HistGradientBoostingClassifier): learns player-1 win probability directly from score/live features, no Markov structure. XGBoost and LightGBM were also tried; HGBM had the lowest validation log loss.
5. **Trace** (the paper's contribution): a hybrid. Feature vector = [Elo-asymmetric Markov prob, serve-shrink Markov prob, logit of each, their difference, plus the live score/state features z(s)], passed through a histogram gradient-boosting classifier producing the final win probability.

Elo ratings: every player starts at 1500; updated chronologically after each match with K-factor decaying in matches played (mirroring Kovalchik); each player's rating is recorded *before* the current match's outcome.

## 4. Equations & assumptions

(Copied faithfully from the text. Note: pdftotext scrambled the physical placement of a few equation numbers relative to their equations; content below matches the text. The deuce equation's numerator/denominator were split across two fragments in extraction — the closed form shown is the standard one the fragments compose.)

**Elo expected win probability** (Eq. 1):
qi,t = 1 / (1 + 10^((Rj,t − Ri,t)/400)), where Ri,t, Rj,t are ratings immediately before the match.

**Elo update** (Eq. 2):
Ri,t+1 = Ri,t + Ki,t (Si,t − qi,t), with Ki,t = 250 / (mi,t + 5)^0.4, Si,t ∈ {0,1} the match result, mi,t = matches player i completed beforehand.

**Next-point win probability** (Eq. 3):
q = p1 when player 1 serves; q = 1 − p2 when player 2 serves.

**Match state** (Eq. 4):
s = (S1, S2, G1, G2, P1, P2, σ, τ, b) — sets, games, encoded point scores, server identity σ, tiebreak flag τ, best-of format b.

**Markov recursion** (Eq. 5):
V(s) = q(s)·V(T1(s)) + (1 − q(s))·V(T2(s)), where T1(s), T2(s) are the states after player 1 / player 2 wins the next point.

**Terminal conditions** (Eq. 6):
V(s) = 1 if S1 = m(b); 0 if S2 = m(b), where m(b) = ⌈b/2⌉ sets needed to win.

**Tiebreak**: same recursion; server follows sequence 1, 2, 2, 1, 1, 2, 2, …

**Deuce**: D(q) = q² / (q² + (1−q)²) — player 1's game-win probability from deuce (fragments "D(q) =" and "q² + (1 − q)²" appear adjacent to Eq. 10 in the extraction).

**Symmetric baseline** (Eq. 9): pa = pb = p.

**Elo-asymmetric**: d = Elo1 − Elo2; e = clip(α·d, −0.15, 0.15); pa = clip(β + e, 0.45, 0.88) (Eq. 12); pb = clip(β − e, 0.45, 0.88) (Eq. 13), β = tour-average baseline serve probability.

**Serve-shrink** (Eq. 14, Bayesian shrinkage per Colin & Bechler):
θ̂ = [n/(n+κ)]·θ̂live + [κ/(n+κ)]·θprior, i.e. pa = (n1·r1 + κ·π1)/(n1 + κ); pb = (n2·r2 + κ·π2)/(n2 + κ) (Eq. 15),
where π1, π2 = Elo-based prior serve-point win probs, r1, r2 = observed in-match serve rates, n1, n2 = serve points observed, κ = prior pseudo-count controlling shrinkage strength.

**HGBM baseline** (Eq. 16): p̂H = gφ(z).

**Trace feature vector** (Eq. 17):
x(s) = [p̂M(s), p̂S(s), logit(p̂M(s)), logit(p̂S(s)), p̂S(s) − p̂M(s), z(s)]ᵀ,
with logit(p) = log(p/(1−p)) (Eq. 18); p̂Trace(s) = fθ(x(s)) (Eq. 19), fθ = HGBM.

**Log loss** (Eq. 20): L = −(1/N)·Σᵢ [yi·log(pi) + (1−yi)·log(1−pi)].

**Calibration bins** (Eqs. 21–22): Predk = (1/|Bk|)·Σᵢ∈Bk pi; Obsk = (1/|Bk|)·Σᵢ∈Bk yi; perfect calibration ⟺ Obsk = Predk per bin.

**Key assumptions**: point outcomes conditionally independent given (server, serve-point win prob); serve probabilities fully summarize player strength differential for the recursion; Elo difference maps linearly (slope α) into serve-probability edge; shrinkage weight depends only on sample size n, not on score leverage or recency; Grand Slam matches representative.

## 5. Features/target

Target: y ∈ {0,1} = eventual match winner (player 1), stored separately, predicted from pre-point state only.

Feature groups (paper's Table 3):
- **Score state**: best_of, p1_sets, p2_sets, p1_games, p2_games, p1_score, p2_score, p1_serving, tiebreak.
- **Live serve performance**: p1_serve_rate, p2_serve_rate, p1_serve_n, p2_serve_n (observed in-match serve-point win rates + sample sizes, computed from completed points only).
- **Rally and ace context**: rally_avg, recent_rally_avg, p1_ace_rate, p2_ace_rate (from previously completed points where available).
- **Derived state summaries** (player-1 perspective): sets_diff, games_diff, score_diff, pts_played.
- **Meta features (Trace only)**: p̂M(s), p̂S(s), their logits, and p̂S(s) − p̂M(s).
- **Pre-match**: Elo1, Elo2 (surface-agnostic career-history Elo).

## 6. Validation design

- Strictly chronological: train 2011–2021 → validation 2022 (hyperparameter tuning, all model selection by **validation log loss**) → test 2023–2024. No shuffling; mirrors real-time deployment.
- Hyperparameter grids: symmetric p ∈ {0.60,…,0.65}; Elo-asymmetric β ∈ 0.59–0.65 (step 0.01), α ∈ {4,6,9,13,18,22}×10⁻⁵; serve-shrink κ ∈ {40,80,160,320,640}; HGBM baseline 4 configs over (learning rate, max iterations, max leaf nodes, L2) with log loss and early stopping disabled, random_state=42; Trace HGBM 4 configs over (learning rate, max leaf nodes, L2), max 250 boosting iterations, early stopping enabled. Selected configs refit on train+validation, then tested.
- Selected values were tuned **separately at each checkpoint**: symmetric p = 0.65/0.64/0.60 at 25/50/75%; (β,α) = (0.64, 1.3×10⁻⁴) at 25%, (0.59, 1.3×10⁻⁴) at 50% and 75%; κ = 640/160/40 at 25/50/75%. Trace HGBM random states 19, 30, 6 per checkpoint.
- Metrics: accuracy at checkpoints and across all points; log loss at checkpoints; reliability (calibration) curves for Trace; tour-split (ATP/WTA) accuracy curves.
- Comparison to DeepTennis (LSTM, 79.5% overall) under a deliberately non-chronological 2011–2019 split to match its setup — flagged by the authors as leakage-prone.

## 7. Numerical results/baselines

Quoted exactly as stated:

**Table 4 — accuracy at 25% / 50% / 75% match progress and across all points:**
- Symmetric Markov: 0.6851 / 0.7703 / 0.8544 / 73.21%
- Elo-asymmetric Markov: 0.7575 / 0.8050 / 0.8648 / 77.56%
- Serve-shrink Markov: 0.7564 / 0.7946 / 0.8720 / 77.68%
- HGBM: 0.6944 / 0.7918 / 0.8738 / 73.98%
- Trace: **0.7606 / 0.8215 / 0.8834 / 77.84%** (highest in every column; abstract reports 76.06%, 82.15%, 88.34% at 25/50/75%)

**Table 5 — log loss at 25% / 50% / 75%:**
- Symmetric Markov: 0.6292 / 0.5363 / 0.3498
- Elo-asymmetric Markov: 0.5210 / 0.4549 / 0.3096
- Serve-shrink Markov: 0.5142 / 0.4266 / 0.2842
- HGBM: 0.5376 / 0.3788 / 0.2299
- Trace: **0.4753 / 0.3530 / 0.2002** (lowest at all checkpoints)

**Trajectories worth noting**: the HGBM baseline is *worse than the symmetric baseline* early (0.6944 vs 0.6851 at 25%) but beats every Markov model on log loss at 50% (0.3788) and 75% (0.2299) — live features dominate structure late. Serve-shrink barely moves accuracy over Elo-asymmetric (77.68% vs 77.56% all-points) but consistently wins on log loss — it improves probability *quality*, not the argmax. Trace's largest accuracy edge is mid-match (~40–70% progress). WTA curves fluctuate more sharply than ATP (authors attribute to lower hold rates: ~79% men vs ~66% women service holds cited).

**DeepTennis comparison** (non-chronological 2011–2019 split, Table 6): DeepTennis reported 79.5% overall and 73.2%/84.9%/89.2% at 25/50/75%; under the same split Trace reaches 81.30% across all points (77.66%/83.84%/88.96% at checkpoints). Authors stress this comparison split permits leakage and is only contextual.

**Calibration**: Trace's reliability diagram "reasonably well calibrated, especially at 25% and 50% match progress."

## 9. Leakage & limitations

Adversarial reading:

1. **Correlated rows, inflated headline**: 1.5M "point states" share only 8,222 outcome labels — every point of a match carries the same y. "77.84% across all points" is dominated by late-match points that are near-deterministic; it is not 1.5M independent predictions. The checkpoint numbers are the honest metric.
2. **Ex-post progress framing**: "25% match progress" requires knowing the match's total point count — knowable only after the match ends. The evaluation point is selected with future information (features at that point are pre-point, so no feature leakage, but the frame is not deployable as-is for a live system).
3. **Three models wearing one name**: "Trace" is really three separately-tuned models — different HGBM configs, different random states (19/30/6), different κ (640/160/40), β, α per checkpoint. A deployed system needs one model or an explicit progress-conditioned architecture.
4. **Single small validation year**: all hyperparameters (including the per-checkpoint grids) were selected on 2022 — 473 matches. The symmetric baseline's p = 0.65 → 0.64 → 0.60 across checkpoints smells like noise-fitting; κ collapsing 640 → 160 → 40 likewise.
5. **No uncertainty quantification**: Trace 77.84% vs serve-shrink 77.68% all-points is a 0.16pp gap on 975 test matches — no CIs, no significance tests anywhere. Most pairwise accuracy gaps are plausibly noise; the log-loss gaps are the real signal.
6. **Accuracy is the wrong headline for a probability model**; the authors know it (log loss + calibration included) but still lead with accuracy.
7. **Unexplained 4%**: Elo matched to 96.0% of matches — the paper never states how the unmatched 4% were handled in Elo-dependent models (dropped? default 1500?).
8. **Survivorship filtering**: requiring >20 recorded points and complete server/winner fields drops retirements and badly-recorded matches — exactly the matches where live models are most valuable and most wrong.
9. **Serve-only worldview**: no return features, no surface-specific Elo (author-admitted), no fatigue/injury/weather/handedness/style. Elo is surface-agnostic despite clay/hard/grass being first-order in tennis.
10. **Grand Slams only** (author-admitted): best-of-5 men / premier events; generalization to tour-level best-of-3 untested.
11. **The "ensemble" is mostly feature-stacking**: logit(p̂M), logit(p̂S), p̂S−p̂M are deterministic transforms of two scalars — the meta-learner's real degrees of freedom are the two Markov outputs plus z(s). The HGBM-alone log-loss wins at 50/75% suggest the stacking adds little beyond the live features late.
12. **DeepTennis comparison is confessed leakage** (non-chronological split, test year inside training range) — reported anyway as "contextual."
13. **Authorship caveat**: high-school student project with a mentor; competent execution and honest limitation discussion, but single-author-tuned, no ablation of the clipping bounds (±0.15 edge clip, [0.45, 0.88] probability clip are ad hoc), no sensitivity analysis on the Elo K-factor schedule.
14. **WTA fluctuation explanation untested**: authors attribute sharper WTA swings to lower hold rates but state "this study does not test in depth whether this correlation is sufficient" — honest, but then it shouldn't carry explanatory weight.

Net: methodology is leakage-clean on the core chronological claim (features strictly pre-point, Elo strictly pre-match), but the headline accuracy number is structurally inflated and the per-checkpoint tuning is overfit-friendly.

## 10. GSE overlap

Honesty note: I have **not** read the contents of the listed engine modules — the overlaps below are architectural (by module name and purpose), not verified against code. Relevant modules per the task: `packages/prediction-engine/src/{calibration-ladder, multi-market-ensemble, pick-clv, source-reliability, oos-split, synthetic-fade}.db.ts`.

- **calibration-ladder**: direct overlap. The paper's core evaluation discipline — log loss as the primary objective, reliability curves (Predk vs Obsk per bin), calibration assessed at progressive game stages — is exactly what a calibration ladder should enforce for live NFL win probabilities. The serve-shrink log-loss-vs-accuracy finding (better probabilities without moving the argmax) is the canonical argument for ladder-style calibration over accuracy-chasing.
- **multi-market-ensemble**: direct overlap. Trace is a stacking ensemble: structural model probabilities fed to a gradient-boosting meta-learner **in both probability and logit space**, plus their difference, plus raw live features. The logit-space trick (logit(p̂M), logit(p̂S)) is a portable ensembling detail worth stealing — it linearizes probability-scale relationships the trees would otherwise have to rediscover.
- **oos-split**: direct overlap. Strict chronological train/val/test with all selection on validation log loss is the paper's strongest methodological asset and matches the purpose of oos-split. Its failure mode (single 473-match validation year → noisy per-checkpoint hyperparameters) is a cautionary example for our split design: use multi-year rolling validation, not one year.
- **pick-clv**: indirect. The paper never touches betting lines or CLV, but the live-win-probability output is the input a CLV module needs for in-play pricing; the calibration-by-progress analysis tells you *when* during a game the model's edge is largest (here: mid-match) — the same analysis should gate when GSE's live edges are bettable.
- **source-reliability / synthetic-fade**: no meaningful overlap.
- **Non-transferable**: the tennis Markov scoring recursion itself (points→games→sets has no NFL analogue at that granularity), surface/Elo specifics, and the per-checkpoint re-tuning pattern (do not copy).

## 11. GSE implementation spec

Build a **live NFL win-probability updater** in the prediction engine implementing the paper's two transferable mechanisms. (Tennis scoring recursion does not port; everything below is the domain-free recipe.)

**Module**: `packages/prediction-engine/src/live-wp/` (new; composes with calibration-ladder and multi-market-ensemble — verify interfaces against those files before coding, I have not read them).

**Inputs** (per play, pre-snap/play state only):
- `prior`: pre-game home win probability (from spread/total-implied or GSE pre-game model) + team strength differential.
- `state`: score differential, time remaining (seconds), down, distance, yard line, possession, timeouts remaining (both), quarter.
- `structural_wp`: output of GSE's existing state-based NFL win-probability model for `state` (whatever the current structural/empirical model is).
- `live_rates`: in-game efficiency metrics with sample counts, e.g. offensive success rate, EPA/play, pressure rate allowed — each as (rate, n_obs).
- `prior_rates`: pre-game expected values of the same metrics with effective prior sample size κ0.

**Method**:
1. **Bayesian shrinkage** (paper Eq. 14, exact port): for each live rate, `θ̂ = (n·r + κ·π)/(n + κ)`. Select κ per metric on validation **log loss** (grid like {20, 40, 80, 160, 320} scaled to NFL sample sizes — a half has ~60 plays, not 150 points). Recompute `structural_wp` with shrunk rates where the structural model accepts rate inputs (mirrors serve-shrink).
2. **Stacking meta-learner** (paper Eqs. 17–19, exact port): train HistGradientBoostingClassifier on feature vector `[wp_struct, wp_shrunk, logit(wp_struct), logit(wp_shrunk), wp_shrunk − wp_struct, state..., live_rates...]` → `p_home_win`. Hyperparameter grid over (learning rate, max leaf nodes, L2) mirroring the paper; select by validation log loss. **One model**, not per-progress re-tuning (fixes paper flaw #3); optionally include `progress = elapsed_seconds/total` as a feature instead.
3. **Calibration pass**: fit the existing calibration-ladder on the meta-learner's outputs, binned by game progress decile (mirrors the paper's calibration-by-progress analysis).

**Output shape** (per play, JSON):
`{game_id, play_seq, p_home_win, components: {structural, shrunk, meta}, shrinkage: {metric: {n, kappa, weight_live}}, progress_decile, calibrated: true}`

**Training data**: nflverse play-by-play (or GSE's existing equivalent), strictly chronological: train ≤2021 seasons, validation 2022–2023 (multi-year rolling — fixes paper flaw #4), test 2024–2025. Features strictly pre-play.

## 12. Reproducible test

Using the chronological split in §11 (test = 2024–2025 seasons, untouched until final eval):

1. **Beats structure**: test log loss of the stacked meta-learner < test log loss of `structural_wp` alone AND < test log loss of shrunk-structural alone. Paired per-game comparison, one-sided paired t-test p < 0.05.
2. **Calibration gate**: decile-binned reliability on test — max |Predk − Obsk| ≤ 0.05 in every bin with ≥200 plays; overall ECE reported.
3. **Shrinkage sanity**: κ selected on validation only; assert live-weight n/(n+κ) is monotone increasing in n on test plays, and that κ=0 (no shrinkage) and κ=∞ (prior only) both lose to tuned κ on validation log loss.
4. **No-leakage audit**: assert every feature at play t is computable from data timestamped before play t (replay the feature pipeline on a 50-game sample with a strict temporal cutoff and diff against production features — must be identical).
5. **Ablation**: removing the logit-space features must not improve test log loss by more than 0.5% (guards against the paper's flaw #11 — if logits carry nothing, drop them and simplify).
6. **Progress conditioning**: report log loss by game-progress quartile; the mid-game quartiles must show the largest gain over the structural baseline (paper's empirical signature — if gains concentrate only in garbage time, the edge is not bettable).

Pass = all six hold. Fail on any = reject the stacking, keep shrinkage-only if test 1 holds for shrunk-structural alone.

## 13. Acceptance/rejection gate (numeric)

**ADAPT (implement §11) if**: on the 2024–2025 chronological test set, the stacked live-WP model reduces log loss by **≥3%** versus the best single structural baseline AND max decile calibration deviation ≤ **5pp** AND the mid-game (Q2–Q3) log-loss gain accounts for ≥50% of the total gain.

**REJECT the stacking if**: log-loss gain < **1%**, or calibration deviation exceeds the structural baseline's, or the gain concentrates in Q4/garbage time only.

**Fallback**: if stacking fails but shrunk-structural alone clears ≥1% log-loss gain with calibration intact, ADOPT the shrinkage mechanism standalone (it's 5 lines of code).

**Do not count toward any program target on accuracy alone** — accuracy is disqualified as a metric for this component (paper §9.6); log loss + calibration only.

## 14. Improvement experiment

What would make this better, GSE-specific:

1. **Leverage-aware κ**: the paper's shrinkage weight depends only on sample size n. In the NFL, not all plays are equal — weight the pseudo-count by score leverage (win-probability swing of the upcoming state). High-leverage situations should trust the prior less per observation... or more; make κ a learned function κ(n, leverage, time_remaining) via the validation log-loss surface instead of a scalar grid.
2. **Drive-level structural recursion**: the paper's Markov recursion doesn't port, but an NFL analogue exists — a drive-outcome Markov (TD/FG/punt/turnover probabilities from down/distance/field position, shrunk per §11.1) feeding a game-level recursion over (score diff, time, possession). This gives GSE a *structural* live model the paper's domain got for free, which the meta-learner then stacks.
3. **CLV-close the loop**: the paper stops at probabilities. Feed the calibrated live p_home_win into pick-clv against live market lines: measure whether predicted edge at each progress decile predicts actual line movement / closing-line value. The paper's "edge lives mid-match" finding becomes a bet-timing rule: only fire live edges in the progress window where validation CLV > 0.
4. **Online κ adaptation**: re-tune shrinkage strength within-season as team priors go stale (early-season priors are weak; by week 10 the "prior" should be mostly this-season data). A decaying prior weight over the season beats the paper's static κ.
5. **Opponent-adjusted live rates**: shrink toward opponent-adjusted priors (offense's success rate vs defensive strength faced), not raw season averages — the paper's π is unadjusted; in the NFL, unadjusted rates are actively misleading.
