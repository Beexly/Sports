# Ledger — arXiv 2605.23597

**Full title:** "Structure-Guided Entity Resolution: Fine-Tuning LLMs for Robust Name Matching in Complex Linguistic Contexts"

**Authors:** Shivam Chourasia, Hitesh Kapoor, Nilesh Patil (Dream Sports — i.e., Dream11, the world's largest fantasy sports platform, 250M+ users)

**arXiv:** 2605.23597v1 [cs.CL] 22 May 2026. Accepted to ACL 2026 (author preprint version).

**VERDICT: ADAPT** — Do NOT fine-tune an LLM for name matching (GSE's deterministic, fail-closed ingestion matching does not need an 8B model in the loop); DO adapt the two transferable, non-LLM ideas: (1) structure-guided parsing (first parse a name into structured components, then match on components, not the raw string) and (2) the three domain-informed augmentation invariances as synthetic training data / adversarial tests for the prop/player-name normalization layer.

---

## 1. Research question

Can a two-phase curriculum fine-tuning strategy — first teaching an LLM to parse the grammatical/semantic *structure* of personal names (single name → `{first_name, middle_name, last_name}` JSON), then fine-tuning from that checkpoint on the binary entity-matching task — produce robust name matching in a linguistically and culturally complex, noisy real-world setting (Indian KYC identity data: transliteration inconsistency, patronymics, honorifics, abbreviations, OCR corruption, merged whitespace)?

The paper's hypothesis: standard single-stage fine-tuning forces the model to learn name structure and the decision boundary simultaneously, leaving performance untapped in domains with strong-but-implicit structural grammar; decoupling the two concerns yields a better internal representation.

## 2. Dataset/schema

- **Source:** Proprietary, drawn from Dream11's historical KYC verification workflows. Records contain **name pairs only**; no other PII fields. Not publicly available.
- **Base training corpus:** 20,000 labeled name pairs curated from past operations.
- **Augmentation:** Expanded to **more than 50,000 examples** with three domain-informed augmentation strategies (details in §6):
  1. **Pair Swapping** — for each pair (name1, name2) add (name2, name1); order invariance.
  2. **Component Permutation** — permute constituent name parts (first, middle, last) to create structurally valid novel examples.
  3. **Random Space Removal** — randomly remove spaces between name parts (e.g., "Kirtan Singh" → "KirtanSingh"); simulates data-entry/OCR errors.
- **Phase 1 corpus (separate):** ~10,000 Indian names manually annotated with structural components (first/middle/last), sampled from anonymized identity records and augmented with synthetically generated names; distinct from the binary pairs.
- **Held-out evaluation set:** **50,000 real-world pairs** from historical production data, manually labeled by the in-house risk operations team. Disjointness enforced **at the individual name level**: no name appearing in any test pair occurs in any training pair (original or augmented). Deliberately 2.5× the base training corpus ("high confidence in production performance").
- **Challenge taxonomy (Table 1):** inverted/merged names ("Kirtan Singh" vs "SinghKirtan" — match), spelling inconsistencies from transliteration ("Subham" vs "Shubham" — match), phonetic ambiguity ("Vipin" vs "Bipin" — NO match), truncations/abbreviations ("Rajeshk" vs "Rajesh Kumar" — match), patronymic variants ("Rajesh So Hari" vs "Hari" — NO match), honorifics/postfixes ("Rameshbhai Patel" vs "Ramesh Patel" — match).

## 3. Method/model

**SGER (Structure-Guided Entity Resolution)** — two-phase curriculum fine-tuning of **Meta Llama 3 8B** (base model in experiments: Llama 3 8B Instruct), SFT with **LoRA: rank 4, alpha 8**, mixed precision (fp16), early stopping on validation F1, single NVIDIA A100 80GB. Inputs space-trimmed and lowercased.

- **Phase 1 — Name structure understanding:** supervised mapping from a single name string to a JSON object with fields `first_name`, `middle_name`, `last_name`. Example input "Kirtan Singh Rathore" → `{"first_name": "Kirtan", "middle_name": "Singh", "last_name": "Rathore"}`. Described as "domain-specific pre-training" building an internal representation of name semantics (common first/family names, middle names like "Kumar"/"Lal", merged/abbreviated forms).
- **Phase 2 — Binary name matching:** starts from the Phase 1 checkpoint; trains a classifier over name pairs. Input template: `[Instruction] [Few-Shot Examples] Name 1: "A" | Name 2: "B" -> Match?` (instruction/few-shot crafted with the risk operations team; same template across all setups). Output: a single token, "Yes" or "No". At inference, the scores for the "Yes"/"No" answer tokens are softmaxed to a match probability; a pair is positive when probability exceeds a **decision threshold selected to maximize F1 on the validation set**.
- **Deployment:** Kubernetes, 3× NVIDIA L4 GPUs, served with vLLM; up to **10,000 RPM** with **P99 latency 120 ms**.

## 4. Equations & assumptions

**No equations stated.** The paper contains no formal equations (no loss functions written out, no probabilistic model, no calibration formula). Stated assumptions:

- Names in the target domain have an implicit "grammar" (structural regularities) that standard fine-tuning must learn jointly with the decision boundary — assumed, not proven.
- Decision threshold is chosen to maximize F1 on the validation set (assumes the validation F1 optimum transfers to production).
- Train/test name-level disjointness is assumed sufficient to prevent leakage (see §9 for why this is imperfect).
- The augmentation transforms (pair swap, component permutation, space removal) are assumed to encode true invariances of the domain, "analogous" to CV transforms (mirroring, geometric transforms, noise injection).

## 5. Features/target

- **Phase 1 target:** structured JSON name components (`first_name`, `middle_name`, `last_name`) — the "feature" is the model's internal representation of name structure; no handcrafted features.
- **Phase 2 target:** binary label — "Yes" (same individual) / "No" (different individuals) for a name pair. Decision uses softmax over the two answer-token scores → match probability → F1-optimal threshold.
- **Baselines:** Levenshtein similarity (threshold 0.8, tuned for F1), multilingual BERT-base-cased with a classification head over [CLS] on concatenated names, GPT-4o few-shot (same instruction template), Llama 3 8B few-shot, single-stage SFT Llama 3 8B (with/without augmentation).

## 6. Validation design

- Metrics: accuracy, precision, recall, F1; F1 used for early stopping. Rationale stated: high precision reduces false links (compliance risk); high recall reduces friction for legitimate users.
- Single held-out set of 50,000 pairs with name-level disjointness from training (originals + augmentations). No k-fold CV, no confidence intervals, no repeated-seed reporting.
- Ablation ordered cumulatively: single-stage SFT (F1 0.946) → + augmentation (F1 0.973) → + curriculum Phase 1 (F1 0.994).
- Production deployment at Dream11 as the ultimate validation: 99.95% precision enables fully automated match/no-match decisions; claimed elimination of third-party manual-verification dependency and **>$500K annual cost savings**. Rare false negatives (<1% of users) resolved via customer service.

## 8. Code/data availability

**None.** The dataset is proprietary ("drawn from our platform's historical KYC verification workflows"), the ~10,000 annotated Phase 1 names are proprietary, and no code or model weights are released. ## 9. Leakage & limitations (adversarial)

1. **Augmentation leaks near-duplicates into training in a way that name-level disjointness does not fully fix.** Component permutation and space removal create synthetic variants of names that may appear (in different surface form) in the test set; the test set is drawn from the *same* historical KYC workflow distribution, so synthetic distortions of training names can land close to real test distortions. Disjointness at the exact-string level is weaker than it sounds for near-duplicate-heavy data.
2. **Augmentation provenance is underspecified.** "Expand to more than 50,000 examples" — the exact count, class balance before/after augmentation, and whether augmentations were applied equally to positive and negative pairs are unstated. If augmentation is label-biased (e.g., permutations mostly applied to match-pairs), the F1 lift could partly reflect class-structure artifacts.
3. **No confidence intervals, no seeds, no variance.** F1 0.973 → 0.994 looks decisive, but a single run on a single 50K test set with no reported variance cannot establish that the curriculum gain (2.1 F1 points) is statistically stable — especially with LoRA rank-4 training, which is known to be seed-sensitive.
4. **Threshold selection bias.** The decision threshold is "selected to maximize F1 on the validation set" — fine — but then final metrics are reported on the *test* set with no stated separate threshold discipline; if any threshold tuning touched the test set, the 0.994 is optimistic.
5. **Baseline weakness inflates the story.** Levenshtein at threshold 0.8 gets 57.4% accuracy on this data — a threshold likely mis-tuned for the domain (0.8 is harsh for transliterated names), making classical methods look like strawmen. No Jaro-Winkler, no phonetic, no learned-ensemble classical baseline — the "classical" lane is one threshold of Levenshtein.
6. **Domain mismatch with GSE.** The entire evaluation is Indian personal names for KYC. The transferable claim to "complex linguistic contexts" is untested on Western sports names. Sports-name matching is a *narrower, easier* problem (closed vocabulary of athletes, standardized feeds) — the paper's 0.994 does not transfer as a number, and the problem may not need anything near this machinery.
7. **Production claims unverifiable.** >$500K savings, 10,000 RPM, P99 120 ms are self-reported by the deploying company with no methodology. "Eliminating manual review" rests on 99.95% precision on a *proprietary* test distribution — a 0.05% false-positive rate at Dream11 scale (250M users) is still ~125K wrong links; the paper waves this away.
8. **Error analysis is thin.** Two failure modes (ambiguous phonetics like "Saurabh"/"Sorab"; compound errors like "SubhamKshr" vs "KishoreShubham") with no quantification of their share of the residual ~490 errors (0.98% of 50K).
9. **The curriculum ablation confounds weight-initialization with task design.** Phase 2 starts from the Phase 1 checkpoint — but there is no control where Phase 2 starts from a checkpoint trained on an equal number of *generic* SFT steps (vs. the name-structure task specifically). The gain could partly be "more training steps on name-domain text," not "structural understanding."

## 10. GSE overlap

Honest status: I read the ingestion-layer identity code (`packages/ingestion-pipeline/src/game-identity.ts`, `fixture-collapse.ts` headers, `kalshi-team-abbr.ts` existence, test inventory) and directory listings of `packages/prediction-engine/src/` and `packages/data-ingestion/src/`. I did **not** read the internals of the six engine modules named in the task (`calibration-ladder`, `multi-market-ensemble`, `pick-clv`, `source-reliability`, `oos-split`, `synthetic-fade` `*.db.ts`) — any claim about their contents would be invented.

- **Where entity resolution actually lives in GSE:** the *ingestion* layer, not the six prediction-engine modules. `game-identity.ts` resolves game identity across four external-ID shapes (Odds API 32-hex, TheRundown `event_id`, two ESPN keyings) using **team pair + commence-time matching** (18h tolerance, 2h for MLB doubleheaders), city-prefix rules, and an explicit **fail-closed** doctrine (ambiguity → no merge, never a guess; kill switch `GAME_IDENTITY_MERGE_DISABLED`). `kalshi-team-abbr.ts` handles team abbreviation mapping. This is deterministic, unit-testable, no-I/O matching — philosophically the opposite of the paper's LLM approach, and appropriate: a wrong game merge attaches odds to the wrong contest, which the codebase treats as worse than a duplicate row.
- **The real GSE name-matching surface is player names in prop ingestion** (`prop-line-rows.ts`, five live pick'em intakes: DK Pick6, Underdog, PrizePicks, Sleeper, Action Network). No dedicated player-name-alias/normalizer module was found in the ingestion packages — this is the gap SGER's ideas apply to: book-to-book player name variants ("Jaxon Smith-Njigba" vs "Jaxon Smith Njigba", suffixes Jr./III, accents, DK abbreviations).
- **Fit of the six named modules:** `source-reliability` is the closest conceptual neighbor (trusting which feed's spelling to prefer when books disagree on a name); the others (calibration, ensemble, CLV, OOS splits, synthetic fade) are downstream of identity resolution — they consume whatever the ingestion layer decided a name refers to. SGER offers them nothing directly.

## 11. GSE implementation spec (concrete, non-LLM adaptation)

Build a **structure-guided deterministic player-name matcher** in the ingestion pipeline (new file, e.g. `packages/ingestion-pipeline/src/player-name-resolve.ts`), composed of two stages that mirror SGER's two phases *without* an LLM:

**Stage 1 — Name structure parser (the Phase 1 analog).** Deterministic tokenizer → structured record:
- Input: raw player name string from any book feed.
- Normalization: lowercase, strip punctuation (hyphens → space, periods removed), Unicode fold (é→e), strip known suffixes into a `suffix` field (Jr, Sr, II, III, IV, V).
- Parse: split on whitespace → tokens; heuristic component assignment: last token (pre-suffix) = `family_name`, first token = `given_name`, middle tokens = `middle_names`; detect merged tokens via dictionary-free rule: if a token contains a case boundary (`SmithNjigba`) or matches concatenated known roster tokens, split it.
- Output shape: `{ given: string, middles: string[], family: string, suffix: string | null, raw: string }`.

**Stage 2 — Component-level matcher (the Phase 2 analog).**
- `matchScore(a, b)`: weighted combination of per-component similarities — family-name Jaro-Winkler (weight 0.6), given-name Jaro-Winkler (0.3), middle-initial equality bonus (0.1); order-invariant: compare both orientations and take the max (the paper's pair-swapping invariance, implemented as a rule).
- Merge rule preserving GSE's fail-closed doctrine: merge only if `family` similarity ≥ 0.92 AND combined score ≥ threshold τ; else return null (keep separate rows — today's behavior). τ chosen by the paper's method: **maximize F1 on a labeled validation set of book-to-book player name pairs** (§12).
- Canonical spelling selection: when books disagree, prefer the spelling from the highest-priority feed per `source-reliability` ordering (needs that module's ranking — currently un-read; flag as integration point).

**Augmentation (the paper's three invariances, repurposed):** generate synthetic training/validation pairs from the existing roster: (1) swap token order, (2) permute components, (3) remove spaces / strip punctuation / drop suffixes. Use these to (a) build the labeled validation set cheaply and (b) adversarially test the matcher.

**What is explicitly NOT built:** no LLM, no LoRA fine-tuning, no vLLM serving. The paper's *mechanism* (fine-tuned Llama 3 8B) is rejected as overkill for a closed-vocabulary sports-name problem; the *curriculum structure* (parse-then-match) and *invariance augmentations* are what transfer.

## 12. Reproducible test

New test file alongside the implementation (repo convention: `__tests__/*.test.ts`, vitest):

1. **Unit: parser.** Assert `parse("Jaxon Smith-Njigba")` → `{given:"jaxon", middles:[], family:"smith njigba"→"smithnjigba"...}` — concrete: family tokens `["smith","njigba"]`; assert suffix extraction on `"Kenny Pickett"` vs `"Michael Penix Jr."` → suffix `"jr"`; assert Unicode fold `"José Ramírez"` → family `"ramirez"`.
2. **Unit: matcher positives.** Assert `match("Jaxon Smith-Njigba", "Jaxon Smith Njigba")` merges; `match("Tua Tagovailoa", "Tua Tagovailoa")` merges; order-invariance: `match("Smith-Njigba, Jaxon", "Jaxon Smith-Njigba")` merges.
3. **Unit: matcher negatives (fail-closed).** Assert `match("Jayden Daniels", "Jayden Higgins")` → null; `match("Michael Wilson", "Michael Pittman")` → null (shared given name must not merge); short-token guard: 2–3 letter abbreviations never prefix-merge (mirrors `MIN_PREFIX_MATCH_LENGTH = 4` precedent).
4. **Augmentation sweep:** generate ~5,000 synthetic pairs from the real roster via the three transforms with known labels; assert F1 ≥ 0.97 and precision ≥ 0.995 on this set.
5. **Threshold discipline:** τ is selected on a validation split, asserted frozen in a constants file; the test re-computes F1 at τ±0.02 and asserts τ is the argmax (guards against threshold drift).

**Pass criteria:** all unit tests pass; synthetic-set F1 ≥ 0.97 with precision ≥ 0.995; zero merges on the adversarial negative set (fail-closed preserved — any false merge fails the suite).

## 13. Acceptance/rejection gate (numeric)

**ADOPT the adapted matcher into the prop-ingestion path if and only if:**

- On a hand-labeled validation set of **≥500 real book-to-book player-name pairs** (sampled from the five live intakes: DK Pick6, Underdog, PrizePicks, Sleeper, Action Network), the structure-guided matcher achieves **F1 ≥ 0.98 with precision ≥ 0.995** (precision bar is the binding constraint — a false player merge attaches a prop line to the wrong athlete, the player-name analog of the game-identity "wrong merge is worse than duplicate" rule);
- **AND** it resolves ≥20% more true cross-book duplicates than the current normalization approach at equal-or-better precision (measured by recall delta at fixed precision ≥ 0.995);
- **AND** median added latency per name resolution < 1 ms (pure function, no I/O — trivially satisfiable; guards against anyone reintroducing model inference here).

**REJECT (do not wire into ingestion) if:** precision < 0.995 on the real-pair validation set, or the hand-labeled set cannot be assembled (no labels → no gate → no merge; fail closed), or the recall delta over current normalization is <10% (not worth the new code path).

## 14. Improvement experiment (GSE-specific extension)

The paper's Phase 1 is generic name-structure parsing; GSE's version can be **sport-aware and roster-closed**, which the paper cannot do:

1. **Closed-vocabulary constraint:** GSE knows the full roster of active NFL/CFB players. Replace the paper's open-ended matching with *roster-anchored* resolution: every incoming book name must resolve to exactly one roster entry or to null (unresolved → human-review queue, never a guess). This converts the paper's binary pair-classification into an N-way retrieval problem over a known candidate set — strictly easier and auditable.
2. **Position/team as disambiguation features:** the paper matches on names alone (KYC constraint). GSE prop feeds carry team and position alongside the name. Add hard constraints: a name match is invalid if the two rows' teams differ (except post-trade windows) — this kills the entire class of "two players, similar names" false positives that the paper's error analysis flags as its top failure mode.
3. **Learn the weights, keep it deterministic:** instead of fixed 0.6/0.3/0.1 component weights, fit a logistic regression on the hand-labeled validation set over features {family JW, given JW, middle-initial match, suffix match, token-count delta, order-inversion flag}. Keeps the no-LLM, sub-millisecond, unit-testable properties while squeezing the paper's "learned decision boundary" benefit out of Phase 2.
4. **Temporal alias memory:** persist confirmed resolutions (book spelling → roster ID) in a small alias table with source attribution; new spellings only enter via the matcher + (initially) human confirm, then become O(1) lookups. This is the production-hardening the paper's deployment section gestures at but doesn't detail.

---

**VERDICT: ADAPT** — The fine-tuned-LLM machinery itself has no place in GSE's ingestion path, but the paper's two genuinely transferable ideas — parse name structure *before* matching, and encode domain invariances (order-swap, component-permutation, space-removal) as synthetic data — map directly onto a deterministic, fail-closed, sub-millisecond player-name resolver for the five live prop intakes, where no dedicated normalizer module currently exists. Gate is numeric: F1 ≥ 0.98 at precision ≥ 0.995 on ≥500 hand-labeled real book-to-book pairs, or it doesn't ship.
