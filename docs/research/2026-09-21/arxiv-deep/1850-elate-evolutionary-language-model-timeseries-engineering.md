# [1850] ELATE: Evolutionary Language model for Automated Timeseries Engineering (arXiv:2508.14667)

**Citation:** Andrew Murray, Danial Dervovic, Michael Cashmore (2025). *ELATE: Evolutionary Language model for Automated Timeseries Engineering*. arXiv:2508.14667v1. URL: https://arxiv.org/abs/2508.14667
**Ledger completed:** 2026-09-22. **Read:** full text (PDF, lines 0–3669, main body, references, all appendices — dataset descriptions, per-domain top-10 example features, Algorithms 1–13 pseudocode, evaluator details). Integrity gap corrected 2026-09-22 (lines 2033–2399).
**Verdict:** ADAPT

Rationale: strongest time-series feature-engineering method in the wave and the only one with a prompt-enforced temporal-causality contract, but the trading-domain zero-gain result and the ETTh1/ILI validation-overfitting require GSE-specific adaptation (early stopping, sports domain narrative, FRESH fast tier, human review gate).

## 1. Research question
Can an LLM, guided by an evolutionary population of code features with cheap statistical pre-screening and TreeSHAP-based pruning, automatically engineer time-series features that systematically beat hand-built features, enumerative feature-engineering systems (tsfresh, VEST), and a trained LSTM — under a hard no-leakage contract where features may only use past rows?

## 2. Dataset / schema
Seven forecasting tasks: ILI (CDC flu portal, 965 rows / 10 feats, 1-month horizon), Store (Kaggle Walmart, 6,300 / 11, 1-week), ETTh1 (Zhou et al., 17,419 / 11, 1-hour), Energy (Kaggle, 35,040 / 21, 1-day), Pollution (Kaggle, 43,776 / 13, 1-day), Trading (Kaggle S&P-500, 125,750 / 12, 1-day), Food (Kaggle meal-delivery, 179,568 / 10, 1-week). Tabular+time panel data; rows 965–179,568. All datasets public. Final evaluation model: XGBoost with fixed hyperparameters across all domains.

## 3. Method / model
TS Auto-FE formalized as min_T E(φ(T, X), y) (Def. 3): choose the set of transformations minimizing prediction error, where T: R^{m×n} → R^m produces one new column and φ columnwise-concatenates p transforms. A population (feature_db) of LLM-generated pandas features evolves over G generations. Each generation: features sampled with probability ∝ evaluator score under exponentially decaying temperature; the LLM writes one new pandas feature plus a utility comment; code is AST-validated; the evaluator scores each new feature as the mean of Granger-causality and mutual-information statistics with the target; at Nmax=100 a TreeSHAP-interventional filter with walk-forward XGBoost (|corr|>0.9 dedup, iterative worst-10% pruning) trims to N=50, with an RMSE check that keeps the previous generation's set if it regressed. Versus CAAFE (Hollmann): CAAFE keeps features only on immediate improvement and discards intermediate steps — e.g., height² gets no reward alone, blocking BMI = weight/height². ELATE's feature_db accumulates intermediate code, so the LLM can compose depth-10 features (the trading ADL oscillator example: CLV → money-flow volume → per-symbol cumsum → 3-day MA → oscillator) without greedy step-by-step rewards. Under naive enumeration that feature would need 357 depth-1 candidates to be reachable. Full implementation contract from Appendix C (Algorithms 1–13): Feature objects store code strings (not vectors) so features recompute on new data; `Feature.get_feature` AST-parses and compiles code before executing on X (invalid code raises). Feature_db constructor takes (desc, prompt template, n_prompt, T0=10, K=5, ε=0.1, Nmax=100, N=50, G). `get_prompt` samples features with softmax(score/T) under decaying T = T0·e^(−K·nfeat/Nmax) + ε — early generations explore (high T), late generations exploit. `generate_prompt` fills @@description@@/@@examples@@ slots and appends all generation names+scores. `add_feature` bumps the generation counter and calls `reset_feature_db()` once n ≥ Nmax — the db restarts seeded with the best set of the generation. `update_best_feature_set` runs the SHAP filter, computes walk-forward-XGBoost RMSE of the augmented set, and *reverts* to the previous generation's set if the new set regresses (monotonic guard). `shap_filter` = recursive elimination: compute TreeSHAP, sort, `prune_correlated`, drop worst-10% iteratively until N features remain. ELATE class has a standard fit/transform interface: fit populates the db on the validation matrix and clears LLM conversation history at each generation boundary; transform applies the final best set to any matrix. The ELATE 4o+FRESH variant replaces the SHAP filter with tsfresh's FRESH statistical-significance tests (Benjamini–Yekutieli combination) directly pruning on evaluator scores — no model training, fastest on 5/7 domains.

## 4. Equations & assumptions
- Feature sampling: P(Xj) = exp(E(Xj,Y)/T) / Σ_k exp(E(Xk,Y)/T), with T = T0·e^{−K·nfeat/Nmax} + ε (T0=10, K=5, ε=0.1).
- Evaluator: E(Xj, Y) = (E_GC(Xj, Y) + E_MI(Xj, Y)) / 2.
- Granger causality (Appendix D): statsmodels `test_causality` — VAR F-test on lagged X terms, p < 0.05 threshold, E_GC(X) = |b1| (magnitude of the first lag coefficient). Mutual information: sklearn `mutual_info_regression`.
- Pruning: TreeSHAP with interventional values ("true-to-the-model" per Chen et al.), XGBoost walk-forward, SHAP normalized per fold/instance; |corr|>0.9 duplicate removal; recursive worst-10% pruning until N=50; RMSE(X_k) < RMSE(X_{k−1}) required, else keep X_{k−1}.
- Stated assumptions: temporal-causality contract is *prompt-enforced* ("no negative shifts," "aggregations only over past rows," "avoid bfill"), not AST-enforced — the AST check validates a code allowlist, not causality. Features may only use Target_Tminus1 (the most recent target value available at forecast time); the LLM may build arbitrary lags from it. Evaluators chosen because they are cheap and stable under the addition of new features (SHAP is not, so SHAP is reserved for the pruning stage). Human-in-the-loop is required: no guarantee generated transformations are correct; ELATE is explicitly "not intended to replace the data scientist."

## 5. Features / target
Base features are the raw per-domain columns (e.g., Store: Weekly_Sales, Temperature, Holiday_Flag, etc.; ETTh1: OT_Tminus1, HUFL, MUFL, LUFL, LULL, HULL). Targets and horizons per domain: ILI 1-month-ahead flu incidence, Store 1-week-ahead sales, ETTh1 1-hour-ahead transformer oil temperature, Energy 1-day-ahead demand, Pollution 1-day-ahead, Trading 1-day-ahead stock returns, Food 1-week-ahead demand. Few-shot prompt slots: @@description@@ (feature names, dtypes, NaN flags, domain narrative), @@examples@@ (sampled feature_db entries), @@generated_features@@ (most recent 250 names + scores, preventing duplicates and steering trajectory).

### Representative generated features (Appendix, lines 2033–2399)
- **Store:** Store_Specific_Rolling_Weekly_Sales_StdDev (groupby-Store rolling std, window 6); Store_Specific_Weekly_Sales_Momentum_Temperature_Adjusted ((rolling-mean − rolling-min of sales, w=4) × (1 + 0.01 × avg temperature)); Store_Specific_Rolling_Sales_Temperature_Interaction_Mean (sales×temperature rolling mean, w=3); Store_Specific_Rolling_Holiday_Sales_Mean (holiday-week rolling mean, w=4).
- **ETTh1:** OT_Tminus1_ewma_9h; OT_Tminus1×LUFL interaction ewma 18h; HUFL/OT_Tminus1 ratio ewma 12h; OT_Tminus1×LUFL ewma 720h; OT_Tminus1 standardized deviation 12h; OT_Tminus1×LULL ewma 840h; OT_Tminus1×(HUFL/(HUFL+HULL)) ewma 12h; OT_Tminus1 standardized deviation 24h; OT_Tminus1×LULL ewma 15000h; OT_Tminus1×MUFL ewma 6h. Note the degenerate spans (840h, 15,000h) — the search retains near-constant long-horizon EWMAs that pass the evaluators without adding real signal, an argument for pruning in GSE.
- **Energy:** temp_load_forecast_error_day_interaction (temp × forecast error × sin(day_of_week)); temp_humidity_load_interaction ((temp×humidity)/total_load_actual); generation_load_forecast_error_interaction (24h-rolling generation-to-load ratio × load forecast error); temp_load_interaction; hour_sin/hour_cos encodings; temp_anomaly (hour-of-day groupby deviation).

## 6. Validation design
Walk-forward CV; final 10% of dates as test, penultimate 10% as validation. Baselines: T−1 naive, Base (hand-built features), Zero-Shot (GPT-4o one prompt), VEST, tsfresh, LSTM, plus ablations ELATE 4o+FRESH, ELATE 4o+Const (constant evaluator scores — kills the guidance signal), ELATE 3.5T+SHAP. Metrics: MAE and RMSE. Splits are time-ordered throughout.

## 7. Numerical results / baselines
- ELATE 4o+SHAP is best (bold) in 6/7 domains on both MAE and RMSE; trading is tied with Base (no gain — stock returns too volatile/noisy).
- Average vs. Base: −9.6% MAE, −8.4% RMSE. Energy domain: RMSE 0.1145 → 0.0933 (−18.5%).
- Zero-Shot GPT-4o is often worse than Base (ILI RMSE 0.0621 vs. 0.0427 Base) — the evolutionary selection loop, not the LLM alone, does the work.
- GPT-3.5-Turbo variant: −5.8%/−6.6% average at $1.18–$2.07/run vs. GPT-4o's $5.99–$13.43/run; 3.5T produces more invalid features, raising prompt counts.
- ELATE 4o+FRESH beat all non-ELATE baselines on 4/7 domains, fastest on 5/7.
- tsfresh blew past 128 GB RAM in 6/7 domains (only completed on Store: 7,831 features, 13.7 GB peak on 6,300 rows × 11 features) — the expand-and-reduce memory argument for ELATE.
- Runtime: ELATE 4o+SHAP ~3 h average (2,003–34,677 s across domains), faster than VEST and LSTM on 4/7; anytime algorithm — best-so-far set returnable at any generation.
- Data-scientist cost comparison: ~$75/hr; ELATE completes in hours what takes days manually.
- A consumer-goods survey is cited: a 10% forecast-accuracy gain maps to ~5% inventory-cost reduction and ~2% revenue increase.

## 9. Leakage & limitations
- Temporal-causality contract is prompt-enforced, not AST-enforced; the AST check validates code allowlists, not causality. A GSE port must add a static AST check for negative shifts/rolling on post-cutoff columns.
- Generated features sometimes apply unshifted rolling windows to *current-row* covariates (e.g. Volume rolling mean on the trading day, temperature rolling mean on the same hour) — leakage-free only because the inputs are same-day covariates, not the target.
- Several Energy features use total_load_actual, which is target-adjacent — safe only as strictly lagged history; at inference time this must be recomputed from past actuals only.
- Validation overfitting observed on ETTh1 and ILI (normalized val RMSE keeps improving while test stalls); authors declined early stopping only to keep the comparison uniform — a real GSE deployment must add it.
- No guarantee of validation-RMSE improvement per generation: interventional SHAP is faithful per-feature but the selected top-N set can have overlapping/redundant elements.
- LLM query cost may be prohibitive for some applications; mitigations: open-source/cheaper models (3.5T keeps most of the gain at ~1/5 the cost).
- Human-in-the-loop is required: no guarantee generated transformations are correct.
- Trading domain: zero improvement — the method adds nothing where the target is dominated by noise; a cautionary read for NFL spreads, which are far more efficient than store sales.
- Same prompt template throughout; prompt engineering is unexplored future work.

## 10. GSE overlap
This is the closest paper yet to GSE's actual production problem: inventing rolling/lag/interaction features over time-ordered panel data with a hard no-leakage contract. The prompt rules ("no negative shifts," "only past rows," "avoid bfill") are directly portable into GSE's LLM feature-generation pipeline as a leakage gate. The Target_Tminus1 trick maps exactly to GSE's cutoff discipline: features may reference only data available at kickoff; the LLM is free to build arbitrary lags from that point backward. This is a new capability (evolved code-feature search with statistical pre-screening + SHAP pruning), not a duplicate of existing GSE work. Caution: the trading result is the honest one for GSE — NFL betting markets are closer to stock returns than to store sales in efficiency. Expect single-digit percentage gains, not 18%.

## 11. GSE implementation spec
Sports bridge: NFL totals/forecasting — feed ELATE a panel of weekly team game stats, weather, injury-report counts, and market data with Target_Tminus1 = the team's most recent game total/offensive output. The LLM invents rolling, matchup-adjusted, and weather-interaction features (e.g., "4-week offensive momentum × temperature," the Store example's direct analog) under the past-only prompt contract; TreeSHAP walk-forward pruning selects the top-50 for the production XGBoost. Player props: same loop per market type (passing yards, receptions) with player-game rows grouped by player; the ADL-oscillator example shows the method can invent money-flow-style pressure indicators from raw market fields if given them.

Concrete build plan:
1. Build a `feature_db` table: (name, pandas code string, utility comment, evaluator score, generation).
2. Prompt constructor: dataset description (column names/dtypes/NaN flags + one-paragraph NFL domain narrative), few-shot examples sampled from feature_db, last-250 generated names+scores, and the leakage rules block copied from ELATE's template (no negative shift, past-rows-only aggregations, no bfill, same index, restricted packages: numpy, pandas, sklearn, scipy.stats, statsmodels.tsa). Add a static AST causality check that the paper lacks (reject any `.shift(-` or unshifted target usage).
3. Generation loop (G=10, Nmax=100): sample n_prompt=5 features with T = 10·e^{−5·nfeat/100} + 0.1; call the LLM for one feature; AST-validate against the allowlist; execute in a sandbox on the panel; score E = mean(Granger causality, mutual information) vs. the target column.
4. Prune at Nmax: |corr|>0.9 dedup, TreeSHAP-interventional on walk-forward XGBoost, recursive worst-10% removal to N=50; keep the new set only if walk-forward RMSE improves, else retain the prior generation's set. Add early stopping (missing in the paper).
5. Fast tier: ELATE+FRESH variant (FRESH significance tests on evaluator scores, no model training) for mid-week refreshes; SHAP tier for the weekly rebuild.
6. Human review gate before any generated feature enters the production set (authors' requirement, and GSE's regulator).

## 12. Reproducible test
Task: predict NFL game totals (over/under line movement direction or total points) on a walk-forward split: train seasons 2019–2023, validate 2024, test 2025 (final 10% of games as test, penultimate 10% as validation, mirroring the paper). Baseline: XGBoost on hand-built rolling features (no LLM features). Treatment: XGBoost on hand-built features + top-50 ELATE-generated features, with the prompt's leakage contract enforced and a static AST check rejecting any `.shift(-` or `bfill`. Run both LLM backends (cheap/fast model and flagship model) to replicate the 3.5T-vs-4o cost/quality tiering.

## 13. Acceptance / rejection gate
ADAPT if: ≥0.003 held-out NFL log-loss improvement on the 2025 test games versus the no-LLM-feature baseline, with no post-kickoff leakage (AST scan must show zero negative shifts; all aggregations causal), and at least 60% of the selected features passing the human review gate. REJECT (do not deploy) if any of: leakage scan fails, no gate improvement, or review pass-rate <60%.

## 14. Improvement experiment
Replace the prompt-enforced causality contract with an AST-enforced one: write a static analyzer that rejects any generated feature whose AST contains negative `.shift`, `.bfill`, or a rolling window touching the target column at lag 0, and measure how many of ELATE's accepted features fail it. Then rerun the generation loop with the analyzer in the acceptance path (instead of the prompt instruction alone) and compare accepted-feature count, evaluator-score distribution, and downstream RMSE. Rationale: the paper's honest gap is that the AST check validates syntax, not causality — if a measurable fraction of "valid" features are actually leaking, AST enforcement could both raise out-of-sample performance and remove the need for the human causality review that the authors require.
