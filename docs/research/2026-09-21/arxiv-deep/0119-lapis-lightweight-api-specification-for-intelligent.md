# [0119] LAPIS: Lightweight API Specification for Intelligent Systems (arXiv:2602.18541v1)

**Citation:** Daniel García García (Independent Researcher, Spain). *LAPIS: Lightweight API Specification for Intelligent Systems — A Token-Efficient API Description Format for LLM Context Windows*. arXiv:2602.18541v1, 26 February 2026. URL: https://arxiv.org/abs/2602.18541v1
**Ledger completed:** 2026-09-21. **Read:** full text (PDF via arxiv.org, 738 lines; all sections, tables, conversion rules, evaluation read).
**Verdict:** ADAPT — a token-efficient API description format (85.5% average token reduction vs. OpenAPI YAML) designed for LLM consumers. Directly applicable to GSE: Garrett holds API accounts on 12+ sports-data services (The Odds API, MySportsFeeds, SportsDataIQ, TheSportsDB, 4Deep Sports, etc.), and GSE's agents burn context on API docs and specs. Convert each provider's OpenAPI spec to LAPIS once, store the compact spec in the repo, and inject it into agent context instead of raw docs — cutting both token cost and context-window pressure. Complements 0115 (HiveMind token budgets) and 0116 (governed-MCP schema validation).

## 1. Research question
LLMs are a new class of API-specification consumer (agents, coding assistants), but the de facto standard, OpenAPI, was designed in 2010–2015 for documentation renderers, SDK generators, and testing tools — producing measurable token waste: structural overhead (JSON Schema nesting), error duplication (GitHub's 1,594 error definitions across 1,080 operations; the 404 alone repeated 531×), irrelevant metadata (contact, license, x-* extensions), and missing operational context (rate limits, webhook triggers, operation sequencing buried in free text). LAPIS asks: can a domain-specific format preserve the semantic information an LLM needs for API reasoning while minimizing token usage — as a conversion target from OpenAPI 3.x, not a replacement?

## 2. Dataset / schema
Five real-world production API specifications (Table 3): GitHub (1,080 endpoints, 8,313 types, 11.8 MB), DigitalOcean (545 endpoints, 3,594 types, 2.5 MB), Twilio (197 endpoints, 1,079 types, 1.9 MB), HTTPBin (73 endpoints, 0 types, 28 KB), Petstore (19 endpoints, 33 types, 17 KB). Source: providers' official repositories/endpoints; converted with the reference converter (lapisspec v0.1.0, PyPI). Tokenizers: cl100k_base (tiktoken) and o200k_base. Specs, converter, and evaluation materials: https://github.com/cr0hn/LAPIS (CC BY 4.0); browser tool at https://cr0hn.github.io/LAPIS/; spec EBNF at https://github.com/cr0hn/LAPIS/blob/main/spec.en.md. No ML dataset.

## 3. Method / model
LAPIS v0.1.0: up to seven sections in fixed order ([meta] and [ops] required):
- **[meta]:** api name, base URL, version, desc, auth (`bearer [Authorization]`, schemes: bearer, apikey, basic, oauth2, none).
- **[types]:** reusable objects/enums; 8 scalars (str, int, float, bool, date, datetime, file, any) with array `[T]`, map `{str:T}`, optional `?`, default `= value` modifiers; indentation-based objects; pipe-delimited enums (`InvoiceStatus: draft | sent | paid | overdue`); field annotations `@since:X.Y`, `@deprecated "reason"`.
- **[ops]:** signature-based syntax with directional markers: `create_invoice POST /invoices` / `> customer_id: str` (inputs) / `< Invoice` (output); parameter location inferred ({param} in route → path; GET/DELETE → @query; POST/PUT/PATCH → @body; explicit @location overrides); modifiers (+paginated, +idempotent, +stream, +deprecated).
- **[webhooks]:** `invoice_paid -> POST /webhooks/invoice-paid` with `!` trigger conditions ("When invoice.status changes to 'paid'") — semantic info OpenAPI cannot represent structurally.
- **[errors]:** centralized, defined once globally, optional `@ops:` binding; `~` prefix for error-specific response fields (e.g., 401 unauthorized, 404 not_found, 409 duplicate_customer @ops: create_customer).
- **[limits]:** structured rate limits (`plan: free rate: 60/m @key quota: 1000/mo @key`), on_exceed: 429, retry_after — enables LLM reasoning about throttling/retry/tier selection.
- **[flows]:** multistep sequences with sequencing (->), repetition (*), branching (|), conditionals (?), waiting (...()) — e.g., invoice_lifecycle: create_invoice -> update_invoice* -> send_invoice -> ...(awaiting payment) -> invoice_paid | invoice_overdue.
- **Conversion rules (deterministic, §5):** resolve all $ref; flatten allOf (merge), oneOf/anyOf → most common variant (complex unions → any); schemas referenced >1× become named types, single-use inlined; operationId → operation name (else method_resource); 4xx/5xx deduplicated by code+schema identity into [errors]; OpenAPI 3.1 webhooks → [webhooks]; discard contact/license/termsOfService/externalDocs/tags/x-*/multiple servers/response headers/examples/xml/discriminator. Reference converter: `pip install lapisspec`. Complete EBNF grammar published for tooling authors; "designed to be consumed directly by LLMs without parsing." Explicit non-goals: not a replacement for OpenAPI, no transport/execution protocol (MCP's domain), no bidirectional conversion, not a general serialization format (TOON's domain).

## 4. Equations & assumptions
The paper states no equations — it is a specification/evaluation paper; the only formal artifact is the EBNF grammar (referenced, not quoted in full). Do not invent equations for it.
- Design principles: token minimality (target 70–80% fewer tokens than OpenAPI YAML); LLM-native syntax (whiteboard-style, natural-language-adjacent); lossless conversion from OpenAPI 3.x (fully automatable, deterministic); human readability; semantic completeness for reasoning (validation keywords and XML hints deliberately excluded).
- Assumptions: an LLM needs "what the API does, what inputs it accepts, what outputs it returns" — not JSON Schema exactness; rate-limit/webhook/flow semantics can be hand-authored or extracted into the new sections; the cl100k_base/o200k_base tokenizers are representative (counts consistent within 2% across both).

## 5. Features / target
No ML features/target. Control variable: specification format (LAPIS vs. OpenAPI YAML/JSON/minified JSON). Measured outcomes: token counts (cl100k_base, o200k_base), character counts, line counts, reduction ratios, estimated $/call at February 2026 pricing ($3.00/M input tokens, Claude Sonnet 4.5 pricing).

## 6. Validation design
Corpus study + measurement: five production specs converted with lapisspec v0.1.0; token counts via tiktoken on both tokenizers; four format variants for JSON-source specs (JSON formatted, JSON minified, YAML, LAPIS); section-by-section attribution of savings; scaling analysis (reduction vs. endpoints/types); cross-tokenizer consistency check. No LLM comprehension experiment — explicitly listed as future work ("does not include a controlled experiment measuring whether LLMs produce better API calls when given LAPIS versus OpenAPI context," planned following TOON's retrieval-accuracy methodology). Strengths: real specs, three orders of magnitude in size, deterministic converter, consistent cross-tokenizer results. Weakness: token reduction is measured, but the actual claim that matters (LLM reasoning quality on LAPIS) is untested.

## 7. Numerical results / baselines
- **Token reduction (Table 4, cl100k_base, vs. OpenAPI YAML):** GitHub 1,811,843 → 313,101 (82.7%, 0.17×); DigitalOcean 586,731 → 54,201 (90.8%, 0.09×); Twilio 306,453 → 24,197 (92.1%, 0.08×); HTTPBin 6,007 → 1,689 (71.9%, 0.28×); Petstore 4,634 → 800 (82.7%, 0.17×). Total 2,715,668 → 393,988: **mean 85.5% reduction (0.15×)**. Vs. OpenAPI JSON: 88.6% average claimed in abstract (Table 5: GitHub 86.6%, Twilio 93.7%, Petstore 79.0% vs. JSON; vs. minified JSON: 79.8%/90.9%/79.0% — savings are structural, not whitespace).
- **Attribution (§8.1):** metadata elimination ~25–30%; signature syntax vs. nesting ~25%; type-system compaction ~15%; error centralization ~10–20% (dominant for GitHub: 1,594 error defs → 14 lines).
- **Scaling:** reduction generally increases with API complexity (types count); HTTPBin (0 types) lowest at 71.9%.
- **Tokenizer consistency (Table 6):** within 0.5–1.9% across cl100k_base/o200k_base — tokenizer-independent.
- **Cost (Table 9, GitHub spec as context, $3/M input):** OpenAPI YAML $5.44/call ($5,436/1K calls) → LAPIS $0.94/call ($939/1K); savings $4,497 per 1K calls at 1,000 calls/day.
- **Error duplication (Table 2):** GitHub 1,594 error defs / 14 unique codes (404 ×531, 403 ×349, 422 ×261); Petstore 26/3; Twilio 1/1.

## 9. Leakage & limitations
Adversarial reading: (1) The headline metric (token reduction) is measured, but the operative claim — that LLMs reason as well or better with LAPIS — has no experiment; the paper admits this. A format that discards information could degrade tool-call accuracy even at 85% fewer tokens, and the lossy conversions (oneOf → most common variant, complex unions → any) are exactly where an agent could pick the wrong variant. (2) The [limits]/[webhooks]/[flows] sections — the "information gain" selling point — are NOT produced by the deterministic converter from OpenAPI (OpenAPI can't express them); they must be hand-authored, so real-world LAPIS docs will usually lack them. (3) Single-author independent researcher; converter fidelity on nonstandard specs is hedged. (4) Cost math uses February 2026 Claude Sonnet 4.5 pricing — directionally right, not current. (5) For GSE: sports-data APIs (The Odds API, MySportsFeeds) may not publish OpenAPI specs at all — many use plain docs pages, in which case the converter path doesn't apply and LAPIS docs must be hand-written.

## 11. GSE implementation spec
(1) For each sports-data API GSE uses, obtain or reconstruct its OpenAPI spec (where the provider publishes one) and convert with `pip install lapisspec`; where no spec exists (most sports APIs), hand-author a LAPIS doc from the provider's docs pages — the [limits] section is the highest-value part (rate limits, quotas, tiers map directly to HiveMind provider profiles); (2) store the LAPIS docs in the Sports repo (docs/research/ or a new docs/api-contracts/) as the canonical machine-readable contract per provider; (3) inject the LAPIS doc into agent context instead of raw documentation or full OpenAPI; (4) measure: context tokens per API-using task before/after (target ≥70% reduction), and tool-call correctness (correct endpoint + params on first attempt) to catch the lossy-conversion risk from §9. Estimated effort: 2–3 days for the first 3–4 providers (The Odds API, MySportsFeeds, SportsDataIQ), then ~1 hour per additional provider.

## 12. Reproducible test
Clone https://github.com/cr0hn/LAPIS; run `pip install lapisspec` and convert a public spec (e.g., Petstore); verify token counts with tiktoken cl100k_base reproduce Table 4 within 5% (Petstore: YAML 4,634 → LAPIS 800, 82.7%). For GSE: convert/hand-author LAPIS for The Odds API; run 20 representative GSE agent tasks (fetch odds, fetch scores) with the LAPIS doc vs. raw docs in context; check token reduction ≥70% AND first-attempt tool-call accuracy within 5 pp of the raw-docs baseline. Exact metric: tokens/task + first-attempt accuracy. Exact baseline: raw provider documentation in context.

## 13. Acceptance / rejection gate
ADAPT if: (a) the converter reproduces Table 4 within 5% on at least 2 of the 5 corpus specs; (b) the GSE pilot shows ≥70% context-token reduction with first-attempt tool-call accuracy within 5 pp of baseline; (c) hand-authored [limits] sections match observed provider rate limits (verify against actual 429s). Reject hand-authoring LAPIS for providers whose docs change frequently unless a refresh process exists — a stale compact spec is worse than verbose live docs. If accuracy drops >5 pp, keep LAPIS only for the [limits]/[flows] operational sections and use full docs for endpoints.

## 14. Improvement experiment
Close the paper's admitted gap: run the **LLM comprehension benchmark** the authors left as future work, on GSE's own APIs. Randomized trial: N=50 API tasks × 2 context conditions (LAPIS vs. OpenAPI/raw docs), measuring first-attempt tool-call accuracy, tokens consumed, and task success. This tests whether the 85.5% token reduction preserves reasoning quality — the claim the paper never validates. If LAPIS wins on tokens but loses >5 pp on accuracy, test a hybrid: LAPIS [meta]+[ops] signatures plus full JSON Schema only for the endpoints the task actually calls (retrieved on demand) — measuring whether selective expansion recovers accuracy at a fraction of the token cost.
