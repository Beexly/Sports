# [0115] HiveMind: OS-Inspired Scheduling for Concurrent LLM Agent Workloads (arXiv:2604.17111v1)

**Verdict:** ADAPT — a zero-code-change transparent proxy applying five OS scheduling primitives to concurrent agents; directly applicable to GSE's concurrent-agent infrastructure (Motif/Hermes/Minis lanes, OmniRoute/OpenRouter rate limits, retry storms). ## 1. Research question
When multiple LLM coding agents share a rate-limited API endpoint, they exhibit resource-contention patterns analogous to unscheduled OS processes competing for CPU, memory, and I/O — thrashing, starvation, and cascading failure. Motivating incident: 3 of 11 parallel Claude Code agents died (2 ECONNRESET, 1 HTTP 502; 27% failure rate) despite the API having sufficient aggregate capacity to serve all 11 sequentially, wasting ~135K tokens and ~15 minutes. HiveMind asks: can five OS-inspired scheduling primitives — admission control, rate-limit tracking, AIMD backpressure with circuit breaking, token budget management, priority queuing — be composed as a transparent HTTP proxy to eliminate these failure modes with zero agent-code changes?

## 2. Dataset / schema
Not a data paper: evaluation is synthetic-behavioral. (a) Motivating incident: 11 concurrent Claude Code agents generating proof-of-concept security scripts through one Anthropic API key via a single network proxy (April 15, 2026): 8 completed (73%), 2 died ECONNRESET (18%), 1 died HTTP 502 (9%); ~45K tokens wasted per dead agent (~135K total). (b) Mock API server simulating realistic LLM API behavior in Anthropic and OpenAI response formats: configurable RPM limits, error injection (random HTTP 502 and connection resets at specified rates), provider-specific rate-limit headers (anthropic-ratelimit-*, x-ratelimit-*), latency (base + jitter + configurable spikes), concurrency limits, SSE streaming in both formats. Mock agents make N sequential API calls simulating multi-turn coding sessions; an agent "dies" on the first unrecoverable error. (c) Real-world validation: Ollama serving Qwen_3.5-4B (GGUF, Q_4_K_M) and an MLX inference server serving Qwen 3.5-4B-4bit; 10 agents × 3 turns each. No data access/link for the mock server or agent scripts stated.

## 3. Method / model
HiveMind is a transparent HTTP reverse proxy (Python 3.11, asyncio, Uvicorn + Starlette, httpx upstream; runs as `hivemind proxy`; also registers as an MCP server exposing eight tools: hm.submit, hm.batch, hm.status, hm.priority, hm.budget, hm.metrics, hm.config, hm.setup). Agents call http://localhost:8765/v1/messages; the proxy applies five primitives:
1. **Admission control:** gated counter A protected by asyncio.Condition (not a semaphore — dynamic resizing via notify_all/notify); request admitted when A < Cmax, else waits. On Cmax decrease, the new limit takes effect naturally as active requests complete.
2. **Rate-limit tracking:** two-level — reactive header parsing (anthropic-ratelimit-requests-remaining, x-ratelimit-remaining-requests, retry-after), proactive pause when remaining capacity < threshold (default 10% of limit with ≤2 requests remaining); proactive RPM/TPM sliding-window counters pre-seeded from the detected provider profile (covers providers like Ollama with no rate-limit headers).
3. **AIMD backpressure with circuit breaking:** TCP-style additive-increase/multiplicative-decrease on concurrency c_t using average latency ℓ̄ over a sliding window of W samples vs. target L_target; on errors (429, 502, reset) multiply by β. Overlaid circuit breaker: opens when error rate e/n ≥ τ (default N=20, τ=0.50) → fast-fail 503 + Retry-After; half-open after cooldown T_cool (10 s) with a single probe; closes on probe success. Controller holds a direct reference to the admission controller (set_admission / set_max_concurrency) — no polling lag.
4. **Token budget management:** per-agent token ceiling from a global pool; cumulative input+output tokens tracked per agent (extracted from message_start / message_delta SSE events, or JSON bodies, else heuristic 1 token/4 chars); at 85% utilization warn, at 100% checkpoint (state to disk) and stop — analogous to the OOM killer.
5. **Priority queuing with dependency DAG:** ordering by (1) priority level (Critical > High > Normal > Low), (2) estimated token cost (shortest-job-first within priority), (3) creation-time FIFO tiebreaker; dependencies as a DAG with cycle detection; a task isn't eligible until all predecessors complete.
6. **Transparent retry:** intercepts retryable errors (HTTP 429, 502, 503, 529, ECONNRESET, RemoteProtocolError) and retries with exponential backoff + jitter, delay d_k = min(d_max, d_base·2^k + U(0, d_base)), d_base=1 s, d_max=30 s; Retry-After header overrides. SSE streams pass through unbuffered; the admission slot is held for the stream's duration.
- **Provider autodetection:** regex on upstream URL → one of six profiles (Anthropic, OpenAI, Azure OpenAI, Google AI, Ollama, generic fallback), each specifying RPM/TPM defaults, max concurrency, rate-limit header field names, retryable status codes, AIMD params (α, β, L_target), auth header name.

- **Circuit breaker (Eq. 3):** "state = open, if e/n ≥ τ, n ≥ N; halfopen, if open and t > t_open + T_cool; closed, if halfopen probe succeeds" with N=20, τ=0.50, T_cool=10 s. *(Reconstructed — uncertain.)*
- **Retry delay (Eq. 4):** "d_k = min(d_max, d_base·2^k + U(0, d_base))" with d_base = 1 s, d_max = 30 s, U(0, d_base) uniform jitter. *(Reconstructed — uncertain.)*
- Default provider profiles (Table 4): Anthropic — RPM 50, TPM 80K, Max C 5, L_target 3,000 ms; OpenAI — 60, 150K, 10, 2,000 ms; Azure — 60, 120K, 10, 3,000 ms; Google AI — 60, 100K, 8, 2,000 ms; Ollama — 1000, 10M, 2, 10,000 ms; Generic — 60, 100K, 5, 2,000 ms. AIMD defaults: α=0.5, β=0.5, L_target=2000 ms (Ollama overrides β=0.7, L_target=10,000 ms). Condition-variable admission adds ~50 µs overhead per acquire/release — negligible vs. 500–5000 ms API latency.
- Assumptions: agents are stateless HTTP clients addressable at a proxy endpoint; provider rate limits are expressible as RPM/TPM sliding windows; latency is a congestion signal (TCP analogy); token counting from SSE events is trustworthy when available; no cross-agent filesystem/tool-call coordination (explicitly out of scope); single-machine scope (Redis-backed distributed scheduling "architecturally supported but not yet evaluated at scale").

## 5. Features / target
No ML features/target — this is a systems paper. Control variables: concurrency level c_t, admission threshold C_max, provider RPM/TPM counters, per-agent token budgets, task priorities/DAG edges. Measured outcomes: agent failure rate, tokens consumed by dead agents (waste), wall time, tasks completed, effective throughput (tasks/min), proxy overhead per request. The proxy is transparent: SSE streams forwarded chunk-by-chunk without buffering; non-streaming JSON bodies parsed for token counts.

## 6. Validation design
- Seven scenarios (Table 5) on the mock server, Direct (uncoordinated) vs. HiveMind: micro-5 (5 agents, RPM 50, 0% error), micro-10, micro-20, micro-50, replay-11 (11 agents, RPM 60, 8%+5% error), stress (20 agents, RPM 20, 10%+5% error), latency-spike (10 agents, RPM 60, 0% error).
- Ablation (Table 6): replay-11 with each primitive disabled in turn (No admission, No rate limit, No backpressure, No retry, Admission only) vs. Full HiveMind.
- Real-world validation (Table 7): Ollama and MLX local servers, 10 agents × 3 turns, Direct vs. HiveMind, proxy overhead measurement.
- Cost analysis (Table 8): wasted-token cost at Anthropic Haiku/Sonnet/Opus pricing extrapolated to 10 runs/day.
- A 174-test suite validates correctness across all primitives; MIT license at https://github.com/jayluxferro/hivemind.
- Weaknesses: mock evaluation is primary; local models "queue gracefully" so the stampede scenario isn't reproducible on them (authors admit the real failure mode needs a cloud API with hard rate limits — production validation against Anthropic/OpenAI at 20–50 agents is listed as future work); no confidence intervals or repeat counts reported; residual failures attributed to error-injection rates exceeding the retry budget.

## 7. Numerical results / baselines
- **Table 5 (failure rates, Direct → HiveMind, Δf percentage points):** micro-5: 0% → 0% (Δf 0, Δw 0); micro-10: 100% → 10% (−90, −100%); micro-20: 100% → 10% (−90, −94%); micro-50: 100% → 0% (−100, −100%); replay-11: 73% → 18% (−55, −48%); stress: 100% → 10% (−90, −100%); latency-spike: 100% → 0% (−100, −100%). Residual failures in replay-11/stress "arise from error injection rates that exceed the retry budget."
- **Ablation (Table 6, replay-11):** Full HiveMind — 11 alive, 0 dead, 0.0% fail; No admission — 11/0, 0.0% ("Compensated"); No rate limit — 11/0, 0.0% ("Compensated"); No backpressure — 10/1, 9.1% ("Marginal"); No retry — 4/7, 63.6% ("Most critical"); Admission only — 2/9, 81.8% ("Insufficient"). Finding: transparent retry is the single most critical primitive; admission control alone is insufficient (limits concurrency but doesn't handle rate-limit errors or resets); other primitives are compensated by the remaining ones; combined they are most effective.
- **Real-world (Table 7):** Ollama — Direct 10/10, 0%, 30.5 s; HiveMind 10/10, 0%, 28.5 s (7% faster: admission gate C_max=2 matched Ollama's natural concurrency); MLX — Direct 10/10, 3.9 s; HiveMind 10/10, 3.6 s. Proxy overhead < 3 ms/request. One earlier MLX failure (10%, RemoteProtocolError) resolved by adding that pattern to the retryable list.
- **Cost (Table 8, daily at 10 runs/day):** Haiku ($0.80/M): Direct $0.35 → HiveMind $0.01, 97% savings; Sonnet ($3/M): $1.31 → $0.05, 96%; Opus ($15/M): $6.55 → $0.24, 96%. "In production workloads with 20–50 agents running continuously, waste scales to hundreds of dollars per day."
- Scaling (Figure 4): direct mode completes zero agents beyond 5 concurrent; HiveMind scales linearly; throughput strictly higher on completed work (direct "finishes fast" only because agents die).
- Figure 6: wasted tokens reduced 96–97% (Direct wastes 1–12K tokens per scenario; HiveMind near-zero).

## 9. Leakage & limitations
Adversarial reading: (1) primary evaluation is a mock the authors built — realistic but not production cloud traffic; the headline 72–100% → 0–18% reduction has not been validated against Anthropic/OpenAI at 20–50 concurrent agents (authors list this as future work); (2) no repeat counts or confidence intervals; (3) single-machine scope — GSE's agents run across machines (VM, Windows box, Minis's phone) sharing keys, where Redis-backed distributed state is only "architecturally supported"; (4) token estimation falls back to 1 token/4 chars when provider tokenizers are unavailable — underestimates CJK, overestimates code; (5) no cross-agent filesystem/tool-call coordination (two agents writing the same file remain a user-level concern — relevant to concurrent GSE file writes); (6) priority is static at submission time, no dynamic promotion of near-complete agents; (7) the ablation's "compensated" findings are scenario-specific (replay-11) — may not transfer to pure rate-limit regimes; (8) per-agent retry critique (thundering herd) is real, but frameworks like LangChain already have partial solutions; the paper's contribution is centralization + zero-code-change.

## 14. Improvement experiment
Add cross-agent **filesystem/tool-call coordination**, which the paper explicitly leaves out: extend the proxy's admission layer with a per-resource lock table (file paths, repo branches) so two agents cannot write the same file concurrently — the exact failure mode GSE's concurrent lanes (Motif + Hermes + Minis on the same Sports repo) face. Test: run two agents editing the same markdown file through the proxy with and without the lock table; measure conflict/corruption rate. Second experiment: dynamic priority promotion (promote agents within 1 turn of completion, demoting long-runners — multilevel feedback queue) to improve average completion time, measured on the micro-20 scenario.
