# [1842] OpenFE: Automated Feature Generation with Expert-level Performance (arXiv:2211.12507)

**Citation:** Tianping Zhang, Zheyu Zhang, Zhiyuan Fan, Haoyan Luo, Fengyuan Liu, Qian Liu, Wei Cao, Jian Li (2023). *OpenFE: Automated Feature Generation with Expert-level Performance*. arXiv:2211.12507v3. Published at ICML 2023 (PMLR 202). URL: https://arxiv.org/abs/2211.12507
**Ledger completed:** 2026-09-22. **Read:** full text (arXiv PDF, 2211.12507v3, lines 0–2598, all sections incl. algorithms, theorems 4.1/4.2 and full Appendix A proofs, Tables 2–16, Figures 1–3, conclusion/limitations).
**Verdict:** ADAPT

Rationale: a production-ready expand-and-reduce feature generator whose FeatureBoost evaluator and two-stage pruning plug directly into GSE's tabular pipeline, but it must be adapted for time-ordered sports data since the paper explicitly cannot handle time-series constraints.

## 1. Research question
How can automated feature generation (a) efficiently and accurately evaluate the *incremental* performance of candidate features from a vast pool, without the prohibitively expensive standard procedure of retraining the model on the full feature set for every candidate, and (b) cheaply prune millions of candidates? As a secondary question: can generated features improve even state-of-the-art tabular DNNs, and is feature generation theoretically justifiable? One paragraph answer from the paper: yes — FeatureBoost (gradient-boosted residual fitting on top of base-model predictions) evaluates incremental gain far faster than retraining; a coarse-to-fine two-stage pruning (successive halving, then MDI-based attribution) retrieves sparse effective features; empirically OpenFE beats all reproduced baselines on 10 benchmark datasets plus 49 OpenML CC18 datasets, beats 99.3%/99.6% of Kaggle teams in two competitions, and matches the 1st-place team's feature set on IEEE fraud; theory (Theorems 4.1/4.2) shows generated GroupBy-style features can drive test loss to zero where base-only models provably cannot.

## 3. Method / model
Expand-and-reduce framework. **Expansion:** enumerate candidate features by applying a fixed operator set to base features. Unary ops (log, sigmoid, square, Freq, etc.) and binary ops (+, −, ×, ÷, min, max, GroupByThenMean, GroupByThenStd, GroupBy, Combine, etc.); first-order = one operator per feature; O(d·m²) candidates for m features and d binary operators. **FeatureBoost (Algorithm 2):** instead of retraining, fit a new model f′ *only on the new features* to the residuals of the base model's predictions: minimize L(f′) = Σᵢ l(yᵢ, ŷᵢ + f′(xᵢ[T′])), and score Δ = L(f) − L(f′) as the incremental gain estimate. Implemented with LightGBM GBDT (chosen because GBDT dominates tabular data and handles missing/categorical values natively). **Two-stage pruning (Algorithms 3–4):** Stage I — SuccessivePruning: split D into 2^q blocks; at iteration i build subset Dᵢ from 2^i random blocks, score each candidate τ alone with Δ_τ = FeatureBoost(Dᵢ, {τ}, ŷ), keep top half, deduplicate identical features; finally drop any τ with Δ_τ ≤ 0. Stage II — FeatureAttribution: feed base features T + surviving candidates A′(T) into FeatureBoost for the joint Δ, attribute importance per feature via MDI (mean decrease in impurity; MDI vs PFI vs SHAP compared in Appendix C.6), keep top-ranked candidates. Final model = base + selected generated features. Only first-order features used in main experiments; second-order found hardly effective (Appendix E.2).

## 4. Equations & assumptions
- Problem definition (Eq 1): max_{S ⊆ A(T)} E(L(D_tr, T+S), D_vld, T+S), where A(T) is all candidate features generable from base set T, L is the learning algorithm, E the evaluation metric (larger better).
- Loss: L(f) = Σ_{i=1}^{n} l(yᵢ, f(xᵢ[T])), l e.g. MSE.
- FeatureBoost objective: L(f′) = Σ_{i=1}^{n} l(yᵢ, ŷᵢ + f′(xᵢ[T′])); incremental gain Δ = L(f) − L(f′).
- Theorem 4.1 (informal): under the paper's two-phase transductive data-generation model (Appendix A) with bounded Rademacher complexity, ERM with a feature-generation function H satisfies L^{test}_D(H, f̂) ≤ O(Rad_{k1}(F) + p·ln(4δ⁻¹)/k₁ + p·d·ln(4d(k₁+k₂)δ⁻¹)/h) with probability ≥ 1−δ, where k₁/k₂ = #groups train/test, h = points per group; test loss → 0 as k₁, h → ∞.
- Theorem 4.2 (informal): without feature generation there exists a problem instance where *any* predictor f′ incurs non-vanishing constant test loss regardless of k₁, k₂, h.
- Assumptions (stated): two-phase generative model with group structure (categorical feature partitions data into groups; target depends on group statistics — e.g., user id → mean transaction size); bounded Rademacher complexity; "fairly standard learning theoretic assumptions". Effective features are sparse in candidate space (motivates coarse-to-fine pruning).

## 5. Features / target
Input: base tabular features (numerical, categorical, ordinal) of each benchmark dataset — exact per-dataset schema in Table 2 (see §2). Generated features: unary transforms (log/sigmoid/square/Freq) and binary transforms (+,−,×,÷,min,max) plus GroupBy aggregations (GroupByThenMean/Std/Max/Min/Count etc.) of numerical features keyed by categorical features. Target: dataset-dependent (RMSE regression, AUC binary classification, accuracy multi-class). Horizon: static supervised prediction (no time dimension; paper explicitly does NOT handle time series — §conclusion limitations).

## 6. Validation design
Each of the 10 datasets has one fixed train/validation/test split; all methods use identical splits. Hyperparameter tuning follows Gorishniy et al. Fair-comparison rule: same number of new features generated per method. Baselines: Base (no generation), NN (DCN-V2 last hidden layer as features), FCTree (reproduced), SAFE (reproduced), AutoFeat (reproduced), AutoCross (reproduced), FETCH (reproduced); learning-based methods LFE/ExploreKit/NFS/TransGraph not reproducible (details missing) — OpenFE run on *their* reported datasets and compared against their published numbers in Appendix C.1. ## 9. Leakage & limitations
Adversarial read: (a) FeatureBoost scores candidates on the *same* data used to train the base model ŷ — incremental Δ is computed in-sample-ish (on D with predictions from a model trained on D), so candidate selection can overfit the training set; the paper mitigates by final evaluation on held-out test, and results hold there, but the selection statistic itself has optimism. (b) Successive pruning's random-block subsampling adds variance; hyperparameters (q, top-k) are fixed heuristics. (c) Baselines are the authors' own reproductions of FCTree/SAFE/AutoCross (validated against reported numbers in C.4, but reproduction fidelity for AutoCross involved re-implementation choices). (d) Learning-based methods (LFE, ExploreKit, NFS, TransGraph) excluded from head-to-head — compared only via reported numbers in Appendix C.1. (e) Kaggle "beats 1st-place team" claim: the 1st-place team's actual winning ensemble was withheld; comparison is against one shared XGBoost model with their shared features vs OpenFE features on a reproduced baseline — strong but not a true head-to-head. (f) **Time series explicitly unsupported** — "OpenFE cannot handle time series data... new features should be computed from the past data; OpenFE cannot handle such constraints" (Conclusion). This is the critical gap for sports. (g) Second-order features "hardly effective" — the method is effectively a first-order interaction/groupby engine. (h) No significant gain on 19/68 CC18 datasets — feature generation is not universally useful; needs a per-dataset go/no-go.

## 11. GSE implementation spec
Build "GSE-OpenFE" as a batch feature-discovery service: (1) Base table: game-level (or team-game) rows from nflverse play-by-play aggregates 2006–2024 — base features: EPA/play, success rate, dropback/rush EPA splits, pressure rate, explosive-play rate, turnover luck proxies, rest days, dome/outdoor, spread-context features. (2) Expansion operators restricted to *time-safe* ones: GroupByThenMean/Std/Min/Max/Count with expanding-window semantics keyed by team_id and season (computed only from prior games — this is the core adaptation vs the paper), binary ops (+,−,×,÷ with zero-guard, min, max) on rate features. Exclude lookahead ops. (3) FeatureBoost: LightGBM base model on hand-built baseline features → GBDT residual fitter per candidate → Δ = train-loss reduction; successive pruning with q≈3 blocks over seasons. (4) Stage II MDI attribution on surviving candidates with full feature set. (5) Survivors promoted into the engine's feature store with provenance (operator, keys, window). Serving: offline batch (weekly regeneration); selected features frozen per season to avoid retraining leakage. Effort: ~2–3 days (OpenFE is open-source; the time-aware GroupBy rewrite is the real work).

## 12. Reproducible test
Dataset: nflverse play-by-play aggregated to team-game rows, seasons 2020–2024. Train 2020–2022, validation 2023 (for FeatureBoost scoring and pruning), test 2024 (frozen, never touched during discovery). Target: home-team cover (binary) or game total over/under — pick spread cover to match the engine. Metric: log-loss on 2024 test. Baseline: LightGBM on Garrett's hand-built feature set (the gse-lab 15-family CSVs). Procedure: run time-aware GSE-OpenFE on train/validation only; add surviving features; compare test log-loss vs baseline. Rerun 5 seeds; Welch t-test p<0.05.

## 13. Acceptance / rejection gate
ADOPT the discovered feature set (merge into production engine features) iff test log-loss improves by ≥ 0.003 on the 2024 NFL held-out vs the hand-built baseline, with zero leakage violations (every GroupBy feature provably computable from pre-game data; audit via recomputation on a row-sample). REJECT (keep manual features only) if gain < 0.003, if any surviving feature fails the time-safety audit, or if validation-selected features degrade test (selection overfit). Gate decided before the run; one shot per season-window.

## 14. Improvement experiment
Beyond the paper: make FeatureBoost *time-aware and residual-targeted*. Instead of scoring candidates against base-model residuals on pooled data, score them per rolling-season block and require Δ > 0 in ≥3 of 4 validation seasons (stability filter — kills era-specific flukes like the 2020 COVID season). Second: add a proper-scoring final filter — replace the paper's MDI attribution (which optimizes training loss) with permutation importance measured in *log-loss on the validation season*, so features must improve the actual betting metric, not just fit. Hypothesis: this yields fewer, stabler features and closes the train-selection optimism gap noted in §9.
