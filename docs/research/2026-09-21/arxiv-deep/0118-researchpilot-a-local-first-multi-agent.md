**Citation:** Peng Zhang (pengz7720@gmail.com). *ResearchPilot: A Local-First Multi-Agent System for Literature Synthesis and Related Work Drafting*. arXiv:2603.14629v1, March 2026. URL: https://arxiv.org/abs/2603.14629v1

**Verdict:** ADAPT — an open-source, self-hostable four-stage literature-synthesis pipeline (Search → Extraction → Synthesis → Writer) with DSPy typed contracts, report persistence, and semantic history search. ## 1. Research question
Can literature-review assistance be implemented as a transparent, inspectable multi-stage pipeline rather than a single opaque "summarize the literature" prompt? ResearchPilot decomposes the task into four constrained stages — paper retrieval, per-paper structured extraction, cross-paper synthesis, related-work drafting — each with explicit typed inputs/outputs, wrapped in a local-first web app (FastAPI + Next.js + SQLite + Qdrant) with streaming status, report persistence, and semantic search over prior runs. The paper claims no algorithmic novelty: the contribution is a systems design and reproducible workflow, evaluated through automated tests and end-to-end local runs.

## 2. Dataset / schema
No research dataset. Inputs at runtime: a natural-language research question (e.g., "What methods improve factuality in long-form LLM generation?"). Retrieved corpus: Semantic Scholar + arXiv, filtered to entries with abstracts, deduplicated by DOI/title, truncated to at most 10 papers. Persisted artifacts per report (SQLite + Qdrant): original question, retrieved papers (identifier, title, abstract, source, URL, year, authors, DOI), structured extractions, synthesis (consensus/contradictions/open gaps), markdown draft with [R1]/[R2] labels, warnings, references, timestamp. Embedding modes: remote / local / auto (local default: BAAI/bge-small-en-v1.5; keyword fallback when vector search unavailable). No data access link stated (repo URL not stated in the extracted text — flagged as a gap; paper says open-source but no URL captured).

## 3. Method / model
Four-layer system, four-agent DSPy pipeline:
- **SearchAgent:** async queries to Semantic Scholar + arXiv; filters abstract-less entries; dedups by DOI/title; truncates to ≤10 papers; tolerates partial source failure (HTTP 429 on one source → other source still yields a usable set); warnings surfaced to event stream and report.
- **ExtractionAgent:** per-paper DSPy signature over the abstract, returning JSON with five arrays: claims, methods, datasets, results, limitations. Runs sequentially (not parallelized); keeps context windows small, enables granular progress.
- **SynthesisAgent:** consumes extraction list → three fields: consensus, contradictions, open_gaps.
- **WriterAgent:** synthesis + bibliography → markdown related-work draft with inline [R1]/[R2] labels and a references section. First-draft assistant only: "does not verify that every citation label is perfectly supported."
- **Orchestration:** DSPy signatures as typed input/output contracts; provider changes via env config or per-run runtime overrides (OpenAI-compatible, Anthropic, Groq, OpenRouter); POST /research streaming API with lifecycle events (queued, agent_started, agent_progress, agent_completed, done, error); incremental fetch() reader (not EventSource) so the POST body can carry question + config overrides.
- **Persistence:** SQLite for reports; Qdrant for vector artifacts + semantic history search; keyword fallback. BYOK model access; Docker Compose + Makefile; Python 3.11+ backend, Next.js App Router TypeScript frontend.

## 6. Validation design
Systems-prototype evaluation, explicitly "not a comparative benchmark": (a) automated tests — 11 backend tests + 1 frontend smoke test passing locally (streaming, report lookup, setup-failure propagation, report listing/keyword fallback, no API-key leakage in config exposure, dedup/partial-failure search, embedding-mode selection, frontend shell render); "do not establish output quality." (b) Manual end-to-end runs in the web UI (March 14, 2026): one successful run on "recent trends in RAG for QA" — 12.47 s, 10 papers, 10 extractions, 4 consensus / 2 contradictions / 3 open gaps, 2046-char draft, Semantic Scholar 429 warning tolerated via arXiv; then a 3-query repeat batch that failed with provider-side token rate-limit errors before completion — "an important operational result: even when the pipeline implementation is stable, end-to-end reliability remains constrained by external model-provider quotas." (c) Failure-mode catalog (Table 3): Semantic Scholar rate limiting; malformed model JSON (schema validation + defensive parsing); missing remote embeddings (local fallback + keyword fallback); persistence-layer errors (warning surfacing + SQLite-backed persistence). Weaknesses: 3 queries, no human quality ratings, no baseline comparison, no stage-level latency breakdown.

## 9. Leakage & limitations
Adversarial reading: (1) The paper's own central limitation — abstract-only extraction — is disqualifying for GSE's research standard: the arXiv deep-research program requires full-text method/math/dataset extraction (Garrett's standing directive: researched IN DEPTH, not skimmed; abstracts are "insufficient for precise reporting of datasets, experimental settings, or quantitative outcomes" per the paper itself). (2) No citation verification — the WriterAgent can produce plausible-but-unsupported claims; GSE's trust-no-claims standard requires every number sourced to a file. (3) 10-paper cap and Semantic Scholar/arXiv-only coverage miss domain venues. (4) Evaluation is 1 successful run + 3 failed runs — anecdotal. (5) DSPy typed contracts are a thin orchestration claim; the "multi-agent" framing is a fixed sequential pipeline, not agents in any meaningful sense. (6) The rate-limit failure mode (3/3 repeat queries failed) is the same operational reality GSE hits with its own provider quotas — the paper offers no mitigation beyond warnings.

## 14. Improvement experiment
Add the stage the paper explicitly lacks: a **citation-verification agent** that takes each (claim, [Rn] label) pair from the draft and checks it against the cited paper's full text, returning supported/unsupported/partial with the exact supporting quote. Test on the paper's own example output: measure the fraction of draft sentences fully supported by their cited abstracts — the paper admits it doesn't check this, so the baseline unsupported rate is unknown and likely high. Extend further: run verification against full text instead of abstracts and measure how many abstract-unsupported claims become supported — this quantifies the abstract-only fidelity loss the paper flags but never measures.
