## PART 2 — THE CODE AS IT ACTUALLY RUNS

### 2.1 The published-pick path: `packages/prediction-engine/src/scoring.ts` @ e94154fb21 (1,834 lines, 84,140 B)

Three near-identical scoring functions (spread, total, moneyline), each assembling the same factor array (L910, L1262, L1628):

- `consensusFactor` — "Bookmaker Consensus," weight = the consensus score itself (share of books on the side, scaled to WEIGHTS.CONSENSUS_COMPONENT_MAX = 30). A market-structure measure carrying the largest weight on the pick.
- `depthFactor` — "Market Coverage," weight = bookmaker-count score.
- `edgeFactor` — "Pricing Edge," weight **0**, impact neutral; its description honestly states it is a market-internal comparison, "context only — not in confidence." (The one factor already labeled the way the doctrine requires — and it is the one with no weight.)
- `volatilityFactor` — "Market Risk," negative weight, present only when thin-market/variance penalties trigger.
- `contextFactors` — `ctx?.factors ?? []` (L810, L1259, L1564), produced upstream by `game-context.ts`. A prior partial fix, `zeroMarketEchoFactorWeights` (L852, L1574), force-zeroes the Cross-Market factors inside it.
- `shadowEvidenceFactors` — `buildShadowEvidenceFactors(input)` (L811 etc.): the named signal families (player availability, venue environment, pace, officials…) mapped to **weight 0, impact neutral**, description = the family's why-used-or-blocked note.
- `independentEdgeFactors` — "Independent Edge (sources)," weight = rankingScore − confidence: an external-model-vs-market comparison, the only non-market quantity that can carry weight, and it is still a comparison *to the market*, not a read of the game.

**Confidence** (L854–859, repeated L1271, L1588) is one clamped sum: consensusScore + depthScore + volatilityPenalty + lineMovementScore + restAdvantageScore + historicalFormScore + dataQualityPenalty + headToHeadScore + venueFormScore + uncertaintyPenalty + scheduleStressScore + injuryScore + ngsTrackingScore + dispersionScore + 10. Fifteen terms. The football content of the pick is exactly two of them — `injuryScore` and `ngsTrackingScore` — both arriving as pre-collapsed scalars.

**The published probability is 85% market by construction**: the factorBreakdown block (~L1053) records fairProbability as `recalibrateProbability(rank.rankingP, fairProb)` with the in-code comment "The mix puts 85% on the market (see engine/probability-recalibration.ts)."

**The reasoning sentences** (L1027/1044, L1309, L1698) are assembled market-first: selection + line + book count, fair-value clause, Edge %, contextNote (short phrases fired by thresholds on the aggregate scores — "biophysical injury advantage" when injuryScore > 1, L970), falsifier note, "Confidence: N/100." `reasoningShort` = consensusClause + firstContextClause. No scheme, no personnel matchup, no coach, no spot narrative, no corpus or mind output appears in any of the three, because none is an input to the file.

**`factorNarrative` / `factorHeadline` occur 0 times in this file.** The narrative module (§2.3) is not imported at the audited commit.

### 2.2 The context factory: `packages/prediction-engine/src/game-context.ts` @ e94154fb21 (1,159 lines)

`computeGameContext` emits 13 distinct factor types: Line Movement (L85, L122), Rest Advantage (L184), ATS Form (L252), Data Quality (L316, L324), Head-to-Head Form (L388), Venue Form (L444), Cross-Market Alignment (L483), Cross-Market Divergence (L493), Schedule Density (L561), Signal Conflict (L620), Biophysical Injury Signal (L705), NGS Tracking Edge (L769), Multi-Book Dispersion Penalty (L826). This is where the facts die: the module receives aggregate inputs (scores, counts, rates) and emits factors whose descriptions are generic templates. A Biophysical Injury Signal factor exists; the injured players' names are not in it, because they were never in its inputs. Of the 13 types: 5 are market (line movement, cross-market ×2, dispersion, plus data quality as meta), the football-bearing ones (injury, NGS, rest, schedule, H2H, venue, ATS form) are all single-number compressions of their underlying facts.

### 2.3 The narrative module: `packages/prediction-engine/src/engine/factor-narrative.ts` (branch, 4,085 B, sha 543e150a)

There is no family classification anywhere in the module — FactorDetail carries no field the module could use to tell a football reason from a market measure — so the heaviest factors narrate first, and on real picks the heaviest factors are Bookmaker Consensus (w30) and Line Movement (w10). ### 2.4 The intelligence spine: `apps/web/lib/intelligence-core/` @ e94154fb21

**`engine.ts`** (9,327 B). Header: "Master Engine — wires EVERY surface in the repository into the all-knowing reasoning spine… Nothing is deferred." Body of `runIntelligence(bundle)`: `buildSituationalContext(bundle)` → `reason(ctx)` → `explain(ctx, reasoning)` → `runSituationalTrace(ctx, reasoning)` → return. `wireEverything` is an alias export of `runIntelligence` — a two-call function, not a DAG runner: no stages, no checkpoints, no receipts, no router, no corpus call in this file. The `GameBundle` type is the deeper foreclosure: its fields are market, six situation scalars, and DB row arrays (injuries, NGS, player stats, ratings, weather, game signals, snaps) plus caller extras. **There is no field through which a corpus evaluation, a mind evaluation, a router premise, a narrative, or a coaching tendency could enter.** The situational trace runs after `reason()` has already fixed calibratedProb and publishState, is fail-open by contract ("a trace failure records the reason and never blocks the pick"), and its result is attached as a sidecar (`situationTrace`) that nothing downstream consumes to change the number or the sentence.

**`reasoning.ts`** (650 lines, 27,817 B). Header doctrine comment (L1–24) lists the surfaces feeding the core and describes the research corpus as "(methods, not auto-activated)". `reason()` (L271): familyWeights = base × average trust × freshness (L301–326); `situationalShift` accumulated from hand-coded scalar rules (rest edge, travel, injury adjustments, and charting/scheme leans weighted `o.lean × trust × freshness`, scaled ×0.08, clamped ±0.12); `calibratedProb = clamp(calibratedBase + situationalShift, 0.05, 0.95)`; the why/whyNot prose is framed on edgeVsMarket ("Calibrated P … vs market … positive edge … after de-vig" / "respect the close"). The observations' `fact` strings can surface in `why` for strong leans — the one channel where a real fact can reach the sentence — but the observation set is built from the bundle's DB rows and caller extras, and per §2.5 most families never attach.

**The veto.** `reasoning.ts` L470: `if (shouldSuppress(ctx.sport, ctx.pickType, ctx.grade ?? "LEAN"))` → a WITHHOLD reason is pushed; L504–509: any withhold reason forces publishState WITHHOLD. `shouldSuppress` lives in `packages/data-ingestion/src/calibration-weights.ts` (123 lines) L100–107: it scans the static `PUBLISH_ACTIONS` table for a "suppress-or-shrink" row matching sport OR pickType OR grade. The table (L~84–91) marks **pickType SPREAD** (winRate 0.4721, n=1076) and **sport NFL** (winRate 0.4774, **n=155**) as suppress-or-shrink.
