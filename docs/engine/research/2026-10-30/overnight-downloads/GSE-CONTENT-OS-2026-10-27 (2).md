# 1. TIERED GATE SYSTEM
Adapted from Hallmark's three gate tiers [VERIFIED — massive-extract P26 / github-extract #16: Floor = never ships (contrast, focus, reduced motion, invented facts, broken phone layout); Reflex = defaults an agent may overrule on the record; Finish = craft detail, never blocks; a fresh-context reviewer subagent holds the last word].

Every piece passes Gate 0 → Gate 1 → Gate 2, in that order. A piece that fails an earlier gate is never scored by a later one.

## GATE 0 — FLOOR (auto-reject, zero exceptions, no human override except Garrett's direct-order rule in §1.4)
Any ONE item checked = piece is REJECTED back to drafting with the failed item named. No scoring, no staging, no "mostly fine."

### 0A. Numbers and claims
- [ ] Every number in the piece exists in the day's engine packet, byte-for-byte (spread, total, prop line, stat, record). A number typed from memory = reject.
- [ ] Every record/streak claim ("7-2 this week") traces to the graded ledger, not to a prior post's text.
- [ ] No projected stat presented as a final stat; no "will win / lock / guaranteed / free money" outcome claim anywhere, including images and captions.
- [ ] Player availability claims (injury, inactive, starting) match the packet's health layer as of the packet timestamp printed on the piece's draft file.
- [ ] Opponent, date, and kickoff time match the packet. Wrong matchup = reject even if every number is right.

### 0B. Banned content (exact strings/classes)
- [ ] The suspended slogan "WE DETECT. YOU DECIDE." appears nowhere (posts, graphics, video, captions) [VERIFIED standing rule — voice brief 2026-10-04].
- [ ] No engine-speak in public copy: no "model edge," "EV," "CLV," "the engine says," "algorithm," "units" math shown as dollars. Results are stated in units, never dollars [VERIFIED standing rule].
- [ ] No financial-advice framing: no "bet this," "you should wager," stake sizing instructions to the reader. First-person calls ("I'm on…", "my play is…", "no bet for me") are the allowed form [VERIFIED — X voice, 2026-10-22].
- [ ] No NGS player-tracking names/data presented as public content (internal use only) [VERIFIED standing rule].
- [ ] No fabricated quote, screenshot, or testimonial. No AI-generated image presented as a real photo or real game moment.

### 0C. Format integrity
- [ ] Piece fits its template spec (§2) slot count — a missing Proof slot or CTA slot = reject, not a style note.
- [ ] Video: game action, if any, is real footage in clips of 2–4 seconds, telestrated/commentary-led [VERIFIED — standing video rule 2026-09-15]. Any AI-generated segment is visually synthetic on its face (no photoreal fake highlights).
- [ ] Graphics render legibly at phone width: minimum body text 28px at 1080px-wide export, contrast ratio ≥4.5:1 for text [DESIGNED values; the ≥4.5:1 figure follows Hallmark's Floor contrast class, P26].
- [ ] Links resolve (site link, resources link) — a dead link = reject.
- [ ] Platform hard limits respected: X ≤280 weighted characters for a single post (threads split at sentence boundaries), IG carousel ≤20 slides, video aspect/duration per §2 table.

## 3B. KEEP / CHANGE / CUT decision rules [DESIGNED starting thresholds]
Measured at 48 hours after posting [DESIGNED window], minimum sample: 500 views for video/carousel, 1,000 impressions for X text. Below minimum sample = NO CALL (piece is neither kept nor cut; it is re-queued once in a different slot).
- **Video (Film Room/Explainer):** KEEP the passage if its 5-second retention band holds ≥85% of the viewers the previous band held. CHANGE the passage (rewrite/re-cut) if band-to-band drop is 15–30%. CUT the passage from future scripts if drop >30% or the hook band (0–3 s) loses >40% of starters.

Use before building any new format, offer, or production-heavy lane:
1. Build TWO cheap test versions of the thing (in the source: two waitlist landing pages made with ChatGPT Work for an unbuilt feature).

## 4A. Naming / versioning [DESIGNED convention; X draft ID shape is VERIFIED — x-poster skill uses XP-YYYYMMDD-NN]
- **Piece ID:** `GSE-<FORMAT>-<YYYYMMDD>-<NN>` where FORMAT ∈ {BRD, FLM, RND, EXP} and NN is the day's sequence per format (01, 02…). Example: `GSE-FLM-20261029-02`. The X-post edition of any piece also keeps its legacy `XP-YYYYMMDD-NN` draft ID in the same draft file, cross-referenced both ways.
- **Draft file:** one file per piece, `ops/content/drafts/<piece-id>.md`, containing: the piece text/script, the packet timestamp it was drafted from, Gate 0 checklist result, Gate 1 scores + scorer path, Gate 2 finish list, approval state, post URLs per platform, 48-h KPI snapshot. A piece with no draft file does not exist and cannot be posted.
- **Template versioning:** templates are named `<FORMAT>-v<N>` (BOARD-v1, ROUNDUP-v1…). Any §3D review change bumps N by 1 and the old version is archived, never edited in place. A piece records the template version it was built on.
- **Asset versioning:** rendered exports are `<piece-id>_<platform>_<w>x<h>_v<N>.<ext>`; v1 is the first approved render; any re-render after approval bumps N and requires a new approval state note (the posted file must be byte-identical to the approved file).

## 4C. Voice rules — enforcement, not advice [VERIFIED rules — X voice 2026-10-22 + voice brief 2026-10-04, as carried in the build file and MEMORY.md]

### 1.1 Stage 1 — FUEL
- **Inputs:** morning X sweep output (staging dir); engine board/ratings export; injury + usage feeds; yesterday's graded results; SiriusXM notes when present.
- **Outputs:** `packets/YYYY-MM-DD.json` (§1.0) + one `job_runs` row.
- **Tool/route:** the fuel-packet-builder job (§7, J1) — deterministic assembly + one LLM pass (task class: EXTRACTION, §5) to normalize intel items into `intel[]`. Data packages nfl_data_py / sportsdataverse-py (massive O45) replace hand-maintained scrapers as the data substrate.
- **Failure modes:** (a) sweep missing/stale → packet builds with `intel: []` and a `fuel_degraded: sweep` flag; Board/Roundup may still run, Explainer topics fall back to the evergreen bank. (b) engine export missing → **whole pipeline holds**: no Board piece may be drafted from a stale board; packet is written with `board: []` and the day runs in evergreen-only mode (Explainer + Roundup from intel), flagged in job_runs. (c) conflicting results data for yesterday (two sources disagree on a final) → **publication of the record line halts** for that play only (the NFELO rule, massive C28: conflicting scores halt publication), the rest of the packet proceeds.
- **On failure:** (a)/(c) degrade-and-flag, never block silently; (b) hold Board, notify in the daily batch summary. No retry loop — fuel is rebuilt once at the midday refresh job (J2) if the missing input lands.

### 1.2 Stage 2 — DRAFT
- **Inputs:** today's packet; creator standing instructions (§8.1); lessons ledger (active lessons for the format); template set.
- **Outputs:** one `pieces` row per piece in status DRAFTED + `pieces/<piece_id>/script.md` (master script/text) + per-surface variant drafts in `pieces/<piece_id>/variants/`.
- **Tool/route:** drafting job (J3). Model route by task class (§5): Board text and Film Room scripts = VERDICT class; Roundup/Explainer first drafts = BULK class, escalated to VERDICT only for the final pass; captions/hashtags = BULK. One-source → many-surfaces variants are generated in the same pass (the Shauncore/@Mr_Buzzoni repurposing pattern, massive P13/P14: write once, quote/chart it across surfaces over time).
- **Failure modes:** (a) draft cites a number not in the packet → caught at Gate, counts as a drafting defect, logged against the model route (feeds §5 routing decisions). (b) draft duplicates a piece from the last 7 days (same play + same angle) → draft job self-kills it at creation (dedupe check against `pieces`). (c) model route down → fallback per §5 (gateway fallback chain), never a dead stop.
- **On failure:** (b) kill silently with reason `duplicate`; (a)/(c) proceed to Gate / fallback route. Drafting never blocks the day: if J3 fails twice, the day runs with whatever formats drafted successfully and the gap is reported in the batch summary.

### 1.3 Stage 3 — GATE (automatic, before any production spend)
Three checks, in order; a piece must pass all three to reach PRODUCE. This is where production money is protected — rendering an ungated piece is the expensive failure this stage exists to prevent.
1. **Number check (deterministic, no LLM):** every numeral in script.md is matched against the packet. Unmatched numeral → FAIL.
2. **Voice/quality score (LLM, task class QA):** the qi-check pattern from the X pipeline — composite score + density + bait subscores. Threshold = the standing Hold bar from the X lane (composite ≥ 9.2 to pass clean).
3. **Claim check (deterministic + QA pass):** banned-claims list from `packet.constraints`; tout framing is allowed (Garrett's Oct 27 order) but outcome-guarantee language and any record not equal to `packet.season_record` / `yesterday_results` → FAIL.
- **Inputs:** script.md + packet. **Outputs:** `gate.json` per piece: `{number_check: pass|fail(matches[]), voice_score: {}, claim_check: pass|fail(hits[]), verdict: PASS|REWRITE|KILL}` + status change.
- **On failure:** number/claim FAIL → one REWRITE loop (Draft, with the failing matches attached as the rewrite brief); second FAIL → KILL with reason, logged to lessons as a pipeline defect (not a content lesson). Voice score in the soft band → one rewrite; below soft band → KILL. A human may override a voice-score kill in the Approve batch; a number/claim kill has **no override** — the piece dies, a corrected new piece may be drafted.
- **Tool/route:** gate-runner job (J4); QA scoring via §5 QA route; the Hallmark/Impeccable design lint (massive P26/O-class; github #16/#17) runs here for graphic pieces — browser lint against machine-design tells, tiered Floor/Reflex/Finish gates (Hallmark's own structure).

### 1.4 Stage 4 — PRODUCE
- **Inputs:** GATED pieces only. **Outputs:** master files in `renders/` (mp4 for video, PNG set for carousels, final text for text pieces) + `master_path` + `render_minutes` on the piece row.
- **Tool/route:** by piece `route` — FOOTAGE / RENDER / HIGGSFIELD per §2; TEXT pieces skip to Schedule.
- **Failure modes + rules:** render failure → retry 2× with the same inputs; third failure → HELD with the renderer error attached. Higgsfield job failure → §2.3 rules. Voice render failure (VoiceStudio) → retry 1×, then HELD (never substitute a different voice silently — voice consistency is a brand rule). A piece HELD at Produce does not block other pieces.
- **Tool:** render-queue worker (J5) + higgsfield-poller (J6).

### 1.5 Stage 5 — SCHEDULE
- **Inputs:** PRODUCED pieces. **Outputs:** scheduler entries (one per surface variant) + status SCHEDULED.
- **Tool/route:** Postiz self-hosted (github #1: 30+ networks, one calendar, REST API + MCP server — the agent drafts/schedules, the human approves in the calendar). Mixpost (github #2) is the recorded fallback if Postiz blocks on a network's OAuth. Per-channel previews are generated at load time so the Approve stage shows exactly what will post.
- **Failure modes:** a network's OAuth/app missing (each network needs the operator's own developer app per the Postiz entry) → that surface variant is dropped from the piece, the piece proceeds on its remaining surfaces, and the missing surface is reported once, not daily. Scheduler down → pieces wait in PRODUCED; no manual posting workaround (an unlogged post breaks Measure).
- **On failure:** surface-drop rule above; scheduler outage → hold all, report in batch summary.

### 1.6 Stage 6 — APPROVE (Garrett's tap — the single send-authorized seat)
- **Inputs:** the day's SCHEDULED pieces as one batch: per piece — final text/preview per surface, gate.json summary, route, and any HELD/KILLED items with reasons.
- **Outputs:** per piece: APPROVED or rejected (rejection = KILL with his reason, or HELD with his note).
- **Rules:** one batch per day, one pass. Silence is not approval — unapproved pieces stay SCHEDULED and expire at the next day's Fuel run (stale Board pieces are auto-KILLED at expiry; evergreen formats may be re-batched once). This stage is the fan-in point of the whole OS (§8.3): many producers, exactly one seat that can release a publish.
- **Failure mode:** no approval that day → nothing publishes that day. The system reports the expired count; it never publishes to "catch up" volume.

### 1.7 Stage 7 — PUBLISH
- **Inputs:** APPROVED pieces + their scheduler entries. **Outputs:** live posts + `piece_surfaces` rows (post IDs + URLs) + a copy of every variant in `published/<piece_id>/` + status PUBLISHED.
- **Tool/route:** Postiz publish executor (J8), or the existing X-API path for X-only pieces. Predictions freeze at publish: the published variant files are the frozen record (World-Cup-Forecast / NFELO discipline, massive C27/C28 — forecasts stored pre-game, never rewritten; the public page grades them after).
- **Failure modes:** publish API error → retry 3× over 30 min; still failing → piece returns to SCHEDULED and is flagged in the next batch (never force-posted through a second tool — one publish path per surface keeps the record clean). Partial publish (some surfaces live, one fails) → the live surfaces stay; the failed surface retries on its own row; the piece is PUBLISHED with a `partial` flag until all rows resolve or expire at game start.

### 1.8 Stage 8 — MEASURE
- **Inputs:** `piece_surfaces` rows. **Outputs:** `measurements` rows at 3 checkpoints: H1 (1 hour), H24 (24 hours), D7 (7 days) + game-result grading rows appended to the next day's packet (`yesterday_results`, with CLV).
- **Tool/route:** metrics-collector job (J9) via Postiz analytics + platform reads; results grading is deterministic from final scores.
- **Failure modes:** a surface's metrics unavailable → checkpoint recorded as NULL (never estimated, never back-filled from a later checkpoint). Missing metrics do not block Learn — the lesson pass runs on the checkpoints that exist and says so.
- **Rule:** views are never the only metric carried forward — saves/shares/link_clicks are the quality signals the Learn stage weights (§1.9), per the content-testing method in the corpus (retention + passage data over raw totals, igsweep dm-41).

### 1.9 Stage 9 — LEARN (weekly, Sunday)
- **Inputs:** the week's `measurements`, `pieces`, `cost_ledger`, graded results. **Outputs:** (1) per-piece verdict SCORED; (2) new/retired rows in `lessons` + updated `lessons/LESSONS.md`; (3) per-format scorecard (pieces, total views, saves+shares rate, cost per piece, units record for Board); (4) routing changes proposed for §5 (model swaps require a promptfoo-class eval win first, §5.4).
- **Method (from the corpus, igsweep dm-41 — the content-testing loop):** for video, retention data + transcript → passage-level KEEP / CHANGE / CUT calls with timestamps; every finding becomes a lesson row; **old lessons are re-tested before new ones are added** (the method's own rule). For text/carousel: the same verdict at piece level, with the hook line treated as the "passage."
- **Failure modes:** a week with <10 measured pieces → lessons are marked `provisional` and cannot retire an old lesson (small-sample rule: no format is killed or doubled on a thin week). Conflicting lessons (a new finding contradicts an active lesson) → both stay, the newer one is marked `challenged`, and the re-test decides the following week.
- **On failure:** if the Learn job fails, the next week's drafting runs on the previous lessons — stale lessons are a known state, never a silent one (the job_runs row shows it).

- **Input media rule:** generation inputs must be publicly accessible URLs or media uploaded to Higgsfield storage first (docs: "Upload media" step exists for this). GSE inputs come from `assets/` via an upload step in J6 — local paths are never sent as if they were URLs.
- **Polling rule:** J6 (higgsfield-poller) polls each open job every 20s with jitter, up to `max_wait_s` 1800s. Timeout → job marked `stalled`, one resubmit allowed **only if** the original job confirms `failed`/`cancelled` first (a resubmit of a merely-slow job double-spends credits — prohibited). A `failed` status → piece HELD with the API error; no automatic resubmit of a failed generation with the same prompt (a human or the Learn loop changes the prompt first).
- **Output retention rule (hard):** per the docs, output files are available **for at least seven days** — treated by this OS as *up to* seven days for planning. J6 downloads every completed output to `renders/` **in the same run that first sees `completed`**, verifies file size > 0, and only then marks the piece PRODUCED. A piece whose master exists only at a Higgsfield URL is not produced — it is a dead link waiting to happen.
- **Credit guard:** J6 reads the account state available via the API before the day's first submit; if the balance cannot be read, the day's Higgsfield pieces are capped at 1 (the daily promo) until a balance read succeeds. (Balance was NOT checked in the Oct 27 verification — first J6 run closes that gap; flagged in §9.)
- **Genjutsu motion transfer — where it fits:** Genjutsu is the docs' first example endpoint (motion transfer): body = `video_url` (source video, **must be at least 4 seconds** per docs) + `image_urls` (reference image[s]). In this OS it has exactly two legal uses: (1) **creator segments** — transfer a performance/motion onto the AI-creator visual for PROMO/EXPLAINER pieces where the synthetic nature is the format; (2) **style/motion treatment of GSE's own non-game footage** (studio shots, product shots). It is **never** used to fabricate or alter game action — Route A owns game footage and its rule (real, 2–4s, unaltered action) is not waived by this route existing. Note the spec tension, recorded plainly: Genjutsu's ≥4s source minimum vs Route A's 2–4s clip rule — motion transfer therefore never runs on game clips at all, so the two rules never meet on the same asset.
- **Spend gate:** generation spends credits = spending Garrett's money. The route is specced and the key verified, but the first live generation run — and any credit top-up — is his word (standing hard gate). Until then J6 runs in dry mode: builds job objects, validates them against the schema, does not submit.

### 5.2 The per-piece cost ceiling — expressed as rules, set from measurement
Dollar ceilings are **not invented here**. Week 1 is a measurement week: every piece's true cost lands in `cost_ledger` + `pieces.llm_cost_usd`, and the ceilings below are computed from that data at the first Learn run.
- **Rule C1 (soft ceiling):** a piece whose total LLM cost exceeds **2× the trailing 14-day median cost for its format** is flagged in the batch summary with the reason (long packet, rewrite loops, route fallback). Flagged ≠ blocked.
- **Rule C2 (hard ceiling):** no single piece may consume more than **5% of the weekly LLM budget** (budget = a number Garrett sets, or the measured week-1 total until he does). A piece that would cross C2 mid-production is HELD, not finished expensively.
- **Rule C3 (budget auto-pause — Paperclip pattern, massive O44 / github-area record):** per-lane budgets with threshold alerts; at 100% of a lane's weekly budget, that lane's jobs pause themselves and report. A paused lane never borrows another lane's budget silently.
- **Rule C4 (cache before calls):** any prompt whose static portion (creator instructions + format template) exceeds the dynamic portion is cached at the gateway; the OS tracks cache-hit rate per class in the weekly rollup. Low hit rate on BULK = a prompt-structure defect, fixed in the template, not by paying more.

### 5.3 Routing-change discipline
A cheaper model replaces a dearer one in a class only after a promptfoo-class eval (massive O13 / github #53): the same test set (drawn from real past pieces + their Gate outcomes) run on both routes, scored by assertions + QA model, diff reviewed at a Learn run. ### 6.4 Paperclip operating patterns (the desk's house rules)
From igsweep feed-21 + massive O44, adopted as OS rules:
1. **One shared database as single source of truth** — `content_os.db` + the packet files; no stage keeps private state (the pre-Paperclip failure in the source: every agent on its own store).
2. **Fan-in, not fan-out** — many producers, one send-authorized seat (Approve, §1.6). Before: 8 agents answering 8 ways; after: all report to the one seat that sees everything and is the only one allowed to send. In this OS: nothing publishes except through J8 acting on an APPROVED row.
3. **Budgets with threshold alerts + automatic pause** — §5.2 Rule C3.
4. **Kill token-burners** — agents/jobs that spend without producing are turned off at Learn: a job whose last 3 runs produced 0 advanced pieces is disabled and reported, not left idling.
5. **Heartbeat wake-ups instead of idle loops** — jobs wake on triggers (§7), do their work, and stop; nothing polls forever (the Higgsfield poller is the one bounded exception, and it exits when its job list empties).
6. **Atomic task checkout** — a piece row is claimed by exactly one job at a time (status transition is the lock); two workers cannot draft or render the same piece twice.

## §3. Earshot — Produce-exit listen-back QA (fixes H3; W-22)

**Step P-QA (Produce exit, audio-bearing masters only — Route A narration, Route B voiceover, F6 voice pieces, and any master carrying a music bed):**
1. **Transcript match:** the master's audio is transcribed (faster-whisper, local) and diffed against the final post-Gate script. Any misread proper noun, player name, or numeral = FAIL. Word-error rate above 2% on the remaining text = FAIL.
2. **Voice identity:** the narration voiceprint is compared to the standing reference voice (Route A step A5's reference clip). Mismatch = FAIL (a silently substituted voice never ships).
3. **Levels:** clipping present, or music bed above −20 dB under narration (the Film Room spec value, os-quality §2B), or master loudness off the OS standard set at Route A step A6 = FAIL.
4. **Bed intelligibility:** for music beds, the bed is solo-checked for lyric-like artifacts that compete with narration = FAIL.

**Disposition:** FAIL → piece is HELD with `kill_reason = audio-qa:<check name>` and the failing check named in the batch summary. One re-render is allowed (new voice render or new bed, same script). A second FAIL on the same piece → KILL and a lessons row (scope=piece) so Learn sees the pattern. No audio-bearing master reaches Schedule without a P-QA pass row in its piece directory (`pqa.json`: checks, results, timestamp).

## §4. Calibration check (W-23) + measurements schema fields (W-45)
**Calibration step (new standing step in J12, monthly cadence inside the Sunday Learn run):**
- Input: all graded Board plays in `yesterday_results` history carrying `model_prob` and a realized W/L.
- Computation (Uncertainty Toolbox class metrics, named so a builder implements these and not others): Expected Calibration Error (ECE, 10 bins) and Brier score decomposition (reliability / resolution / uncertainty), computed over the trailing graded set.
- Output: one calibration row per month in the Learn scorecard: set size, ECE, Brier components, and the active wording band.
- **Wording band rule (the gate this feeds):** while ECE ≤ `calibration.ece_restriction` (0.08, §2), Board and Explainer copy may use the packet's confidence language as written. While ECE >0.08, Gate 0A gains an active check: any confidence word stronger than the band permits ("strong play" class language) is rejected, and pieces state the model's probability numerically from the packet instead. The band lifts automatically at the first monthly computation at or under the threshold — no human decision, the number decides.
- J12 also writes the calibration row into the packet inputs, so Draft sees the active band before writing, not after Gate rejects.

**Measurements schema amendment (W-45):** the `measurements` table gains two columns: `quote_posts INT NULL` and `follows_attributed INT NULL`. J9 and J-Measure-48h populate them from platform reads where the platform exposes them; where it does not, the value is NULL — never estimated, never carried from another checkpoint. ### W-20 — Gate 0's executor (Opt-U6)
Gate 0 runs in two tiers, and the tier boundary is mechanical:
- **Tier 1 — code, zero model calls.** A single checker (`gate0` step in J4) runs: banned-string scan (slogan, banned-claims list from `packet.constraints`, engine-speak list from `voice/banned.txt`); hashtag count; units-not-dollars pattern check (currency symbols / dollar amounts in public copy); dimension and file checks (contrast value from the render metadata, text-size floor, aspect, slide count vs template); slot-count check against the piece's template; numeral equality against the packet/visual pack; link resolution (HEAD request, 2xx/3xx = pass). Every Tier 1 check is a string, schema, or arithmetic test. A Tier 1 failure is a Gate 0 fail with the check named — no model is consulted and none can overrule it.
- **Tier 2 — batched typed decisions.** The residual judgment checks (availability-claim plausibility against the health layer, fabricated-quote screen, worked-example arithmetic sanity) are NOT run per piece at full model price. A Tier 2 verdict of fail is a Gate 0 fail; an evidence_span that does not quote the piece text is discarded and the check re-runs once, then the piece is HELD.
