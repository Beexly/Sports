## 2. Proposed project identity

### Title

**NOVA: The AI Opportunity Intelligence Engine**

### One-line description

NOVA continuously turns AI releases, platform changes, developer ecosystems, credits, marketplaces, and monetization programs into evidence-backed, reversible engineering and revenue experiments.

### Short description

AI changes faster than a founder or engineering team can research it. NOVA monitors approved first-party sources, distinguishes product capability from distribution and actual payment, maps each change against an existing codebase, and generates a bounded work packet with evidence, economics, rights, security, tests, rollback, and owner-only decisions.

It is designed to prevent two expensive failure modes at once: missing a material change and chasing an attractive announcement that is not actually usable, legal, secure, or monetizable.

### Track rationale

Developer Tools is the best fit because NOVA is an engineering control plane for:

- AI and coding-model change detection;
- platform and API migration intelligence;
- developer-tool and MCP discovery;
- bounded prototype planning;
- cost and token routing;
- marketplace and productization planning;
- evidence-backed coding-agent handoffs.

## 3. Problem

A modern engineering team must track dozens of fast-changing systems:

- models and APIs;
- coding agents;
- SDKs and plugins;
- MCP and agent registries;
- databases and workflow systems;
- security advisories and deprecations;
- startup credits and grants;
- marketplaces, partner programs, affiliates, and creator payouts;
- data/model licensing and evaluation opportunities.

The usual response is a collection of bookmarks, newsletters, screenshots, integration guides, and speculative revenue estimates. That creates volume without decision quality.

The real engineering problem is not finding announcements. It is converting a change into a trustworthy action:

1. What changed?
2. Is the evidence primary and current?
3. Does it duplicate an existing capability?
4. Can it create product value, distribution, revenue, or cost savings?
5. What rights, security, eligibility, or commercial terms apply?
6. What is the smallest reversible test?
7. What outcome would justify adoption, rejection, or scale?

---

## 4. Solution

NOVA implements an evidence-first opportunity pipeline:

1. **RADAR** monitors allowlisted first-party metadata sources.
2. **TERMS** verifies eligibility, pricing, payout, credit, marketplace, and deadline terms.
3. **ATLAS** maps the discovery against the existing repository and capability registry.
4. **YIELD** identifies product, distribution, revenue, partnership, affiliate, data, model, or cost paths.
5. **FORGE** receives a bounded coding packet for an isolated prototype.
6. **PROOF** attacks claims, tests, rights, security, economics, and rollback evidence.

The system never infers that “available,” “approved,” “activated,” “earned,” “invoiced,” and “paid” mean the same thing.

The system also never gives a discovered plugin or model install authority merely because it appears in an official registry.

## 8. Proposed Devpost description

### Inspiration

AI is moving faster than small teams can track. Every week introduces new models, coding agents, APIs, plugins, data systems, credits, marketplaces, partner programs, and monetization claims. The problem is not a shortage of information. It is the absence of a system that can establish what is true, map it to a real codebase, and turn it into a safe engineering or revenue decision.

### What it does

NOVA monitors approved first-party sources and detects material changes. It separates build capability, distribution, native payment, partner access, credits, and negotiated licensing. It scores strategic fit, evidence, revenue potential, time to value, recurring leverage, cost reduction, rights, security, complexity, and vendor dependence.

For each opportunity, NOVA generates either:

- an internal implementation packet;
- an isolated prototype packet;
- an owner decision packet;
- a research hold;
- a watch item;
- quarantine;
- rejection.

Every packet includes exact files, why the work matters, acceptance criteria, test commands, evidence requirements, rollback, and the actions the software is forbidden to take.

### How we built it

NOVA is implemented inside a TypeScript/Next.js monorepo with strict typing, Vitest, GitHub Actions, source-rights gates, an authenticated operator cockpit, and deterministic scoring. Codex and GPT-5.6 are used to build the qualifying public demo and work-packet compiler, run repository validation, and repair failures through an evidence-first development loop.

### Challenges

The hardest challenge was preventing the agent from optimizing for activity. A large credit maximum is not an awarded credit. A marketplace listing is not demand. A plugin registry is not a security review. A model release is not automatically better. A potential payout is not paid revenue.

We built explicit evidence and lifecycle states so those distinctions cannot disappear inside an enthusiastic summary.

### Accomplishments

- Distinguishes native payment from distribution-only platforms.
- Uses sequential money states from discovery through paid receipt.
- Converts changes into bounded coding and owner packets.
- Preserves source and decision evidence.
- Learns from measured outcomes without automatically rewriting production policy.
- Operates with zero automatic external actions.

### What we learned

Autonomy becomes useful when authority is narrow. The strongest agent is not the one that can do everything. It is the one that can research, test, reject, and prepare almost everything while making the remaining human decision unmistakably small.

### What is next

- persistent bitemporal evidence storage;
- scheduled source monitoring;
- JARVIS decision-queue integration;
- isolated FORGE execution;
- PROOF adversarial verification;
- productized NOVA API and enterprise marketplace offers.
